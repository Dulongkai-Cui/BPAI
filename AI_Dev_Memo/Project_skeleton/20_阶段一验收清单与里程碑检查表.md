# 20｜阶段一验收清单与里程碑检查表

## 本文目的

作为 `Project_skeleton` 第一阶段的收口文档，统一沉淀：

- 阶段一到底验收什么
- 各条主线应达到什么程度才算“过线”
- 哪些是必须项，哪些是加分项，哪些可以后置
- 如何用一份检查表，帮助产品、研发、AI 编排、权限治理和后续移动端准备做同一套阶段性判断

本文不替代具体测试用例，也不替代项目管理软件中的任务拆解，而是作为阶段一“是否可以收阶段、进下一阶段”的统一判断基线。

## 1. 阶段一的核心目标再确认

阶段一不是追求“大而全”，而是追求“主干成立”。

如果用一句话总结，阶段一的核心目标是：

> 让 BPAI 从“静态原型 + 分散设想”，进入到“正式产品骨架成立、主链路可跑、核心规则可控”的状态。

因此，阶段一的验收重点不应放在：

- 页面数量够不够多
- 每个子域是否都精修完整
- 视觉是否已经终稿级别

而应放在：

- 六大模块骨架是否成立
- BP问问调度主线是否成立
- 工单、文档、AI 执行之间是否真正串起来
- 权限、回写、协作是否具备基础可控性
- 第一批移动端轻动作是否具备清晰落点

---

## 2. 阶段一的统一验收原则

### 原则 1：先验主链，不先验边缘能力

只要主链没通，做再多边缘页都不算阶段一完成。

### 原则 2：先验对象和规则是否成立，再验视觉是否丰满

如果对象关系、权限规则、回写规则没立住，页面再好看也不能算真正通过。

### 原则 3：验收必须同时覆盖产品、系统、AI、协作和权限

阶段一是系统主骨架阶段，不能只从某一个视角验。

### 原则 4：把“可以后置”的内容主动剥离

只有主动承认哪些还可以后置，验收口径才不会失控。

---

## 3. 阶段一里程碑建议

当前建议把阶段一拆成 4 个可检查里程碑。

## 里程碑 M1：产品骨架与对象骨架成立

判断重点：

- 六大模块定义稳定
- 正式前端不再只有 scaffold
- 核心对象清单已明确
- 模块与对象关系已建立统一口径

## 里程碑 M2：主链路打通

判断重点：

- BP问问 → 工单 / AI / 文档的主链跑通
- 页面级主链路至少有一版可走通
- 工单、文档、AI 执行之间可形成闭环

## 里程碑 M3：协作与回写规则成立

判断重点：

- 文档锁、评论、建议层成立
- AI 结果不失控
- 状态和内容回写规则成立
- 权限边界基本可控

## 里程碑 M4：阶段性可运营与可扩展基础成立

判断重点：

- 总览可看
- 工单可跟
- 文档可协作
- AI 执行可承接
- 移动端第一批轻动作有清晰路线
- 可以进入第二阶段扩展

---

## 4. 阶段一必须通过的总体验收项

下面这些属于阶段一必须项。

## 4.1 六大模块骨架成立

必须满足：

- BP问问、总览、工程队、工单、文档档案室、AI宿舍的定义未被推翻
- 正式前端中至少已存在六大模块骨架入口
- 模块之间导航关系基本可走通

通过标准：

- 新成员进入项目后，能够清楚识别六大模块职责

## 4.2 BP问问主线成立

必须满足：

- BP问问能作为用户入口承接问题
- 能区分简单 / 中等 / 复杂问题
- 能把复杂问题导向工具 / 工作流 / AI员工 / 工单 / 文档上下文
- 最终能返回解释性结果

通过标准：

- BP问问不再只是一个静态聊天壳，而是具备调度语义

## 4.3 工单作为状态承接主对象成立

必须满足：

- 工单能被创建
- 工单状态能被更新
- 工单能关联责任方和关联对象
- 工单能承接异常与归档语义

通过标准：

- 至少一条任务链可以真实进入工单并被跟踪

## 4.4 文档档案室作为内容与协作承接层成立

必须满足：

- 文档 / 表格 / CAD / 合作空间四类入口语义仍成立
- 文档对象可被读取
- 评论与建议机制至少有基础形态
- 锁状态机制至少有基础形态

通过标准：

- 至少一类内容对象能进入“查看 → 评论/建议 → 受控编辑/接力”的协作流程

## 4.5 AI 执行层成立

必须满足：

- AI宿舍中的 AI员工 / 工作流语义成立
- 复杂任务可被调度进入执行层
- 执行后能产生结果对象或结果摘要
- 结果可被 BP问问、工单或文档承接

通过标准：

- 至少一条复杂任务链不再停留在嘴上，而是有执行结果沉淀

## 4.6 权限与回写边界成立

必须满足：

- 至少存在模块访问、对象操作、回写权限三层意识
- BP问问不默认直接大面积正式回写
- AI 默认不直接无限制正式写入
- 文档编辑锁和评论权限不冲突

通过标准：

- 第一阶段系统不会因为权限和回写规则完全缺失而失控

## 5. 按主线拆解的验收清单

下面按主线给出更细的验收口径。

## 5.1 前端骨架线验收清单

### 必须项

- [ ] 正式前端中已承接六大模块基础入口
- [ ] 顶层导航可走通
- [ ] 至少一条 BP问问 → 工单 / 文档 / AI 的主链路页面可走通
- [ ] 关键页面至少支持加载中 / 执行中 / 待确认 / 受限 / 异常等基础状态展示

### 加分项

- [ ] 已有较稳定的对象详情容器页
- [ ] 已有清晰的状态标签与回写反馈提示
- [ ] 页面之间跳转已经围绕对象，而不是仅围绕列表和路由

### 可后置项

- 所有子页视觉精修
- 所有图表地图高级版
- 所有工程队子域深页完整落地

---

## 5.2 后端对象线验收清单

### 必须项

- [ ] 核心对象已形成统一口径
- [ ] 工单对象可创建、读取、更新状态
- [ ] 文档 / 表格对象可读取并被关联
- [ ] 评论对象和编辑锁对象至少有基础承接方式
- [ ] AI 执行结果对象已具备基础承接能力

### 加分项

- [ ] 项目 / 任务上下文对象已形成稳定引用方式
- [ ] 审计记录对象已有统一承接路径

### 可后置项

- 更复杂的项目中心对象
- 更完整的财务 / 后台治理模型
- 边缘业务对象全量展开

---

## 5.3 AI 编排线验收清单

### 必须项

- [ ] BP问问可区分简单 / 中等 / 复杂问题
- [ ] 中等问题可走工具/知识库链
- [ ] 复杂问题可走工作流或 AI员工链
- [ ] AI 执行结果不会只停留在临时对话文本里
- [ ] BP问问能对执行结果做最终表达

### 加分项

- [ ] AI 执行状态在 AI宿舍中可查看
- [ ] AI 失败、待确认、已完成有明显状态区分
- [ ] AI 结果可以自然挂到工单或文档建议层

### 可后置项

- 多执行体复杂协同
- 龙虾内部再调工作流的深层机制
- 高级任务记忆与回放

---

## 5.4 权限与回写线验收清单

### 必须项

- [ ] 已能区分查看、评论、编辑、解锁、回写等核心动作
- [ ] 文档对象编辑受锁控制
- [ ] 评论不被编辑锁完全阻断
- [ ] AI 默认不能直接无限制写正式正文或关键状态
- [ ] 工单状态回写与文档内容回写有清晰边界

### 加分项

- [ ] 角色差异在前端已有明显表现
- [ ] 关键回写动作已有待确认机制
- [ ] 审计记录已开始贯穿关键动作

### 可后置项

- 按钮级超细权限
- 所有模块的完整 ACL 扩展

---

## 5.5 文档协作线验收清单

### 必须项

- [ ] 至少一类内容对象具备锁状态显示
- [ ] 至少一类内容对象可评论
- [ ] 至少一类内容对象可受控编辑
- [ ] 能区分只读、评论、编辑、解锁等协作状态
- [ ] AI 可作为建议者或草稿生成者介入

### 加分项

- [ ] 评论区已支持 @人 与状态管理
- [ ] 草稿 / 建议层已可视化
- [ ] 文档、工单、协作状态三者已有更强联动

### 可后置项

- 完整实时多人共编
- 高级版本分叉合并
- 更复杂的富文档编辑体验

---

## 5.6 移动端准备度验收清单

阶段一不要求移动端全量完成，但建议至少检查“是否已经准备好了”。

### 必须项

- [ ] 已明确移动端第一阶段定位为轻操作与轻查看入口
- [ ] 已明确移动端优先动作：出工 / 到场 / 开工 / 暂停 / 完成 / 异常上报
- [ ] 已明确这些动作最终回写到哪些对象
- [ ] 已明确移动端权限默认更收敛

### 加分项

- [ ] 已有“我的任务 / 我的工单”移动端页面草案
- [ ] 已有移动端动作对应事件清单
- [ ] 已考虑移动端审计记录

### 可后置项

- 深文档编辑
- AI 工作流配置
- 复杂总览深操作

## 6. 里程碑检查表

下面给出更适合阶段性会议使用的里程碑检查表。

## M1｜骨架成立检查表

- [ ] 六大模块定义没有被推翻
- [ ] 正式前端开始承接模块骨架
- [ ] 核心对象模型已统一
- [ ] 权限与回写规则已有主文档
- [ ] AI 主干、文档协作主干已统一口径

### M1 通过判断

如果团队已经不再用“静态原型 + 零散想法”讨论项目，而能用同一套模块、对象、主线语言沟通，则 M1 可通过。

---

## M2｜主链打通检查表

- [ ] BP问问可承接问题
- [ ] 至少一条复杂任务可进入执行层
- [ ] 至少一条任务可创建或关联工单
- [ ] 至少一条链路可进入文档对象协作
- [ ] 执行结果已不再只是“对话里说一嘴”

### M2 通过判断

如果系统已经至少有一条可从需求发起走到结果承接的真实链路，则 M2 可通过。

---

## M3｜规则成立检查表

- [ ] 文档锁成立
- [ ] 评论不受锁完全阻断
- [ ] AI 回写边界成立
- [ ] 工单状态回写与文档内容回写边界成立
- [ ] 关键动作有基础审计意识

### M3 通过判断

如果系统已具备基本可控性，不会因为协作和回写完全无边界而失控，则 M3 可通过。

---

## M4｜阶段收口检查表

- [ ] 六大模块主骨架成立
- [ ] 主链路可跑
- [ ] 对象可引用、可回写、可追踪
- [ ] 权限与协作有基础规则
- [ ] AI 执行可承接
- [ ] 移动端轻操作方向已明确
- [ ] 团队可进入第二阶段细化与扩展

### M4 通过判断

如果 BPAI 已从“概念和原型阶段”进入“系统主骨架已成立、可以扩展”的状态，则阶段一可视为完成。

## 7. 阶段一通过时，哪些现象应该已经出现

如果阶段一真正通过，通常会出现以下现象：

### 现象 1

团队在描述系统时，已经不再反复争论 BP问问、AI宿舍、工单、文档档案室到底各自是干什么的。

### 现象 2

至少有一条主链从用户提需求到结果承接已经变成真实系统行为，而不是纸面描述。

### 现象 3

权限和协作不再完全靠口头约定，而是已经有明确机制雏形。

### 现象 4

后续如果要扩子域、扩移动端、扩 AI 能力，不再需要推翻整个产品骨架。

---

## 8. 阶段一通过时，哪些东西仍然可以没完成

为了防止范围失控，这里明确列出“阶段一通过时允许还没完成的内容”。

可以后置的内容包括：

- 工程队所有子域的深页精修
- 所有页面的视觉终稿化
- 完整实时多人共编
- 高级工作流画布
- 深度多 Agent 协同
- 完整移动端产品体系
- 极细粒度权限系统
- 全量项目中心 / 财务中心 / 后台治理深模型

只要主骨架和主链成立，这些都可以进入下一阶段继续做。

## 9. 测试点

## 9.1 验收口径稳定性测试

测试点：

- 是否已经把“必须项 / 加分项 / 可后置项”区分开
- 是否能有效避免阶段一无限膨胀

## 9.2 里程碑可执行性测试

测试点：

- M1~M4 是否可用于真实项目检查会
- 团队成员是否可以据此快速判断当前卡在哪一段

## 9.3 跨角色适用性测试

测试点：

- 产品、前端、后端、AI 编排、权限治理是否都能读懂这份检查表
- 是否不是只站在单一研发角色视角编写
