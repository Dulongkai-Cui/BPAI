# 21｜后端服务边界与系统拓扑草案

## 本文目的

在现有 `Project_skeleton` 已经明确产品骨架、AI 主干、对象模型、权限规则、接口与事件草案、移动端轻操作方案的基础上，补充一份后端视角的系统拓扑与服务边界草案。

本文不进入具体部署 YAML、数据库表结构、消息中间件选型代码实现，而是站在系统设计层，明确：

- BPAI 后端整体应如何分层
- 不同能力应如何划分服务边界
- 哪些能力适合做同步 API
- 哪些能力适合走异步事件
- 哪些结果应先写入执行结果对象，再决定是否正式回写
- 核心存储组件需要承接哪些职责

目标是为后续后端架构、服务拆分、接口设计、AI 执行链路与数据基础设施设计提供稳定主线。

## 1. 为什么这一篇现在就要写

当前如果只从前端和产品角度推进，后续很容易在后端上出现两个问题：

### 问题 1：所有能力都被塞进一个大 API 后台

结果会导致：

- 工单、文档、AI 执行、权限、总览聚合全部混在一起
- 回写逻辑越来越难控
- 服务职责不清
- 系统扩展时耦合迅速上升

### 问题 2：AI 能力接入后没有稳定系统边界

结果会导致：

- 编排层和执行层混掉
- AI 结果到处直写正式对象
- 文档、工单、总览与 AI 执行的关系越来越难统一

因此，本篇的意义是：

在第一阶段就给后端一个“够稳、够清晰、可逐步实现”的系统拓扑草案。

---

## 2. 后端整体设计原则

### 原则 1：不推翻六大模块骨架

后端分层和服务边界，必须服务于：

- BP问问做调度
- AI宿舍做执行能力承载
- 工单承接状态
- 文档档案室承接内容协作
- 总览承接聚合观察

而不是反过来把前台产品结构打散。

### 原则 2：调度层、执行层、业务层要分开

尤其是 AI 接入后，这一点非常关键。

### 原则 3：对象写入要区分“执行结果层”和“正式对象层”

第一阶段必须避免 AI 与自动化流程大面积直接写正式对象。

### 原则 4：同步 API 用于确定性交互，异步事件用于传播状态变化

这会让后续系统更稳，也更适合移动端与 AI 编排加入。

---

## 3. 整体后端分层

当前建议把 BPAI 后端整体理解为以下六层。

## 3.1 Web 前端层

职责：

- 负责 PC 端与未来移动端界面
- 发起用户交互请求
- 展示对象状态、权限状态、执行状态与协作状态

这一层不承担复杂业务规则，而是通过 BFF / API 层拿到适合页面消费的数据。

## 3.2 BFF / API 层

职责：

- 承接前端请求
- 做前端友好的接口聚合
- 做鉴权入口与会话上下文承接
- 为不同端（PC / Mobile / 未来管理端）提供面向界面的 API 形态

说明：

BFF 不应成为“大业务黑洞”，它更像前端友好的组合层。

## 3.3 业务服务层

职责：

- 承接正式业务对象与业务规则
- 管理工单、文档协作、权限审计、总览聚合等主业务能力

这一层是系统的核心稳定层。

## 3.4 AI 编排层

职责：

- 承接 BP问问背后的问题分流、任务拆解与调用决策
- 决定走知识、工具、工作流还是 AI员工 / Open Claw
- 生成执行任务、执行上下文与回写建议

说明：

AI 编排层不是执行层，也不应直接承担所有底层业务对象写入。

## 3.5 执行层

职责：

- 真正调用工作流、工具链、AI员工 / Open Claw、OCR、分析器等能力
- 产出执行结果对象

说明：

执行层优先对“结果对象”负责，而不是直接对正式业务对象负责。

## 3.6 数据与知识层

职责：

- 承接结构化数据、文档、文件、缓存、向量知识、事件、任务状态等底层存储与检索能力

说明：

这一层是系统的数据基础设施，不直接暴露为业务概念，但对 AI 和业务服务都很关键。

---

## 4. 推荐系统拓扑总图（文字版）

当前建议将系统拓扑理解为：

前端（PC / Mobile）
→ BFF / API 层
→ 业务服务层
→ （按需调用）AI 编排层
→ 执行层
→ 数据与知识层

同时：

- 业务服务层之间可通过同步 API 或异步事件协作
- AI 编排层通常不直接面向最终前端页面，而通过 BFF / API 层和业务服务协同
- 执行层产出先进入执行结果对象，再按回写规则决定是否进入正式对象层

## 5. 服务边界建议

以下是当前第一阶段最值得明确的服务边界。

## 5.1 工单服务

### 职责

- 工单创建、查询、状态更新、指派、归档
- 异常工单承接
- 关联项目、团队、文档、执行结果

### 它不应承担的职责

- 文档正文协作规则
- AI 调度决策本身
- 总览聚合渲染逻辑

### 它的核心地位

工单服务是“状态主对象服务”。

---

## 5.2 文档协作服务

### 职责

- 文档 / 表格 / CAD / 合作空间对象管理
- 评论、建议、草稿管理
- 编辑锁、接力编辑、解锁规则
- 与工单、AI 执行结果的内容侧挂接

### 它不应承担的职责

- 工单状态机
- AI 调度分流
- 总览全局聚合

### 它的核心地位

文档协作服务是“内容主对象服务”。

---

## 5.3 AI 编排服务

### 职责

- 接收 BP问问侧的任务请求
- 做问题分类与任务拆解
- 选择：知识库 / 工具 / 工作流 / AI员工
- 生成执行计划或执行请求
- 收回执行结果并生成面向 BP问问的表达材料

### 它不应承担的职责

- 直接成为正式对象的大规模写入者
- 直接替代工单服务和文档协作服务的业务规则

### 它的核心地位

AI 编排服务是“调度中枢后端化”的核心承载。

---

## 5.4 工作流服务

### 职责

- 工作流定义、版本、运行、状态管理
- 标准化多步骤流程执行
- 输出执行结果对象

### 它不应承担的职责

- 直接解释给用户
- 直接替代 AI 编排服务做任务分流
- 直接替代业务服务做正式回写判断

### 它的核心地位

工作流服务是“标准流程执行引擎”。

---

## 5.5 权限 / 审计服务

### 职责

- 用户角色权限判断
- 模块访问控制
- 对象操作权限判断
- 回写权限判断
- 关键动作审计记录
- 解锁、管理员动作留痕

### 它不应承担的职责

- 业务对象本身的全部状态管理
- 页面级聚合接口渲染

### 它的核心地位

权限 / 审计服务是“系统可控性和可追溯性底座”。

---

## 5.6 总览聚合服务

### 职责

- 聚合工单、工程队、AI执行、异常、移动端轻动作等跨服务状态
- 形成总览所需指标、看板、摘要与风险聚合结果

### 它不应承担的职责

- 工单原始业务处理
- 文档协作原始逻辑
- AI 调度决策

### 它的核心地位

总览聚合服务是“观察层聚合引擎”，而不是原始业务处理中心。

---

## 6. 核心存储建议

当前建议从系统设计层至少明确以下五类存储能力。

## 6.1 关系库

适合承接：

- 用户
- 角色
- 工单
- 评论元数据
- 编辑锁状态
- 工作流元数据
- AI 执行任务元数据
- 审计记录索引

说明：

关系库是第一阶段正式业务对象的主存储底座。

## 6.2 对象存储

适合承接：

- 文档文件
- 表格文件
- CAD 文件
- 附件
- 草稿文件
- 执行产物文件（如报告、导出结果）

说明：

对象存储应与文档协作服务、执行层产物承接密切配合。

## 6.3 缓存

适合承接：

- 热门对象查询缓存
- 会话态临时数据
- 锁状态热点读取
- 总览聚合结果短期缓存
- 移动端高频轻状态读取

说明：

缓存不应成为正式真相来源，但可显著提升实时体验。

## 6.4 向量库

适合承接：

- 规范知识
- 档案内容向量化索引
- 文档检索增强
- BP问问检索增强上下文

说明：

向量库是 AI 主干中知识层的重要补充，但不是正式业务状态存储。

## 6.5 事件队列

适合承接：

- 工单状态变化事件
- 编辑锁变化事件
- AI 执行状态事件
- 移动端轻动作事件
- 总览聚合更新触发

说明：

事件队列非常适合第一阶段的“异步传播变化”需求。

## 7. 同步 / 异步调用关系

这是本篇最关键的一部分之一。

## 7.1 哪些走同步 API

同步 API 更适合：

### 1）用户立即需要结果的动作

例如：

- 登录鉴权
- 查看工单详情
- 查询文档详情
- 获取锁状态
- 创建评论
- 创建工单
- 手机端点击出工并立即看到结果

### 2）需要明确成功/失败反馈的动作

例如：

- 获取编辑锁
- 释放编辑锁
- 更新工单状态
- 申请正式回写

### 当前建议

前端 → BFF / API → 业务服务 的主交互，优先走同步 API。

---

## 7.2 哪些走异步事件

异步事件更适合：

### 1）状态变化传播

例如：

- 工单状态已更新
- AI 执行已完成
- 编辑锁已释放
- 移动端已完成开工打卡

### 2）聚合更新

例如：

- 总览重新聚合
- AI 宿舍状态刷新
- 异常看板更新

### 3）不要求用户当前页面阻塞等待的动作

例如：

- 审计记录写入
- 通知其他模块刷新状态
- 统计更新

---

## 8. 哪些结果先写执行结果对象，哪些再正式回写

这部分必须和 [15_权限矩阵与回写规则](./15_权限矩阵与回写规则.md) 保持一致。

## 8.1 先写执行结果对象的场景

建议以下结果优先先写“执行结果对象”：

- AI 分析报告
- 风险识别结果
- OCR 识别结果
- 表格补齐建议
- 文档草稿生成结果
- 清单生成结果
- 多步骤工作流运行产出

原因：

- 便于审计
- 便于回看
- 便于确认
- 便于后续决定挂工单还是挂文档

## 8.2 再正式回写的场景

在以下条件满足后，再考虑正式回写：

- 权限允许
- 对象状态允许
- 锁状态允许
- 人工确认或规则确认已完成

适合正式回写到：

- 工单状态字段
- 文档正式正文
- 表格正式字段
- 合作空间正式状态

## 8.3 当前不建议直接正式回写的场景

第一阶段不建议让以下场景默认一步到位：

- AI 直接覆盖正式文档正文
- 工作流直接修改关键审批状态
- 执行层无确认地直接修改关键金额、数量、送审状态等字段

## 9. 推荐的典型调用链路（后端视角）

## 9.1 BP问问发起复杂任务

推荐链路：

前端 BP问问
→ BFF / API
→ AI 编排服务
→ 工作流服务 / AI 执行层
→ 生成执行结果对象
→ 事件通知
→ 工单服务 / 文档协作服务按规则承接
→ BFF / API 汇总结果
→ 前端 BP问问展示

## 9.2 文档编辑锁协作

推荐链路：

前端文档页
→ BFF / API
→ 文档协作服务
→ 权限 / 审计服务判断
→ 获取锁成功 / 失败
→ 返回结果
→ 事件通知其他协作者锁状态变化

## 9.3 移动端出工动作

推荐链路：

移动端前端
→ BFF / API
→ 工单服务 / 工程状态更新逻辑
→ 权限校验
→ 状态更新成功
→ 事件通知总览聚合 / 审计写入 / 相关页面刷新

## 10. 第一阶段技术上建议怎么落

## 10.1 先做“少而清晰”的服务，不先做“多而碎”的服务

第一阶段更推荐：

- 工单服务
- 文档协作服务
- AI 编排服务
- 工作流服务
- 权限 / 审计服务
- 总览聚合服务

先把这些主服务边界立住。

## 10.2 BFF 要做组合，不要做业务黑洞

BFF 的职责应是：

- 面向端聚合
- 屏蔽后端细节
- 帮前端形成好消费的数据形态

而不是把真正业务规则写到 BFF 里。

## 10.3 业务服务和 AI 编排服务要刻意分开

这是后续系统是否稳定的关键。

### 原因

如果 AI 编排逻辑和业务服务揉在一起，后续会很难控制：

- 权限
- 审计
- 结果确认
- 执行回溯

## 10.4 事件先从关键状态变化开始，不必一开始做全量事件化

第一阶段建议优先事件化：

- 工单状态变化
- 编辑锁变化
- AI 执行状态变化
- 移动端轻动作状态变化

这已经足够支撑大多数跨模块同步需求。

## 11. 测试点

## 11.1 分层清晰度测试

测试点：

- 是否明确区分了 BFF / API 层、业务服务层、AI 编排层、执行层、数据与知识层
- 是否没有把 AI 编排和业务服务混为一层

## 11.2 服务边界稳定性测试

测试点：

- 工单、文档协作、AI 编排、工作流、权限审计、总览聚合是否具备清晰服务边界
- 是否没有出现一个服务什么都管的倾向

## 11.3 调用关系合理性测试

测试点：

- 同步 API 是否主要承接立即反馈型动作
- 异步事件是否主要承接状态传播与聚合更新
- 执行结果是否优先经过执行结果对象而不是大面积直写正式对象

## 11.4 研发可落地性测试

测试点：

- 是否能够支持下一步后端服务拆分讨论
- 是否能够支撑接口清单、事件清单、对象存储与知识层设计继续展开

---

## 12. 验收标准

满足以下条件，可视为本篇成立：

1. 明确了 BPAI 后端整体分层结构
2. 明确了工单服务、文档协作服务、AI 编排服务、工作流服务、权限/审计服务、总览聚合服务的边界
3. 明确了关系库、对象存储、缓存、向量库、事件队列的基础职责
4. 明确了哪些动作适合走同步 API，哪些状态变化适合走异步事件
5. 明确了执行结果对象与正式回写对象之间的关系
