# AI宿舍页面结构草图（文字版）

## 1. 设计目标

AI宿舍这一阶段不应该一上来做成完整 AI 员工平台，而应该先成为：

> **BP问问后面的最小执行后场。**

因此页面结构必须围绕两件事展开：

1. **谁来干活**
   - 龙虾 / 执行单元 / 承接者
2. **怎么干活**
   - Skill / Workflow / 任务流程

同时，还要有一个中间层：

3. **接住 BP问问派发任务**
   - execution task 收件箱

---

## 2. 推荐一级导航

建议 AI宿舍第一版收敛为下面这套一级导航：

- 工作流工坊
- Skill 仓库
- AI员工

并把：
- 任务收件箱
- 执行记录
- 配置 / 协议
- 资源 / 算力 / 账单

降为二级页面、详情页或设置位，而不是一级核心入口。

---

## 3. 页面结构草图

### 3.1 `/ai-dorm`｜AI宿舍首页 / 总入口

#### 作用
给用户一个总控视角，快速看到：
- AI宿舍当前整体状态
- 最近从 BP问问流进来的任务
- 当前哪些执行单元最活跃

#### 页面内容

##### 顶部摘要卡片
- 待承接任务数
- 执行中任务数
- 已完成任务数
- 失败任务数
- 需要人工确认任务数

##### 中部左侧：最近任务
展示最近的 execution task：
- goal
- primaryIntent
- targetDomain
- executionMode
- 当前状态
- executorKind
- createdAt

##### 中部右侧：执行单元概览
展示不同龙虾 / 执行单元：
- 名称
- 状态
- 最近任务数
- 当前负责领域

##### 底部：运行说明
说明当前版本定位：
- BP问问已经负责入口与调度
- AI宿舍当前是最小执行后场
- Longxia / tools / workflow 还在逐步接入

---

### 3.2 `/ai-dorm/workflows`｜工作流工坊

#### 作用
承接“怎么把多个能力串起来干活”。

#### 产品感觉
工作流工坊未来应更接近 Coze 风格：
- 节点可以在一张画布上自由拖动
- Skill、AI员工、条件判断、输入输出都可以成为节点
- 支持调试、运行、版本管理

#### 页面内容
- 工作流列表
- 画布入口
- 最近运行情况
- 步骤数
- 是否启用
- dry run / test run 预留

#### 第一版边界
第一版可以先做列表与静态步骤说明，不要求立刻实现完整拖拽画布。

---

### 3.3 `/ai-dorm/skills`｜Skill 仓库

#### 作用
承接“单点能力”的资产管理。

#### 页面内容
- 上传现成 skill
- 按模板创建 skill
- 通过 BP问问对话生成 skill 草案
- Skill 列表
- Skill 输入 / 输出 / 适用场景
- 测试运行入口

#### BP问问小窗口
Skill 仓库里可以有一个小型 BP问问窗口，用于：
- 根据自然语言需求生成 skill 草案
- 帮用户选择模板
- 辅助补全输入输出 schema

注意：这属于 Skill 仓库能力，不是把 BP问问变成 Skill 仓库本体。

---

### 3.4 `/ai-dorm/agents`｜AI员工

#### 作用
展示“谁来干活”。

#### 页面内容

##### 列表卡片
每个 AI员工 / 小龙虾展示：
- 名称
- 负责领域
- 当前状态
- 简要描述
- 最近任务数
- 是否启用
- owner / 维护人

##### 执行单元详情页
可进一步预留：
```text
/ai-dorm/agents/[agentId]
```

详情页可以包含：
- 职责边界
- 可承接任务类型
- 可调用哪些 skills
- 最近执行记录
- 输入输出协议说明
- 配置编辑入口

#### 权限口径
像 Dulongkai Cui 这样的系统级角色，应能查看并编辑系统内所有小龙虾配置。

---

### 3.5 `/ai-dorm/tasks`｜任务收件箱（二级/承接页）

#### 作用
这是 AI宿舍最重要的页面。
它是 BP问问把任务正式“派给后场”的承接面板。

#### 页面内容

##### 任务列表
每条任务至少展示：
- taskId
- goal
- primaryIntent
- targetDomain
- executionMode
- executorKind
- status
- requiresWrite
- requiresConfirmation
- createdAt

##### 筛选区
支持按这些筛选：
- status
- executorKind
- targetDomain
- executionMode
- 是否需要人工确认

##### 任务详情抽屉 / 详情页
点开某个任务后展示：
- targetRefs
- constraints
- metadata
- summaryText
- responseText
- structuredPayload
- 如果当前只有模拟执行，明确标注“模拟执行结果”

#### 第一版数据来源
优先直接读取现有：
- `execution_tasks`
- `execution_results`

不要重新发明新的任务数据模型。

---

### 3.3 `/ai-dorm/agents`｜龙虾 / 执行单元页

#### 作用
展示“谁来干活”。

#### 页面内容

##### 列表卡片
每个执行单元展示：
- 名称
- 负责领域
- 当前状态
- 简要描述
- 最近任务数
- 是否启用

##### 执行单元详情页
可进一步预留：
```text
/ai-dorm/agents/[agentId]
```

详情页可以包含：
- 职责边界
- 可承接任务类型
- 可调用哪些 skills
- 最近执行记录
- owner / 维护人
- 输入输出协议说明

#### 第一版建议的静态执行单元
- 工单龙虾
- 文档龙虾
- 图纸龙虾
- 预警龙虾
- 报表龙虾
- 表单龙虾

第一版可以先用静态 mock 数据，不要求真实 LongxiaAdapter 接入。

---

### 3.4 `/ai-dorm/skills`｜Skills 列表页

#### 作用
展示“单点能力”。

#### Skill 的定位
Skill 是原子能力，不是完整流程。

例如：
- 读取工单详情
- 查询合作空间状态
- 列出待确认意见
- 生成周报草稿
- 定位最新上传文档
- 解析 CAD 文件元信息

#### 页面内容
- 名称
- 描述
- 所属领域
- 输入
- 输出
- 是否可测试
- 最近更新时间

#### 详情页可预留
```text
/ai-dorm/skills/[skillId]
```

第一版不强求真的做编辑器，可以先做只读定义页。

---

### 3.5 `/ai-dorm/workflows`｜Workflow 列表页

#### 作用
展示“怎么把多个能力串起来干活”。

#### Workflow 的定位
Workflow 是多步流程，不是单点 skill。

例如：
- 工单受理流程
- 文档归档流程
- 风险汇总流程
- CAD 资料归档流程

#### 页面内容
- 名称
- 目标
- 步骤数
- 说明
- 是否启用
- 最近执行情况

#### 详情页可预留
```text
/ai-dorm/workflows/[workflowId]
```

详情页可展示：
- 步骤列表
- 输入输出
- 条件分支
- 涉及哪些 skills / agents
- 是否需要人工确认
- dry run / test run 预留区

第一版不建议直接做复杂拖拽编辑器。

---

### 3.6 `/ai-dorm/runs`｜执行记录页

#### 作用
展示历史执行痕迹。

#### 页面内容
- 最近 execution_results
- 对应 taskId
- 成功/失败
- summaryText
- structuredPayload 摘要
- 执行器类型

这页可以帮助快速排查：
- 哪类任务经常失败
- 哪些结果现在还只是模拟执行

---

### 3.7 `/ai-dorm/settings`｜配置 / 协议页

#### 作用
让 AI宿舍的系统边界更清晰。

#### 页面内容
- BP问问 -> AI宿舍 调度协议说明
- executorKind 说明
- executionMode 说明
- LongxiaAdapter 预留位
- 模型配置说明
- 风险动作确认规则

---

## 4. 第一版最小落地建议

### 推荐第一批先做 4 个页面
1. `/ai-dorm`
2. `/ai-dorm/tasks`
3. `/ai-dorm/agents`
4. `/ai-dorm/workflows`

其中优先级最高的是：

### 第一优先
`/ai-dorm/tasks`

因为这是当前 BP问问和 AI宿舍之间真正已经有数据桥梁的地方。

### 第二优先
`/ai-dorm`

因为要让整体结构先立起来。

### 第三优先
`/ai-dorm/agents`

因为你明确希望有“不同人的龙虾 / 不同执行单元”。

### 第四优先
`/ai-dorm/workflows`

因为你明确希望有一块能编辑 Skill / Workflow。

---

## 5. 与当前已完成成果的衔接

当前 BP问问已经具备：
- execution_tasks
- execution_results
- Kimi 普通聊天
- 任务筛网
- 模拟执行预案
- 多轮线程与记忆

因此 AI宿舍第一版不是从 0 开始，而是：

> **把 BP问问已经产出的 execution_tasks 正式接住。**

这也是为什么 AI宿舍第一版最合理的切入页是：

```text
/ai-dorm/tasks
```

---

## 6. 一句话总结

AI宿舍第一版最合理的页面结构是：

> **一边管理“谁来干活”（龙虾 / 执行单元），一边管理“怎么干活”（Skills / Workflows），中间用任务收件箱接住 BP问问派来的 execution task。**
