# Longxia 与工具链接入边界草案

## 1. 为什么要先定义边界

当前 BP问问已经有：

- 对话入口
- 调度判断
- execution task/result
- 模拟执行预案

所以现在最容易犯的错误是：

> 看到它已经会判断，就开始把 Longxia、工具链、工作流全都直接往 BP问问里堆。

这会破坏系统边界。

---

## 2. 基本边界

### BP问问不是 Longxia

BP问问负责：
- 理解用户输入
- 判断该走哪条路
- 解释当前在发生什么
- 向用户确认风险动作
- 收回执行结果再表达给用户

Longxia 负责：
- 真正跑步骤
- 浏览器/工具型执行
- 需要多步自动化的动作

### 工具链也不应该直接堆在 BP问问前台

像这些能力：
- 读取合作空间对象
- 读取工单详情
- 操作系统表单
- 文档挂接
- CAD 资源处理

都更适合通过：

> AI宿舍承接层 / system tool / workflow runner

接入，而不是直接让 BP问问前台承担。

---

## 3. 阶段五建议的层次关系

```text
用户
-> BP问问（入口、理解、调度、解释）
-> execution_tasks
-> AI宿舍（承接层）
   -> system tools
   -> workflow runner
   -> LongxiaAdapter
-> execution_results
-> BP问问（结果表达）
```

---

## 4. LongxiaAdapter 在哪里最合理

Longxia 不应直接作为 BP问问页面内部行为。

更合理位置是：

- 作为 AI宿舍中的一种执行器
- 接 execution task
- 输出 execution result

也就是说，LongxiaAdapter 最合理的归属是：

> **AI宿舍执行后场的一部分**

而不是 BP问问本体。

---

## 5. 工具链接入顺序建议

阶段五建议按轻重排序：

### 第一批
- 只读读取类工具
  - 读合作空间
  - 读工单
  - 读表单
  - 读文档元数据

### 第二批
- 受控写入类工具
  - 创建对象
  - 更新对象
  - 分配对象
  - 权限变更

### 第三批
- Longxia / 浏览器执行器 / 多步骤 workflow

这样做的好处是：
- 先把 AI宿舍最小承接层跑起来
- 再逐步接复杂执行器

---

## 6. BP问问与 Longxia 的前台关系

用户前台看到的永远应该是：

- BP问问在解释当前任务
- BP问问在说明下一步
- BP问问在请求确认
- BP问问在汇总结果

而不是：
- 直接暴露 Longxia 内部执行人格
- 让 Longxia 成为新的前台入口

---

## 7. 一句话总结

Longxia 与工具链不是要直接塞进 BP问问，而是应该：

> **统一收编到 AI宿舍承接层，再由 BP问问负责调度与表达。**
