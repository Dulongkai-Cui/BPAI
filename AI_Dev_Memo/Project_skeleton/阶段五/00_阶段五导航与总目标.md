# 阶段五｜导航与总目标

## 1. 阶段五要解决什么

阶段一到阶段四，BPAI 已经把前端承接层、工单与文档/合作空间基础链路，以及 BP问问的对话与调度骨架逐步搭起来了。

到当前节点，BP问问已经具备：

- `/bp-ask` 页面入口
- 多轮线程与历史对话
- 滚动摘要（rolling summary）
- 记忆事实（memory_facts）
- execution task / execution result
- 任务筛网
- Kimi 普通聊天生成
- Kimi 结构化分类增强
- 模拟执行预案
- 历史线程删除
- 即时发送与 assistant 加载动画

因此阶段五不再是“继续把 BP问问做成更像聊天框”，而是：

> **正式开始为 BP问问补后场承接层，让 AI宿舍成为 execution task 的真实去处。**

---

## 2. 阶段五的主题

阶段五的主题是：

- 把 BP问问前台与调度层沉淀为稳定入口
- 为 AI宿舍建立最小承接层
- 明确 BP问问 -> execution_tasks -> AI宿舍 -> execution_results 的链路
- 为后续 Longxia / 工具链 / workflow runner 接入提前定义边界

阶段五强调的是：

- 不是继续做更复杂的前台话术
- 不是马上做完整自治智能体平台
- 而是先把“执行后场”搭起来

---

## 3. 当前基线（进入阶段五前已完成）

### 3.1 BP问问前台

当前 BP问问前台已经具备：

- 普通聊天与任务型请求共存
- 任务筛网：无明确任务信号先按聊天，明确任务才进调度
- 渐进式任务呈现：普通聊天默认不显示调度细节，任务细节默认折叠
- 历史线程删除
- 用户消息即时上屏
- assistant 独立加载动画

### 3.2 BP问问后端调度层

当前已经具备：

- `primaryIntent`
- `targetDomain`
- `executionMode`
- `targetRefs`
- `constraints`
- `toolHints`
- `memoryScopes`
- `requiresWrite`
- `requiresConfirmation`

### 3.3 数据层

当前已具备：

- `conversation_threads`
- `conversation_messages`
- `conversation_summaries`
- `memory_facts`
- `execution_tasks`
- `execution_results`

这些对象意味着阶段五已经有天然桥梁，不需要从 0 设计“AI 如何接任务”。

---

## 4. 阶段五的总目标

### 目标 1：让 AI宿舍成为 execution task 的承接层

BP问问不再只是：
- 理解
- 调度
- 模拟执行

而是开始把一部分任务真正交给 AI宿舍承接。

### 目标 2：定义执行器类型和状态流转

至少明确：
- BP问问自己处理
- Kimi 辅助
- system tool
- workflow runner
- Longxia（未来）
- dorm agent（未来）

### 目标 3：为复合任务做准备

当前像：

> “去看看文档空间里最新上传的雨花区 CAD，再把它安排到合作空间里去”

这种复合任务已经暴露出问题：
- 需要先解析对象
- 再拆步骤
- 再交给执行后场

阶段五要开始给这类能力找落点，而不是让 BP问问前台越来越会“理解但做不了”。

---

## 5. 阶段五不做什么

为了避免失控，阶段五暂不追求：

- 完整自治 AI员工网络
- 全量 Longxia 浏览器执行闭环
- 全量 RAG / 搜索 / 检索系统
- 所有 executionMode 的真实落地
- 多模型编排平台的一次性完成

阶段五先做：

> **最小执行后场。**
