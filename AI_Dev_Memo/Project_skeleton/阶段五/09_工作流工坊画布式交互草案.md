# 工作流工坊画布式交互草案

## 1. 为什么要单独写这一篇

用户已经明确表达：

> Workflow 不想只是列表页，而希望像 Coze 那样，节点可以在一张画布上自由拖动组装。

这意味着工作流工坊不只是“流程列表管理页”，而是 AI宿舍中的核心编排板块。

---

## 2. 工作流工坊的定位

工作流工坊负责：

- 让用户定义“怎么干活”
- 把 Skill、AI员工、条件分支、输入输出串成一个执行流程
- 对流程做调试、运行、版本管理

一句话理解：

> 工作流工坊负责“把能力连成工序”。

---

## 3. 推荐的页面形态

### 3.1 左侧：节点仓库

节点仓库可分组展示：

- Skill 节点
- AI员工节点
- 条件节点
- 输入节点
- 输出节点
- 人工确认节点
- 未来工具节点

### 3.2 中间：流程画布

中间是一张画布，支持：
- 拖入节点
- 连接节点
- 调整顺序
- 观察流程主链
- 未来支持分支与并行

### 3.3 右侧：节点配置区

点击某个节点后显示：
- 名称
- 输入
- 输出
- 参数
- 说明
- 失败处理策略
- 是否需要人工确认

---

## 4. 第一版不必做什么

为了防止范围爆炸，阶段五第一版不建议直接做：

- 完整无限自由拖拽
- 复杂多分支编排引擎
- 真正运行时调度器
- 图形化复杂版本 diff

第一版只需明确：

> **工作流最终目标是画布式，但可以先从“画布感列表 + 节点说明 + dry-run”开始。**

---

## 5. 第一版建议最小交互

### 5.1 流程列表页
- 流程名
- 说明
- 步骤数
- 是否启用
- 最近运行结果

### 5.2 流程详情页
- 左边节点列表
- 中间流程骨架图 / 简化画布
- 右侧节点配置说明

### 5.3 dry-run 区
允许用户模拟：
- 这条 workflow 接到某类 execution task 时会如何走
- 哪些节点会触发
- 哪些节点需要确认

---

## 6. 与 Skill 仓库和 AI员工的关系

工作流工坊不是孤立存在的。

它应能：
- 调用 Skill 仓库中的 skill
- 调用 AI员工中的执行单元
- 在必要时插入人工确认节点

所以：

- Skill 负责“能力资产”
- AI员工负责“执行主体”
- Workflow 负责“能力编排”

---

## 7. 与 BP问问的关系

BP问问当前已经可以判断：
- executionMode
- targetDomain
- targetRefs
- constraints

因此未来合理链路是：

```text
用户说任务
-> BP问问判断这是工作流型任务
-> 交给工作流工坊对应流程
-> 落 execution_tasks
-> 返回 execution_results
-> BP问问解释给用户
```

也就是说：

BP问问不直接承担画布式编排本身，
它负责决定“该不该进工作流工坊”。

---

## 8. 一句话总结

工作流工坊的最终形态应该是：

> **一个能像 Coze 一样用画布串节点的流程编排台。**

但阶段五第一版只需先把：

- 页面结构
- 节点分组
- 简化画布
- dry-run 心智模型

建立起来。
