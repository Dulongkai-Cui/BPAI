# 从当前本地 JSON 后端迁移到 PostgreSQL 的分阶段方案

## 1. 这份文档的定位

这份文档不是数据库建表说明，也不是运维部署文档，而是阶段二的迁移路线图。

它要回答的是：

- 当前这套本地 JSON 后端到底哪些值得保留
- 哪些结构应该尽快迁到 PostgreSQL
- 哪些内容不该直接塞进 PostgreSQL
- 文档档案室如何继续独立存在
- 工单模块如何直接建立在 PostgreSQL + PostGIS 之上
- AI 自动化后面应该怎样顺着这套底座接入

---

## 2. 当前后端到底是什么状态

现在的账号后端和文档档案室后端，本质上是：

- `app-store.json` 作为本地结构化数据存储
- `.bpai/storage` 作为本地文件本体存储
- Next 服务端代码直接读写这些本地文件

它不是纯前端 mock，因为：

- 用户、工作区、session 都是真持久化
- 文档元数据和回收站状态都是真持久化
- 文件本体也是真落盘

但它也不是正式数据库后端，因为：

- 所有结构化真源仍然压在单个本地 JSON 文件里
- 并发能力、可扩展性、查询能力、审计能力都有限
- 后续 AI 自动化如果直接建立在这套本地 JSON 之上，会越来越难管

所以迁移到 PostgreSQL 的意义，不是“技术升级好看”，而是要给工单模块和后续 AI 自动化建立稳定底座。

---

## 3. 迁移总原则

### 3.1 迁“结构化真源”，不迁“所有二进制文件”

最重要的原则是：

- 结构化对象进 PostgreSQL
- 文件本体继续放文件存储或对象存储

也就是说：

- 工单、账号、工作区、文件元数据、文件夹关系、缺失项、角色工作台依赖数据，应迁到 PostgreSQL
- PDF、DOCX、XLSX、PPTX、图片、图纸包、资源包这类文件本体，不建议直接塞进 PostgreSQL

### 3.2 先迁真源，再迁投影

先迁正式真源对象，再处理各类底表、工作台、导出表、视图。

不要先迁“合作空间里的系统表单底表”，而应该先迁：

- 工单主对象
- 附表
- 缺失项
- 文档挂接关系

然后再从这些真源里投影出角色工作台。

### 3.3 先允许并存，再逐步切换

文档档案室已经跑通，不建议为了迁 PostgreSQL 一把推翻。

更合理的迁移方式是：

- 先让新后端和旧本地 JSON 后端并存
- 先迁账号和元数据
- 先让新工单模块直接建在 PostgreSQL 上
- 再逐步把文档元数据和合作空间元数据迁过去

### 3.4 给 AI 预留“服务层入口”，不要让 AI 直接裸写数据库

PostgreSQL 是真源底座，但 AI 后续不应该默认直接通过 SQL 或 CLI 裸写业务数据。

更合理的方式是：

- PostgreSQL 作为真源
- 服务层负责业务校验、权限、审计、状态机
- AI 通过服务层读写，而不是绕过规则直接改库

---

## 4. 哪些内容建议迁到 PostgreSQL

建议分三批迁。

### 4.1 第一批：底座真源

这一批建议最先迁，因为后续工单、合作空间、权限和 AI 都会压在上面。

建议迁入 PostgreSQL 的对象包括：

- 用户
- 工作区
- Session
- 文档 / 表格 / 演示稿的元数据
- 文件与用户、工作区、文件夹的归属关系
- 回收站状态
- 个人文件夹结构
- 子文件夹结构
- 文件在文件夹中的位置关系
- 共享工作区中的文件布局状态
- 合作空间
- 合作空间成员

这一批的重点是：

- 把 `app-store.json` 中最核心的结构化对象先拆出来
- 让文档档案室和账号系统先有正式数据库底座

### 4.2 第二批：工单业务真源

这一批建议不要再做 JSON 过渡版，而是直接建立在 PostgreSQL 上。

建议迁入 PostgreSQL 的对象包括：

- 工单主表
- 来源与需求附表
- 派单与执行附表
- 交付与资源附表
- 缺失项与补录表
- 状态流转记录
- 预警记录
- 工单与文档挂接关系
- 合作空间角色工作台依赖的数据

这批对象会成为阶段二真正的核心真源。

### 4.3 第三批：AI 自动化相关真源

这一批不一定要第一天就上，但越早留位越好。

建议迁入 PostgreSQL 的对象包括：

- AI 任务记录
- AI 建议记录
- AI 补录草稿
- AI 回写审计日志
- 人工确认 / 驳回记录
- AI 操作的目标对象关系

这批对象存在的意义是：

- 让 AI 的行为可追踪
- 让 AI 的建议和正式回写分开
- 让后续自动化不再依赖临时脚本和散落文件

---

## 5. 哪些内容不建议直接迁到 PostgreSQL

下面这些内容不建议直接作为 PostgreSQL 主体数据：

- PDF 文件本体
- DOCX 文件本体
- XLSX 文件本体
- PPTX 文件本体
- 图片、照片、现场截图
- 图纸包
- 资源包
- 邮件附件原文
- OnlyOffice 实际编辑文件

更合理的方式是：

- PostgreSQL 存元数据、挂接关系、权限关系、版本关系
- 文件本体继续放文件系统
- 后续如有需要，再升级成 MinIO / S3 这类对象存储

也就是说：

文件系统或对象存储负责“存内容”，PostgreSQL 负责“存结构和关系”。

---

## 6. 迁移后的目标形态

迁移完成后的理想形态建议是：

- PostgreSQL：账号、工作区、工单、合作空间、文件元数据、缺失项、AI 审计
- PostGIS：站点位置、施工位置、工程队位置、区域围栏
- 文件存储：文档、表格、演示稿、图片、图纸、资源包
- 服务层：权限、校验、状态流转、审计、AI 回写控制
- 前端：工单页、合作空间系统表单区、工程队底表、文档档案室

这里最关键的判断是：

- 文档档案室继续作为内容协作层独立存在
- 工单模块以后端真源为中心
- 两者通过文档挂接关系联动

---

## 7. 建议的分阶段迁移顺序

### 阶段 M0：先做对象映射，不急着切流量

先完成三件事：

- 把当前 `app-store.json` 里的结构拆成正式对象清单
- 明确哪些对象进 PostgreSQL
- 明确哪些对象继续留在文件系统

这个阶段先不要急着重写所有业务页。

### 阶段 M1：先迁账号与工作区底座

建议优先迁：

- 用户
- 工作区
- Session

因为这是所有业务模块的共同底座，而且迁完后收益立刻很明显。

### 阶段 M2：再迁文档档案室元数据

建议迁：

- 文件元数据
- 文件夹结构
- 文件布局状态
- 回收站状态
- 合作空间元数据
- 成员关系

这个阶段迁的是“文档档案室的结构”，不是“所有文档本体”。

### 阶段 M3：工单模块直接在 PostgreSQL 上起

不要先做 JSON 版工单再迁一次。

建议直接建立：

- 工单主表
- 附表
- 缺失项
- 工单与文档挂接关系
- 合作空间中的系统表单工作台投影逻辑

### 阶段 M4：接入 PostGIS 的位置能力

建议在工单与工程队模块开始联动时就接入：

- 站点位置
- 施工位置
- 工程队位置
- 服务区域 / 围栏

这样后面再做地图、附近工程队、片区归属时不会返工。

### 阶段 M5：再接 AI 自动化层

当 PostgreSQL 真源稳定后，再把 AI 自动化接进来：

- AI 查询工单
- AI 识别缺失项
- AI 生成摘要
- AI 回写建议草稿
- AI 操作审计落库

这样 AI 的动作就有了稳定、可审计、可回滚的落点。

---

## 8. 文档档案室在迁移中的位置

文档档案室不需要因为工单模块而推倒重来。

它在迁移中的正确位置是：

- 继续保留内容协作层身份
- 逐步把结构化元数据迁进 PostgreSQL
- 文件本体先继续保留现有方式
- 通过稳定文档 ID 与工单真源建立挂接关系

所以它不是被替代，而是被“接上正式底座”。

---

## 9. 这条路为什么更适合未来 AI 自动化

因为 AI 真正需要的不是“去扫一个大 JSON 文件或目录”，而是：

- 查谁是当前责任人
- 查工单现在在哪个阶段
- 查缺失项还有哪些
- 查某站点关联了哪些工单
- 查某合作空间里有哪些待处理系统表单
- 查某文件挂在哪个工单上

这些都天然适合 PostgreSQL。

而且一旦进入 PostgreSQL 后，后面 AI 自动化的路径会更清楚：

1. 先查结构化真源
2. 再按权限拿文件引用
3. 产出建议或草稿
4. 通过服务层回写
5. 自动留下审计记录

这比让 AI 直接在本地 JSON 和文件夹里乱翻，稳定得多。

---

## 10. 阶段二最实际的建议

如果现在就准备开工，我建议不要一上来同时做太多。

最实际的第一步是：

1. 先确定 PostgreSQL 下的账号、工作区、文档元数据、合作空间元数据模型
2. 直接在 PostgreSQL 上起工单主对象和附表
3. 保持文档文件本体继续走现有文件存储
4. 再做合作空间中的系统表单工作台

这样做的好处是：

- 风险可控
- 路径清楚
- 文档档案室不用重来
- 工单模块从一开始就站在正确底座上
- 后续 AI 自动化有稳定真源可接

---

## 11. 一句话版本

这次迁移的正确方向不是“把所有东西都塞进 PostgreSQL”，而是：

把账号、工作区、文档元数据、合作空间元数据、工单真源和 AI 审计迁进 PostgreSQL，把文件本体继续留在存储层，再通过服务层把这套底座提供给前端和未来 AI 自动化使用。
