# 24｜BP问问与龙虾通信架构草案

## 1. 文档定位

这份文档用于定义 BPAI 在阶段四的 AI 调度主链。

这里要解决的不是“再接一个聊天框”，而是把：

- `BP问问`
- `龙虾 / Open Claw`
- `AI宿舍`
- `文档空间 / 合作空间 / 系统表单 / 工单`

接成一套可持续扩展的 Harnessing AI 架构。

当前结论是：

> `BP问问` 负责调度与解释，`龙虾 / Open Claw` 负责执行，`AI宿舍` 负责执行资源与状态承接。

---

## 2. 当前阶段判断

到当前为止，BPAI 已经完成了阶段一的大量承接层工作：

- 登录、会话与本地 BFF
- 我的文档空间
- 合作空间
- 回收站
- 系统表单入口
- OnlyOffice 编辑链
- 总览地图占位与点位承接入口

因此下一步不应继续把 AI 做成“单次问答气泡”，而应转向：

> 长对话、可记忆、可检索、可调度、可执行、可回写的统一 AI 中枢。

这也是 BPAI 从“阶段一承接层”向“阶段四 AI 编排层”过渡的核心动作。

---

## 3. 角色定义

### 3.1 BP问问

BP问问不是龙虾本体，也不是纯聊天壳。

BP问问应被定义为：

- 用户入口
- 任务识别器
- 执行路由器
- 结果整合器
- 最终表达层

BP问问负责：

- 识别用户真实意图
- 判断需要调用哪类工具或执行器
- 维护长对话上下文
- 调用记忆与搜索
- 把执行结果翻译成用户能直接理解的输出

### 3.2 龙虾 / Open Claw

龙虾应被定义为：

- 浏览器型执行器
- 页面操作执行器
- 多步骤任务处理器

它适合承接：

- 复杂网页流程
- 多步骤表单填写
- 页面读取与交互
- 条件判断后的连续动作

它不应直接承担：

- 用户对话总入口
- 全局记忆控制
- 权限最终裁决
- 系统主输出口径

### 3.3 AI宿舍

AI宿舍应被定义为：

- 执行资源池
- AI员工目录
- 工作流与任务状态区
- 结果回收区

BP问问调度任务，AI宿舍承接执行资源与状态展示。

---

## 4. 推荐总体架构

推荐主链如下：

用户
→ BP问问前端
→ `dispatch API`
→ `BP问问 Orchestrator`
→ 选择：

- 直接回答
- 读取系统数据
- 调用业务工具
- 调用工作流
- 调用 `LongxiaAdapter`

→ 执行结果写入 `execution_result`
→ BP问问整合并输出
→ 必要时引导用户进入：

- 我的文档空间
- 合作空间
- 系统表单
- 工单
- AI宿舍任务页

其中：

- `Kimi 2.5` 先作为 BP问问的第一推理模型
- `龙虾 / Open Claw` 先作为第一执行器

---

## 5. Kimi 2.5 的当前定位

当前建议把 Kimi 2.5 用在 BP问问这一层，而不是直接替代龙虾。

推荐职责：

- 意图识别
- 多轮对话理解
- 任务拆解
- 路由判断
- 结果总结
- 记忆抽取
- 长对话压缩

不建议一开始就让 Kimi 2.5 直接负责：

- 浏览器页面执行
- 系统表单正式回写
- 文件系统批量动作

因此当前阶段应形成：

- `Kimi 2.5 = BP问问的大脑`
- `龙虾 / Open Claw = BP问问调度下的执行手`

当前本地环境变量建议至少保留：

- `KIMI_API_KEY`
- `KIMI_BASE_URL`

---

## 6. 从 Claude Harnessing 结构里借什么

参考 Claude 源码后，BPAI 最值得借的不是整套产品形态，而是以下结构：

### 6.1 Coordinator / Worker 分层

对应到 BPAI：

- `BP问问` = Coordinator
- `龙虾 / Open Claw / 业务工具` = Worker

### 6.2 工具池过滤

BP问问不应永远看到全量工具。

应按以下维度动态过滤：

- 用户身份
- 当前空间
- 当前对象
- 当前任务类型
- 当前权限

### 6.3 类型化动作

建议把执行动作统一为几类：

- `read`
- `search`
- `draft_write`
- `structured_writeback`
- `browser_agent`
- `workflow_trigger`
- `human_confirm_required`

### 6.4 控制传输层

BP问问与龙虾之间不应直接传一句自然语言。

应有一层 `LongxiaAdapter` 做桥接，负责：

- 输入规范化
- 权限边界下发
- 结果结构化回收

---

## 7. BP问问与龙虾的通信方式

### 7.1 不推荐方式

不推荐：

- 前端直接调龙虾
- BP问问把完整上下文裸发给龙虾
- 龙虾直接决定是否正式写回系统

### 7.2 推荐方式

推荐：

BP问问前端
→ `POST /api/bp-ask/dispatch`
→ 后端创建 `execution_task`
→ `LongxiaAdapter`
→ 龙虾执行
→ 龙虾返回结构化结果
→ 后端落 `execution_result`
→ BP问问读取并总结

### 7.3 LongxiaAdapter 输入示例

```json
{
  "taskId": "exec_001",
  "source": "bp_ask",
  "goal": "检查仓库材料总表近一周缺项并生成建议",
  "intent": "system_form_analysis",
  "user": {
    "id": "user_dev_001",
    "role": "developer"
  },
  "scope": {
    "workspaceId": "sys-space-warehouse",
    "systemFormId": "form_warehouse_master",
    "documentIds": ["doc_001"]
  },
  "permissions": {
    "canRead": true,
    "canEdit": true,
    "canDelete": false,
    "canUpload": false
  },
  "allowedActions": [
    "read_system_form",
    "read_document",
    "write_draft_comment",
    "return_structured_result"
  ],
  "expectedOutput": "structured_report"
}
```

### 7.4 LongxiaAdapter 输出示例

```json
{
  "taskId": "exec_001",
  "status": "completed",
  "summary": "发现 3 项高频缺项，建议补货并同步仓储系统后台",
  "artifacts": [],
  "suggestions": [
    "生成一份缺项说明草稿",
    "提醒仓储负责人确认主表"
  ],
  "writebacks": []
}
```

## 8. 核心数据对象

为了支持长对话、执行、追踪与回放，至少需要以下对象：

### 8.1 `conversation_thread`

代表一段连续对话线程。

建议字段：

- `id`
- `user_id`
- `title`
- `status`
- `last_message_at`
- `last_summary_id`

### 8.2 `conversation_turn`

代表一轮用户输入或系统输出。

建议字段：

- `id`
- `thread_id`
- `role`
- `content`
- `referenced_objects`
- `token_estimate`
- `created_at`

### 8.3 `memory_capsule`

代表压缩后的中间记忆单元。

建议字段：

- `id`
- `thread_id`
- `capsule_type`
- `summary`
- `open_loops`
- `confirmed_facts`
- `preferences`
- `referenced_objects`
- `valid_from_turn_id`
- `valid_to_turn_id`

### 8.4 `execution_task`

代表一次被调度出去的执行任务。

建议字段：

- `id`
- `source`
- `thread_id`
- `user_id`
- `intent`
- `executor_kind`
- `status`
- `allowed_actions`
- `target_objects`
- `created_at`

### 8.5 `execution_result`

代表执行器返回的结构化结果。

建议字段：

- `id`
- `task_id`
- `status`
- `summary`
- `raw_output`
- `structured_output`
- `artifacts`
- `writeback_candidates`
- `created_at`

## 9. 长对话与单用户记忆

BP问问必须支持长对话，不能做成“单次问答后上下文消失”的模式。

### 9.1 推荐记忆分层

建议拆成四层：

1. `短时上下文`
   当前窗口附近若干轮对话。

2. `会话级压缩记忆`
   当前线程内已确认事实、目标、约束、未完成项。

3. `用户长期记忆`
   用户偏好、常用术语、常管空间、常管表单、角色习惯。

4. `对象记忆`
   和文档、合作空间、系统表单、工单绑定的上下文记忆。

### 9.2 推荐数据库模式

阶段四推荐采用：

- `PostgreSQL` 存对话、任务、结果、元数据
- `pgvector` 存语义向量
- 文件对象仍沿用现有资产存储链

推荐原因：

- 与现有对象模型兼容
- 便于长期记忆检索
- 便于后续权限过滤

---

## 10. 上下文压缩机制

长对话不能每次把所有历史原文全部塞回模型。

### 10.1 触发条件

建议满足任一条件即触发压缩：

- 总 token 超阈值
- 单线程轮次超过阈值
- 出现重要状态变更
- 线程准备交给执行器前

### 10.2 压缩结果应抽取什么

压缩不应只是“短摘要”，而应抽成结构化信息：

- 当前核心目标
- 已确认事实
- 已确认限制
- 用户偏好
- 已引用对象
- 未完成事项
- 下一步建议

### 10.3 压缩后的用途

压缩结果用于：

- 后续继续对话
- 调用龙虾执行
- AI宿舍任务回放
- 工单与系统表单的审计链

---

## 11. 文档与合作空间文件搜索

### 11.1 不能只做文件名搜索

如果 BP问问要真正可用，文档空间和合作空间的搜索不能只停留在：

- 文件名
- 文件夹名

还必须支持：

- 文本内容片段搜索
- 表格内容检索
- 演示稿正文检索
- 元数据检索
- 当前空间/当前表单上下文检索

### 11.2 推荐搜索分层

建议拆成三层：

1. `元数据搜索`
   文件名、类型、空间、负责人、更新时间、标签。

2. `全文搜索`
   抽取文本后做关键词检索。

3. `语义搜索`
   把片段切块后入向量索引，供 BP问问与 AI 使用。

### 11.3 推荐流程

上传或更新文件时：

- 提取文本
- 分块
- 记录对象归属与权限
- 写入搜索索引
- 写入向量索引

检索时：

- 先做权限过滤
- 再做元数据与全文检索
- 最后按需要调用向量召回

### 11.4 当前范围建议

阶段四优先支持：

- 文档
- 表格
- 演示
- 合作空间系统表单

CAD 可以先只支持：

- 文件名
- 元数据
- 关联工单 / 关联空间

---

## 12. 权限与写回规则

BP问问虽然是总调度层，但不应天然拥有全权写入能力。

当前建议规则：

- 默认允许 `read`
- 默认允许 `search`
- 默认允许 `draft_write`
- `正式回写` 需要权限与条件双重满足

需要明确人工确认的场景：

- 删除
- 移动系统主文件
- 系统表单正式回写
- 工单状态正式推进
- 合作空间成员变更

对龙虾 / Open Claw：

- 默认只允许受控动作
- 只允许访问被下发的页面范围
- 结果先回 BP问问，不直接替代系统最终裁决

---

## 13. Prompt 设计建议

这里不建议直接复制 Claude 的系统 Prompt 原文，而应借其分层思路。

### 13.1 BP问问协调器 Prompt

核心目标：

- 判断用户真实意图
- 不臆造系统状态
- 优先用结构化对象说话
- 能自己答就不乱调执行器
- 复杂流程才交给龙虾

### 13.2 龙虾执行器 Prompt

核心目标：

- 严格按允许动作执行
- 页面动作尽量可复现
- 不越权
- 不直接决定正式回写
- 返回结构化执行结果

### 13.3 压缩器 Prompt

核心目标：

- 不写废话
- 只保留后续执行真的需要的信息
- 明确区分确认事实与待确认事项

## 14. 第一版技术落地建议

### 14.1 第一步

先做：

- `BP问问` 页面壳
- `dispatch API`
- `execution_task`
- `execution_result`
- `Kimi 2.5` 调度模型接入

### 14.2 第二步

再做：

- `LongxiaAdapter`
- 复杂任务默认调龙虾
- 结果结构化回收

### 14.3 第三步

再做：

- 单用户长对话线程
- 会话压缩记忆
- 文档空间与合作空间搜索

### 14.4 第四步

最后做：

- AI宿舍任务看板
- 执行回放
- 正式回写审批链

---

## 15. 当前最值得先做的 5 件事

1. 定义 `BP问问` 前端页与后端 `dispatch API`
2. 定义 `execution_task / execution_result` 表结构
3. 把 Kimi 2.5 接成 BP问问第一推理层
4. 定义 `LongxiaAdapter` 输入输出协议
5. 为文档空间、合作空间、系统表单建立统一搜索索引入口

---

## 16. 一句话总结

BP问问不应做成“另一个聊天框”，也不应做成“龙虾壳”。

它应被做成：

> 一个有长对话、有记忆、有压缩、有搜索、有权限边界、能调龙虾和业务工具的 Harnessing AI 中枢。
