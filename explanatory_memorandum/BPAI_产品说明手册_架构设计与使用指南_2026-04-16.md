## 1. 项目一句话定义

`BPAI` 是一套面向工程型组织的 AI 原生工作平台，用来把“需求理解、任务调度、工单流转、文档协作、AI 执行、过程留痕”统一到一个系统里。

它不是单独的聊天工具，不是单独的工单系统，也不是单独的文档库，而是一套围绕真实工程协同场景设计的统一工作平台。

更直观地说，BPAI 想解决的是这样一种常见状态：用户脑子里只有一句业务需求，但系统背后其实要同时调用人、任务、文档、图纸、表格、规则、AI 和执行记录。过去这些动作往往分散在多个系统和多个群聊里，现在 BPAI 试图把它们收束到同一个平台中，让“提需求的人、执行任务的人、做记录的人、做分析的人、看结果的人”都围绕同一套对象工作。

## 2. 这套产品要解决什么问题

### 2.1 入口分散

真实业务中，用户经常面临以下问题：

- 有问题，但不知道该问谁
- 有任务，但不知道该进哪个系统
- 有资料，但不知道应该挂到哪里
- 有异常，但不清楚该走工单、文档、审批还是人工协作

### 2.2 工程协同链路割裂

工程类业务天然跨对象、跨角色、跨页面：

- 项目
- 工单
- 图纸
- 文档
- 台账表格
- 送审材料
- 施工日志
- 预警异常
- 交付结果

如果这些对象散落在不同系统里，结果通常是：

- 状态无法追踪
- 责任不清
- 信息重复搬运
- AI 无法得到稳定上下文

### 2.3 文档协作与业务执行脱节

很多业务最终都会落到：

- 文档
- 表格
- CAD 图纸
- 材料包
- 回单
- 送审内容

如果文档系统只存文件，不承接协作、评论、AI 草稿、工单挂接和过程留痕，就无法形成闭环。

### 2.4 AI 没有稳定的调度边界

如果 AI 只是散落在页面里的按钮或助手，会出现：

- 谁负责理解问题不清楚
- 谁负责执行不清楚
- 谁负责回收结果不清楚
- 权限边界不清楚
- 审计与留痕不清楚

因此 BPAI 的核心设计不是“给系统加一个 AI”，而是把 AI 作为系统主干之一来设计。

在工程业务里，这个问题尤其严重。因为用户常常不是来做一句闲聊，而是来发起一条会继续扩散的请求，例如“帮我把长沙最近一周异常工单整理一下，顺便看看哪些材料还没补齐”。这句话背后很可能会触发工单检索、资料核对、文档挂接、执行预案生成、人工确认等一整串动作。如果 AI 只是一个聊天框，它就只能给出一段漂亮但不可追踪的回答；如果 AI 被纳入系统主干，它就能把这句话拆成任务、对象、状态和后续动作。

## 3. 产品定位与核心价值

### 3.1 产品定位

BPAI 的产品定位可以概括为四个关键词：

- `统一入口`
- `状态闭环`
- `内容协作`
- `受控 AI`

这四个关键词不是并列口号，而是一条因果链：

- 因为入口分散，所以需要 `统一入口`
- 因为任务要有人接、要有状态推进，所以需要 `状态闭环`
- 因为很多执行结果最终都会落成资料、清单、图纸或报告，所以需要 `内容协作`
- 因为 AI 要参与到真实流程里，所以必须是 `受控 AI`

### 3.2 核心价值

对管理者：

- 快速看全局
- 快速看异常
- 快速知道该叫谁处理
- 快速拿到结构化结论

对调度者 / 项目负责人：

- 通过 BP问问统一发起任务
- 把任务沉淀到工单
- 把资料沉淀到文档空间
- 把 AI 执行结果变成可追踪对象

对执行人员：

- 明确自己当前该做什么
- 明确与工单关联的资料和图纸
- 明确哪些结果由 AI 先整理、哪些需要人工确认

对协作者：

- 文档协作有秩序
- 评论、建议、接力编辑可留痕
- AI 参与时不破坏正式内容秩序

对 AI 管理者：

- 工作流、Skill、AI 员工有统一承接面
- AI 任务与执行结果可观察、可统计、可回放

## 4. 核心设计思路

这套产品的设计思路不是“堆模块”，而是“围绕对象和链路做分层”。

换句话说，BPAI 不是先想“我要做几个页面”，而是先想“一个真实业务请求在系统里会穿过哪些对象、经过哪些角色、在哪些点发生确认和回写”。页面只是这些机制最终被用户看到的外壳，真正重要的是对象关系、职责边界和状态变化被组织清楚。

### 4.1 统一入口优先

用户优先从 `BP问问` 进入系统，而不是先要求用户自己判断应该去哪个深层模块。

### 4.2 调度层与执行层分离

- `BP问问` 负责理解、拆解、路由、整合与最终表达
- `AI宿舍` 负责承接执行资源、工作流、Skill 与 AI 员工
- `OpenClaw / 龙虾 / AI员工 / 工作流` 负责专业执行

### 4.3 工单承接状态，文档承接内容

这是一条必须明确的系统原则：

- 工单优先承接：状态、责任、进度、异常、流程推进
- 文档档案室优先承接：内容、草稿、评论、版本、资料、图纸

### 4.4 AI 默认受控，不默认直写正式对象

AI 的默认职责更接近：

- 读取
- 总结
- 分类
- 给建议
- 起草草稿
- 生成执行预案

AI 不默认拥有无限制正式写入权。

### 4.5 协作规则优先于炫技

文档协作第一阶段优先采用：

- 单编辑者锁
- 多人旁观评论
- 权限解锁编辑

而不是一开始就追求多人无边界实时共编。

### 4.6 结果必须有落点

执行结果不能只停留在对话里，必须能沉淀到：

- 工单
- 文档
- 表格
- 评论
- 草稿
- AI 执行结果对象

## 5. 六大模块总览

当前 BPAI 已形成六个顶层模块，这个信息架构是整个系统的骨架。

| 模块 | 定位 | 当前作用 | 当前正式路由 |
| --- | --- | --- | --- |
| BP问问 | 统一入口、调度中枢、最终表达层 | 承接自然语言请求，做普通聊天或任务调度 | `/bp-ask` |
| 总览 | 全局观察层 | 看系统态势、地图、预警、设置 | `/dashboard` |
| 工程队 | 组织化执行层 | 看编队、成员、后台域、执行面 | `/engineering` |
| 工单 | 状态机与执行承接层 | 创建、跟踪、派单、阶段资料上传 | `/work-orders` |
| 文档档案室 | 内容资产与协作层 | 文件、表格、文档、CAD、合作空间 | `/docs/**` |
| AI宿舍 | AI 执行后场与能力资产层 | 任务收件箱、工作流、Skill、AI员工、OpenClaw 发射入口 | `/ai-dorm` |

从使用感知上看，这六个模块对应的是六种完全不同的“工作姿势”：

- 进入 `BP问问` 时，用户是在“提问题、交代意图、请求系统帮我想清楚”
- 进入 `总览` 时，用户是在“看局势、看异常、看哪里需要介入”
- 进入 `工程队` 时，用户是在“看组织、人力和承接能力”
- 进入 `工单` 时，用户是在“盯状态、盯责任、盯进度”
- 进入 `文档档案室` 时，用户是在“处理资料、内容和协作对象”
- 进入 `AI宿舍` 时，用户是在“看 AI 后场、执行资产和能力承接”

### 5.1 模块关系不是并列孤岛

- `BP问问` 是入口层
- `总览` 是观察层
- `工程队` 是组织执行层
- `工单` 是状态与流转层
- `文档档案室` 是内容与协作层
- `AI宿舍` 是 AI 能力与执行资源层

### 5.2 当前模块关系主链

```text
用户
-> BP问问
-> 选择直接回答 / 检索 / 工作流 / AI员工 / OpenClaw
-> 执行结果写入 execution_tasks / execution_results
-> 必要时挂回工单 / 文档 / 合作空间
-> BP问问做最终解释
```

## 6. 关键用户角色

这些角色并不总是互斥的。在真实项目中，同一个人可能同时具备“调度者 + 文档编辑者”的身份，也可能在不同时间段切换成“管理者”或“系统治理者”的视角。因此 BPAI 的角色设计不是为了把人锁死在单一身份里，而是为了在不同操作场景下明确“此刻他应该看什么、能做什么、不能越过什么边界”。

| 角色 | 核心关注点 | 高频模块 |
| --- | --- | --- |
| 管理者 / 决策者 | 全局状态、预警、资源负载、结果摘要 | 总览、BP问问、工单、AI宿舍 |
| 调度者 / 项目负责人 | 任务拆解、指派、工单推进、AI 调度、文档挂接 | BP问问、工单、工程队、文档档案室、AI宿舍 |
| 工程执行人员 | 我的任务、现场状态、资料与图纸、回单与补件 | 工程队、工单、文档档案室 |
| 文档编辑者 | 谁在编辑、怎么接力、版本与评论怎么管理 | 文档档案室、工单 |
| 文档评论者 | 如何只读、评论、提建议、不误改正式内容 | 文档档案室、工单 |
| AI 工作流设计者 / AI 执行管理者 | 哪些任务可标准化、哪些 AI 员工负责什么、执行链是否稳定 | AI宿舍、BP问问 |
| 系统管理员 / 解锁者 | 权限治理、解锁、审计、系统健康 | 系统后台、文档档案室、AI宿舍、总览 |

如果从一天的工作节奏来理解这些角色：

- 管理者更像“看盘的人”，他关心系统今天有没有异常、有没有卡点、资源有没有失衡
- 调度者更像“排兵布阵的人”，他关心任务怎么拆、该派给谁、是否需要 AI 先跑一段
- 工程执行人员更像“真正下场的人”，他需要的是清晰的任务对象和少废话的状态入口
- 文档编辑者更像“正式产出内容的人”，他关心的是编辑秩序、版本和责任归属
- AI 管理者更像“能力运营者”，他不是每天盯某个工单，而是盯系统里哪类任务正在被标准化

## 7. 关键业务旅程

### 7.1 旅程一：模糊需求进入系统

```text
用户提出自然语言需求
-> BP问问理解问题
-> 判断是直接问答、数据检索还是执行任务
-> 输出答案或进入调度
```

这个旅程的价值在于把“模糊”变成“可落地”。很多用户并不会一开始就把目标描述成结构化任务，他们只是说一句“帮我看一下这个项目卡在哪”。BP问问的职责不是急着输出答案，而是先把这句话翻译成系统能处理的对象组合，例如：这是在问某个工单、某个项目上下文、某类风险，还是在请求一次资料核查。

### 7.2 旅程二：任务进入执行闭环

```text
用户需求
-> BP问问调度
-> 生成 execution task
-> 需要持续跟进时创建或更新工单
-> 工程队承接执行
-> 结果回写工单 / 文档
```

这条旅程体现了 BPAI 与普通聊天工具最大的差异。普通聊天工具通常停在“给出建议”，BPAI 要尽量继续往下走到“生成任务对象、分配责任、挂接资料、形成可追踪状态”。也正因为如此，工单在 BPAI 中不是附属功能，而是承接 AI 结果走向真实执行的关键桥梁。

### 7.3 旅程三：文档协作与资料沉淀

```text
资料上传到文档档案室
-> 进入文档 / 表格 / CAD / 合作空间
-> 在线查看或编辑
-> 评论、建议、接力编辑
-> 与工单和协作空间形成关联
```

这条旅程对应的是工程协同里最“琐碎但关键”的部分。很多系统在任务流转上设计得很完整，但一到资料侧就只剩一个上传按钮。BPAI 试图避免这种断裂，让文件不是上传完就消失，而是继续留在系统主干里，能被查看、被评论、被关联到工单、被 AI 读取，最终成为可追踪的业务资产。

### 7.4 旅程四：AI 协助处理但不失控

```text
BP问问识别复杂任务
-> AI宿舍承接任务对象
-> 工作流 / Skill / AI员工给出执行预案或结果
-> 结果写 execution_results
-> 人工确认后再决定是否正式回写
```

这条旅程最关键的不是“AI 多聪明”，而是“AI 的动作有没有被系统化约束”。BPAI 明确把 AI 执行结果先放进 execution result，再决定是否回写到正式对象，就是为了避免系统被一次错误生成直接污染。对于作品集而言，这一点非常重要，因为它体现的是产品治理能力，而不是单点模型接入能力。

### 7.5 旅程五：管理者从总览追到细节

```text
管理者查看总览
-> 发现异常 / 预警 / 卡点
-> 通过 BP问问继续追问
-> 跳到工单 / 工程队 / 文档 / AI宿舍深查
```

这条旅程说明 BPAI 的观察层和执行层不是断开的。总览不是一个漂亮的大屏死图，它的意义在于帮助用户发现值得追的对象；BP问问不是单独的聊天框，它要承担“继续追问、继续定位”的功能；工单和文档也不是孤立页面，而是管理者最终落脚到的具体对象层。

## 8. 当前系统架构总览

## 8.1 技术栈

| 层 | 技术 |
| --- | --- |
| Web 框架 | `Next.js 16.2.1` |
| 前端框架 | `React 19.2.4` |
| 数据访问 | `drizzle-orm` + `pg` |
| 数据库 | `PostgreSQL` |
| 文档编辑 | `OnlyOffice` |
| CAD 查看 | `@mlightcad/cad-viewer`、`@mlightcad/cad-simple-viewer`、`three` |
| 地图能力 | `leaflet`、`@amap/amap-jsapi-loader` |
| AI 模型适配 | `Kimi / Moonshot OpenAI-compatible chat completions` |
| AI 执行 sidecar | `OpenClaw` |
| 容器编排 | `docker-compose.dev.yml` |

## 8.2 分层结构

```text
用户界面层
-> frontend/src/app/** 页面
-> frontend/src/components/** 组件

API / BFF 层
-> frontend/src/app/api/**/route.ts

领域服务层
-> frontend/src/lib/auth
-> frontend/src/lib/content
-> frontend/src/lib/workspace
-> frontend/src/lib/work-order
-> frontend/src/lib/engineering
-> frontend/src/lib/engineering-team
-> frontend/src/lib/bp-ask
-> frontend/src/lib/ai-dorm

数据与持久化层
-> frontend/src/lib/db/schema.ts
-> frontend/drizzle/*.sql
-> PostgreSQL
-> .bpai/storage
-> raw shadow / app-store mirror

外部集成层
-> OnlyOffice
-> CAD viewer
-> Kimi API
-> OpenClaw gateways
```

如果把这套结构理解成一次真实请求的通道，可以把它想象成：

```text
用户在前端说一句需求
-> 页面或组件发起 API 请求
-> Route Handler 做鉴权和参数整理
-> 领域服务决定读哪类对象、写哪类对象
-> 数据层与文件层完成持久化
-> 外部集成层负责在线编辑、模型调用、执行 sidecar
-> 再把结果回送到前端，让用户看到可解释的状态变化
```

这个分层的好处是，产品逻辑不会全都挤在前端页面里，也不会散成难以管理的脚本式调用。它为后续继续扩大业务域提供了足够稳定的骨架。

## 8.3 架构特点

### 8.3.1 前后端不是分离微服务

当前后端形态是：

- `Next.js App Router BFF`
- `Route Handlers`
- `server-only domain services`

而不是独立的后端微服务集群。

### 8.3.2 数据层处于“Postgres + 过渡镜像层”并存状态

当前部分能力已经正式落到 Postgres，但仍保留：

- `raw-shadow`
- `app-store-read`
- `app-store-write`

用于兼容旧存储结构和过渡迁移。

### 8.3.3 内容存储仍是本地磁盘为主

当前真实文件存储路径在：

- `process.cwd()/.bpai/storage`

这意味着当前更适合本地开发、单机演示或带持久卷的容器环境。

## 9. 仓库目录说明

| 路径 | 作用 |
| --- | --- |
| `frontend/` | 正式前端工程、API、服务层、数据库定义 |

| `frontend/drizzle/` | 迁移 SQL 与快照 |
| `frontend/scripts/` | DB、冒烟、CAD 相关脚本 |
| `Front/` | 早期静态原型与视觉样板来源 |
| `AI_Dev_Memo/Project_skeleton/` | 产品骨架、角色、AI 主干、权限、协作规则 |
| `Construction_ Specification/` | 基于当前代码事实整理的建设规范 |

| `explanatory_memorandum/` | 本次产品说明手册输出目录 |

### 9.1 一个重要边界

必须明确区分：

- `Front/`：原型和产品结构来源
- `frontend/`：正式工程承接目录

不能把原型页当成正式实现，也不能把正式工程误判成“只有壳子没有方向”。当前 BPAI 是“原型骨架清晰、正式承接已在多个业务域落地”的状态。

## 10. 当前正式路由地图

### 10.1 页面路由

## 12. 六大模块的详细说明

## 12.1 BP问问

### 12.1.1 产品定位

BP问问是 BPAI 的：

- 统一入口
- 调度中枢
- 最终解释层

一句话概括：

> BP问问负责“想清楚、叫对人、收结果、说人话”。

如果把 BPAI 比作一个工程现场的中枢室，BP问问更像站在最前面的总调度台。用户不需要知道底下到底是数据库、工单服务、文档空间还是 AI sidecar 在干活，他只需要先把问题交给 BP问问。BP问问负责把用户说的话翻译成系统内部的语言，再把系统内部复杂的返回结果翻译回用户能继续行动的话。

### 12.1.2 当前实现位置

- 页面：`frontend/src/app/bp-ask/page.tsx`
- 主控组件：`frontend/src/components/bp-ask/bp-ask-shell.tsx`
- 服务层：`frontend/src/lib/bp-ask/server.ts`
- 调度层：`frontend/src/lib/bp-ask/dispatch.ts`
- 模型适配：`frontend/src/lib/bp-ask/kimi.ts`

### 12.1.3 当前能力

- 会话线程列表
- 新建线程
- 删除线程（实际是归档）
- 多轮消息持久化
- rolling summary
- memory facts upsert
- dispatch preview
- 普通聊天与任务型请求分流
- Kimi 分类增强与普通聊天回复
- execution task / result 写库

### 12.1.4 当前交互特点

- 用户消息先即时上屏
- assistant 单独 loading
- 普通聊天不强制展示任务细节
- 任务型请求会在折叠区域展示处理细节

### 12.1.5 一次消息的完整生命周期

```text
前端输入 prompt
-> POST /api/bp-ask/threads/[threadId]/messages
-> 写 user message
-> 读取 recent messages / rolling summary / memory facts
-> dispatchBpAskPrompt
-> 写 execution_tasks
-> 写 execution_results
-> 写 assistant message
-> 更新 rolling summary
-> upsert memory facts
-> 返回更新后的 thread detail
```

### 12.1.6 设计价值

BP问问不是简单聊天，而是把“自然语言入口”转换成“可追踪任务对象”的关键桥梁。

这意味着 BP问问的成功标准不只是“回答得像不像人”，而是它能不能把含糊的请求转成明确的对象、状态和下一步动作。对一个工程型系统来说，这种能力比单次回答的文采更重要。

## 12.2 文档档案室

### 12.2.1 产品定位

文档档案室不是简单文件夹，而是：

- 内容资产中心
- 协作空间承接层
- 文档 / 表格 / CAD / 合作空间入口
- AI 与业务结果的资料承接面

从用户体验上看，文档档案室应该给人的感受不是“文件都堆这里”，而是“这里是所有资料对象继续活着的地方”。文件上传之后不会立即脱离业务主链，而是继续有可能被评论、被引用、被挂到工单、被 AI 读取、被用于后续交付和归档。

### 12.2.2 当前实现位置

- 页面：`frontend/src/app/docs/**`

- 内容服务：`frontend/src/lib/content/server.ts`
- 浏览状态服务：`frontend/src/lib/content/browser-state.ts`
- 协作空间服务：`frontend/src/lib/workspace/server.ts`

### 12.2.3 当前能力

- 上传文件
- 创建文档 / 表格 / 演示
- 浏览文件夹
- 回收站恢复与清空
- 工作区浏览状态持久化
- 合作空间列表与详情
- 系统表单入口
- 文档详情按文件类型分流
- OnlyOffice 在线编辑
- CAD 文件流与查看链路

### 12.2.4 文档详情分流逻辑

```text

-> 查询 document / sheet / slide 资产
-> 判断扩展名
-> Office 文件走 OnlyOffice
-> dwg / dxf 走 CAD viewer
-> 其他文件走下载 / 通用预览路径
```

### 12.2.5 协作设计原则

当前产品层明确采用：

- 单编辑者锁
- 多人旁观评论
- 权限解锁编辑

虽然当前代码中协作锁机制尚未完整落地成全部对象级能力，但这已经是项目明确的设计方向。

### 12.2.6 设计价值

文档档案室为 BPAI 提供了内容承接层。没有它，AI 结果只能停留在聊天里，工单也无法挂接材料、图纸和草稿。

它的另一个价值是给系统建立“内容记忆”。很多工程系统的问题不是状态没有被记录，而是材料和过程没有被系统化沉淀，导致每次都要重新翻群聊、翻聊天记录、翻本地文件夹。文档档案室的意义，就是让这些内容对象从“散文件”升级成“系统对象”。

## 12.3 工单

### 12.3.1 产品定位

工单模块是系统中的状态机与执行事务对象。

它负责：

- 创建任务对象
- 承接进度

如果说 BP问问负责把问题说清楚，工单负责的就是把事情真正挂起来。它是整个系统中最接近“事情到底有没有被人接住”的对象层。没有工单，很多 AI 分析和人工讨论最后都会停留在口头层；有了工单，系统才能把责任、优先级、阶段、阻塞项、关联资料稳定承接下来。

从作品集表达角度看，工单模块体现的是 BPAI 不是“AI 看板”，而是真正把系统设计成了可以往下执行的业务平台。它让“分析结果”开始拥有责任人、时间线和回写路径。

## 12.5 AI宿舍

### 12.5.1 产品定位

AI宿舍是 AI 的执行后场和能力资产层，不是主要对话入口。

当前三核结构已经非常明确：

- 工作流工坊
- Skill 仓库
- AI员工

再加一个与 BP问问打通的任务收件箱。

可以把 AI宿舍理解成 BPAI 的“AI 运营后台”。BP问问更像前台接单的人，AI宿舍更像后场机房和调度舱：这里能看到任务有没有进来、哪些能力是现成资产、哪些执行体在待接入、哪些能力只是蓝图还没完全动态化。

### 12.5.2 当前实现位置

- 页面：`frontend/src/app/ai-dorm/**`
- 组件：`frontend/src/components/ai-dorm/**`
- 服务：`frontend/src/lib/ai-dorm/server.ts`
- OpenClaw 配置：`frontend/src/lib/ai-dorm/openclaw.ts`

### 12.5.3 当前真实能力

- 读取当前用户的 `execution_tasks / execution_results`
- 生成 AI宿舍总览数据
- 任务收件箱页面
- 工作流工坊页面
- Skill 仓库页面
- AI员工页面
- OpenClaw sidecar 发射入口

### 12.5.4 当前能力的“真实与蓝图”边界

需要明确区分两层：

第一层，当前真实落地：

- 任务数据来自真实数据库表
- AI宿舍导航统计来自真实任务数据
- OpenClaw launch route 已存在

第二层，当前蓝图承接：

- 工作流、Skill、AI员工目前主要由 `server.ts` 中的 blueprint 数据驱动
- 它们现在的定位更接近“可用产品壳 + 清晰结构定义”
- 这使得 AI宿舍既能展示设计方向，也不会冒充成已经 fully automated 的执行系统

### 12.5.5 当前 AI 员工与 OpenClaw

当前已定义的 sidecar 包括：

- `work-order-longxia`
- `document-longxia`
- `drawing-longxia`
- `alert-longxia`
- `report-longxia`

其 launch route 形态为：

- `/api/ai-dorm/openclaw/launch`
- `/api/ai-dorm/openclaw/[agentId]/launch`

实现方式是：

```text
后端根据 agentId 读取环境变量
-> 拼出 OpenClaw console URL
-> 把 gateway token 放到 hash
-> redirect 到对应 sidecar 控制台
```

### 12.5.6 设计价值

AI宿舍的意义不在于替代 BP问问，而在于把执行资源、流程资产和 AI 员工管理从“不可见后台”变成“可观察、可配置、可扩展的后场”。

这点对作品集表达尤其重要，因为很多 AI 产品只展示前台聊天，而不展示执行后场。BPAI 把后场显性化之后，整个系统就不再是黑盒，而是一个可以被观察、被讲解、被继续扩建的 AI 执行平台。

## 13. 权限、协作与回写规则

这一部分决定了 BPAI 最终会不会失控。因为系统一旦同时拥有 AI、文档、工单和执行链路，如果没有权限与回写规则，表面上看很智能，实际上会非常脆弱。当前这套规则的目标不是把系统做得保守，而是把“谁能看、谁能改、谁能建议、谁能正式回写”先分清楚。

## 13.1 当前权限设计的三层结构

### 第一层：模块访问权限

决定用户能否进入某模块。

### 第二层：对象操作权限

决定用户能否：

- 查看
- 评论
- 编辑
- 创建
- 指派
- 归档
- 解锁

### 第三层：回写权限

决定用户或 AI 执行体是否能把结果写回正式对象，以及写回到哪一层。

## 13.2 文档协作设计

第一阶段推荐规则：

- 同一时刻只允许一个正式编辑者
- 其他用户默认只读，但可评论
- 评论不受编辑锁完全阻断
- 管理者或解锁者可强制解锁
- AI 默认是建议者 / 评论者 / 草稿生成者，而不是默认正式编辑者

## 13.3 工单与文档的回写职责分工

- 工单优先承接状态回写
- 文档档案室优先承接内容回写

## 13.4 AI 回写总原则

AI 第一阶段优先写入：

- execution result
- 评论
- 建议
- 草稿
- 受限字段

不默认直接覆盖：

- 工单关键状态
- 正式文档正文
- 关键业务字段

## 13.5 手机端轻操作原则

虽然当前仓库尚未形成完整移动端实现，但产品骨架已明确手机端未来更适合承接：

- 出工
- 到场
- 开工
- 暂停
- 完成
- 异常上报
- 简短备注

而不是一开始开放复杂配置与深度编辑。

## 17. 模块级使用说明

以下部分按“作品集演示 / 新协作者上手”的视角编写。

建议把这一章理解成一份“带着人走系统”的讲解稿。它不是低层接口文档，而是告诉第一次接触 BPAI 的人，应该先从哪里看、每一步会看到什么、每一步背后大致发生了什么。

## 17.1 登录

1. 打开 `/login`
2. 使用任意内置测试账号登录
3. 登录成功后，系统当前会跳转到 `/docs/documents`

## 17.2 文档档案室使用

### 17.2.1 上传资料

1. 进入 `/docs/documents`
2. 通过文件浏览器上传文件
3. 系统会调用 `/api/assets/upload`
4. 文件落盘到 `.bpai/storage`
5. 资产信息写入 `content_assets` 与 `file_placements`

对演示者来说，这一步很关键，因为它能直接说明 BPAI 的资料不是“传完即失联”的附件，而是正式资产对象。上传完成后，文件已经具备了标题、类型、更新时间、打开路径、内容流地址和后续被工单或 AI 引用的可能性。

### 17.2.2 打开文档

1. 在文件列表中点开某个文档
2. 系统跳到 `/docs/documents/[docId]`
3. 若为 Office 文件，会进入 OnlyOffice
4. 若为 `dwg/dxf`，会走 CAD viewer
5. 若为其他文件，会走下载或通用内容路径

### 17.2.3 回收站

1. 进入 `/docs/trash`
2. 可执行恢复或清空
3. 对应调用 `/api/trash/restore`、`/api/trash/clear`

### 17.2.4 合作空间

1. 进入 `/docs/workspace`
2. 创建合作空间
3. 可在详情页查看成员、相关表单与协作对象

## 17.3 工单模块使用

### 17.3.1 创建工单

1. 进入 `/work-orders`
2. 点击创建工单
3. 填写标题、来源、优先级、负责人、项目与站点信息
4. 如需要，可同时创建专属合作空间

这一动作最能体现 BPAI 的“对象化”思路。因为创建工单并不只是新增一条列表数据，它同时意味着这件事开始拥有正式编号、阶段、责任人、可能的资料空间，以及未来继续被派单、被追踪、被回写的能力。

### 17.3.2 查看与更新工单

1. 打开 `/work-orders/[workOrderId]`
2. 查看当前阶段、负责人、缺项、交付状态
3. 可更新进度和阶段
4. 可执行派单
5. 可上传阶段资料

### 17.3.3 上传阶段资料

1. 在工单详情页进入阶段资料面板
2. 选择当前阶段并上传文件
3. 系统会自动创建阶段文件夹并挂接工单与资产关系

## 17.4 工程队模块使用

### 17.4.1 查看工程看板

1. 进入 `/engineering/board`
2. 查看成员状态、编队与工作负载
3. 配合工单派单判断资源承接情况

### 17.4.2 创建编队

1. 在工程看板中创建 squad
2. 指定队长与成员
3. 供工单派单弹窗读取

## 17.5 BP问问使用

### 17.5.1 普通聊天

输入例如：

- “你好”
- “你是谁”
- “这个系统是干什么的”

系统特点：

- 不会默认进入重任务模式
- 更偏轻量对话与说明

### 17.5.2 任务型请求

输入例如：

- “帮我整理最近一周长沙有哪些预警工单”
- “把这个工单的缺项和下一步建议总结一下”
- “帮我看看这份材料是否适合归档”

系统特点：

- 会经过任务筛网
- 生成 execution task / result
- 在工作台展示折叠的处理细节
- 必要时为后续工单 / 文档 / AI宿舍承接做准备

如果是在作品集演示场景，建议在这一段重点观察两件事：

- 一是系统没有把所有输入都粗暴地当任务，而是先判断有没有明确任务信号
- 二是当任务成立时，结果不只是显示一段文字，而是会留下结构化任务与结果对象

### 17.5.3 历史线程

1. 左侧线程栏可切换线程
2. 删除操作实际是归档，不是物理删除

## 17.6 AI宿舍使用

### 17.6.1 总览页

进入 `/ai-dorm`，可看到：

- 任务总数
- 待处理任务数
- 已完成任务数
- 需要确认的任务数
- 三个核心入口：工作流工坊、Skill 仓库、AI员工

### 17.6.2 任务收件箱

进入 `/ai-dorm/tasks`，可看到：

- 真实来自 `execution_tasks / execution_results` 的任务列表
- 每条任务的 intent、domain、execution mode、confidence、requires write 等信息

这一页很适合作为“系统不是黑盒”的展示点。因为在这里可以直接看到 BP问问刚才那句自然语言，是如何被翻译成结构化任务的。对于非技术评审者，这一页会让他们更容易理解 BPAI 并不是“AI 说完就结束”，而是“AI 的判断被系统记录下来了”。

### 17.6.3 工作流工坊

进入 `/ai-dorm/workflows`，当前可查看：

- 工作流模板
- 节点结构
- linked skill / linked agent
- 最近任务预览

### 17.6.4 Skill 仓库

进入 `/ai-dorm/skills`，当前可查看：

- Skill 资产
- 来源类型：模板、上传、BP问问草案
- linked workflow / linked agent
- 通过 BP问问生成 Skill 草案的入口提示

### 17.6.5 AI员工

进入 `/ai-dorm/agents`，当前可查看：

- 工单龙虾
- 文档龙虾
- 图纸龙虾
- 预警龙虾
- 报表龙虾

若对应 sidecar 可用，可从页面打开 OpenClaw 控制台。

## 17.7 总览使用

1. 进入 `/dashboard`
2. 查看总览卡片与地图画布
3. 进入 `team-status`、`alerts`、`settings`
4. 从总览发现问题后，再跳转工单 / 工程队 / BP问问继续处理

## 20. 当前实现边界与已知限制

这部分非常重要，作品集展示时必须保持诚实。

对于作品集来说，清楚写边界不是减分项，反而是成熟度的一部分。因为它说明这个项目没有把设计稿、蓝图和真实落地混为一谈，而是清楚知道哪些已经在代码里、哪些还是下一步要推进的方向。

## 20.1 原型与正式工程并存

- `Front/` 是产品骨架来源
- `frontend/` 是正式工程
- 两者不能混用认知

## 20.2 workspace 仍处于过渡态

当前 `workspace/server.ts` 仍混合依赖：

- mock data
- raw shadow
- Postgres mirror

这意味着合作空间与部分协作逻辑仍在迁移过程中。

## 20.3 文件存储仍以本地磁盘为主

当前上传文件写入 `.bpai/storage`，不是对象存储。

这对本地开发很友好，但在生产环境要额外处理：

- 持久卷
- 多实例共享
- 备份与恢复

## 20.4 AI宿舍部分内容仍是结构蓝图

当前 AI宿舍里：

- 任务收件箱是实时数据
- 工作流 / Skill / AI员工页面已经成型
- 但这些页面中的大量对象仍以 blueprint 方式承接，而不是已经 fully dynamic 的运营后台

这不是缺点，而是当前阶段的真实边界。

## 20.5 AI 写回仍应视为受控设计，而非全面开放

当前代码已经有 execution task / result 与 Kimi 接入，但系统整体仍坚持：

- AI 优先给建议和结果对象
- 正式回写需人工确认或更明确的权限模型

## 20.6 地图与协作锁等能力仍在演进

当前可以确认设计方向，但并非所有对象级治理已经 fully shipped。

## 22. 这个项目作为作品集的亮点

如果从作品集视角看，BPAI 的亮点不在“页面多”，而在“结构清晰且跨层打通”。

### 22.1 AI 不是外挂，而是主干设计的一部分

BP问问、AI宿舍、execution task / result、Kimi、OpenClaw 不是零散拼接，而是有明确分层。

### 22.2 业务闭环完整

系统不是只做“分析”，而是把：

- 问题理解
- 任务调度
- 工单流转
- 资料承接
- 协作留痕
- AI 执行

放到了同一条链路中。

### 22.3 内容系统不是附件系统

文档档案室不仅存文件，还连接：

- 合作空间
- 表格
- CAD
- 工单资料
- OnlyOffice
- AI 草稿与结果承接

### 22.4 兼顾产品思维与工程思维

仓库中同时具备：

- 产品骨架文档
- 当前代码事实文档
- 可运行前端工程
- 数据模型与迁移
- 外部服务编排

这让 BPAI 非常适合作为“产品 + 工程 + AI 编排”的综合型作品集案例。

### 22.5 边界清楚

项目没有把“规划”和“已实现”混在一起，而是非常明确地区分：

- 当前代码事实
- 产品设计方向
- 正在承接的能力
- 仍在蓝图层的模块

这本身就是成熟项目表达能力的一部分。

## 23. 总结

BPAI 当前已经不是一个单页原型或单点实验，而是一套结构清晰、方向明确、已经具备真实代码承接的工程型 AI 工作平台。

它的核心价值不在于某一个页面做得多炫，而在于以下几件事被系统性地组织起来了：

- 用 `BP问问` 统一承接自然语言入口
- 用 `工单` 承接状态与责任闭环
- 用 `文档档案室` 承接内容、资料与协作
- 用 `工程队` 承接真实组织执行
- 用 `AI宿舍` 把 AI 执行后场显性化
- 用 `execution_tasks / execution_results / memory_facts` 把 AI 调度过程结构化、可追踪、可扩展

如果从产品说明手册的角度给出一句最终结论，那么 BPAI 可以被定义为：

> 一套以 BP问问为统一入口、以工单与文档为业务承接对象、以 AI宿舍为执行后场、面向工程型组织的 AI 原生协作平台。
