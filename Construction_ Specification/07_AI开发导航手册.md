# AI 开发导航手册

> 信息来源范围：本手册建立在 `Construction_ Specification/00-05/99` 与当前 `frontend/` 代码事实之上。更新时间：2026-04-11。
>
> 目标：以后无论你还是 AI 想“快速回答一个项目问题”或“快速定位一个新功能应该串哪几层”，都先按本手册走，而不是重新全仓库遍历。

## 1. 使用方法

### 1.1 当你想快速回答问题时
先把问题归类成下面 9 种之一：

1. 改页面 / UI
2. 改组件交互
3. 改 API
4. 改数据库 schema / migration
5. 改工单流转
6. 改文档协作 / 上传 / OnlyOffice / CAD
7. 改工程队 / 编队 / 派单
8. 改 BP Ask / memory / dispatch / AI 执行
9. 改认证 / session

### 1.2 标准回答模板
以后回答项目问题时，优先按这个格式组织：

```text
1. 先看哪篇文档
2. 先读哪些文件
3. 常涉及哪些 API
4. 常涉及哪些表
5. 改完怎么验证
6. 有哪些高耦合点/风险点
```

## 3. 任务类型导航

---

### 3.1 改页面 / UI

**先看文档**
- `01_前端页面_组件_数据链路.md`
- 必要时 `00_总索引与导航.md`

**先读文件**
- `frontend/src/app/**/page.tsx`
- `frontend/src/components/<domain>/**`

**常涉及 API**
- 客户端组件若有 fetch，则去 `frontend/src/app/api/**/route.ts`

**常涉及表**
- 视页面所在业务域决定：
  - docs -> `content_assets/file_placements/...`
  - work-orders -> `work_orders/...`
  - bp-ask -> `conversation_* / memory_facts / execution_*`

**改完怎么验证**
- 至少打开对应页面走一遍黄金路径
- 若有表单/按钮，验证提交、刷新、数据回显

**高风险点**
- 页面是服务端页面还是客户端壳层，不要搞混
- 服务端页面改数据来源时，可能根本不需要改 API

---

### 3.2 改组件交互

**先看文档**
- `01_前端页面_组件_数据链路.md`
- `02_API路由_后端职责_调用链.md`

**先读文件**
- 组件本身
- 对应 route
- 对应 service

**常见场景**
- 创建按钮
- 弹窗表单
- 提交后刷新列表
- 乐观更新 / 本地 state

**改完怎么验证**
- 点按钮
- 看请求
- 刷新页面确认服务端状态一致

**高风险点**
- 前端本地 state 更新了，但服务端没成功
- 返回结构变了，壳层没同步

---

### 3.3 改 API

**先看文档**
- `02_API路由_后端职责_调用链.md`

**先读文件**
- `frontend/src/app/api/**/route.ts`
- `frontend/src/lib/<domain>/server.ts`
- `frontend/src/lib/db/schema.ts`

**常涉及表**
- auth -> `users/sessions`
- assets -> `content_assets/file_placements`
- workspace -> `workspaces/collaboration_spaces`
- work-orders -> 工单域六张主表
- bp-ask -> `conversation_* / memory_facts / execution_*`

**改完怎么验证**
- 校验 200/400/401/403/404/409/500 行为
- 校验前端是否还能消费返回结构
- 跑相关 smoke script

**高风险点**
- 返回字段改了但前端没改
- 只改 route，没改 service / schema / enums

---

### 3.4 改数据库 schema / migration

**先看文档**
- `03_数据库模型_迁移_业务映射.md`

**先读文件**
- `frontend/src/lib/db/schema.ts`
- `frontend/drizzle/*.sql`
- 使用该表的 route/service

**标准动作**
1. 找锚点表
2. 确定字段属于哪个业务域
3. 更新 schema
4. 更新 migration
5. 更新 service / route / UI label

**改完怎么验证**
- 至少跑类型检查
- 若能运行数据库，确认 migration 可执行
- 抽样走对应业务链路

**高风险点**
- 增加枚举后忘了改前端 label
- 改表后忘了改 raw shadow / app-store mirror 过渡层

- 若启用真实模型，还要同步检查 env 与调用封装

## 4. 最快定位索引

### 如果用户问“某页面的数据从哪来”
1. 先看 `01`
2. 再看对应 page.tsx
3. 若页面是客户端壳层，再看对应 route

### 如果用户问“某接口会写哪些表”
1. 先看 `02`
2. 再看 route 调到哪个 server.ts
3. 再看 `03`

### 如果用户问“某表是谁在写”
1. 先看 `03`
2. 再 grep 对应表对象在 `frontend/src/lib/**`、`frontend/src/app/api/**` 中的使用

### 如果用户问“BP Ask 为什么没记住”
1. 看 `04`
2. 看 `bp-ask/server.ts`
3. 看 `memory_facts` 是否有写入路径
4. 看 `0003/0004` 是否已执行

## 5. 推荐问答姿势

以后你问我问题时，如果是开发定位类问题，我会优先这样回答：

- 这是哪个业务域
- 先看哪篇文档
- 关键文件是哪些
- 关键表/API 是哪些
- 如果要改，应该从哪一层入手
- 怎么验证改动是否真的打通

这样可以把回答时间压缩到最短，而不是再全盘扫描。
