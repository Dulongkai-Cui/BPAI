## 1. 第一性原理

工作协议网关的目标不是做一个传统工作流编辑器，而是做一个普通人也能使用的“工作方式搭建器”：

```text
用户只需要选部门、选龙虾、摆方块、拉线、用自然语言写想让它干什么。
系统负责把这些松散表达梳理成可校验、可试运行、可执行的工作协议。
```

因此，工作协议网关必须分成两层：

```text
自由表达层：用户画图、写话、描述意图
协议编译层：系统理解、改写、补参、校验、标错、生成执行协议
```

这意味着用户可以“瞎搭”，但系统不能“瞎跑”。能理解的部分要被梳理成标准协议；不能理解或不能执行的部分要被明确标红，并给出修改建议。

## 2. 核心产品心智

用户不应该感觉自己在配置复杂 schema，而应该感觉自己在安排一个办公室如何干活：

```text
选一个工作部门
-> 放一个或多个龙虾 / AI员工
-> 在每个方块下写“您想让它干什么”
-> 在线上写“想把什么传给下一个节点”
-> 点击“协议梳理”
-> 系统把整张图变成可运行的工作协议
```

画布上最重要的对象有三个：

1. 方块：谁来做什么。
2. 连线：什么信息从一个方块传给下一个方块。
3. 部门大方块：资源、权限、上下文和可见龙虾的沙箱边界。

## 3. 部门大方块

部门不是传统组织架构，而是工作沙箱。它可以很大，也可以很细。

示例：

- 某个工单页面。
- 某个合作空间。
- 某个文档空间。
- 某个文档文件夹。
- 某个项目资料包。
- 某个系统表单集合。

部门大方块要承担四件事：

1. 限定资源范围：这个协议能看见哪些工单、文档、文件夹、合作空间。
2. 限定执行者：这个部门里能使用哪些龙虾 / AI员工。
3. 限定工具：这个部门允许调用哪些 Tool / Skill。
4. 限定写回边界：哪些动作必须人工确认，哪些动作禁止写回。

建议的部门结构：

```ts
type WorkDepartment = {
  id: string;
  name: string;
  scopeType:
    | "document_folder"
    | "document_space"
    | "work_order_board"
    | "collaboration_space"
    | "system_form"
    | "project"
    | "custom";
  resourceRefs: Array<{
    kind: string;
    id: string;
    name: string;
  }>;
  visibleAgentIds: string[];
  allowedSkillIds: string[];
  allowedToolNames: string[];
  defaultConfirmationPolicy:
    | "none"
    | "before_write"
    | "before_external_action"
    | "always";
};
```

龙虾 / AI员工配置中应增加“可见工作部门”：

```ts
type AgentDepartmentVisibility = {
  agentId: string;
  visibleDepartmentIds: string[];
};
```

运行时含义：

```text
龙虾只能看到自己可见部门里的资源。
龙虾只能调用该部门允许的 Tool / Skill。
龙虾只能把结果写回该部门允许的出口。
```

## 4. 方块设计

第一版不需要很多复杂按钮。每个小方块最重要的是一个自然语言输入栏：

```text
您想让它干什么？
```

例如：

```text
读取这个工单，把当前状态、风险、下一步整理出来。
检查这个文件夹里缺哪些归档材料。
把上一个节点的风险点整理成给项目负责人的确认清单。
```

画布草稿中的节点可以非常轻：

```ts
type WorkProtocolCanvasNodeDraft = {
  id: string;
  kindHint?: "bp_ask_entry" | "department" | "agent" | "skill" | "tool" | "human_gate" | "output";
  departmentId?: string;
  agentId?: string;
  skillId?: string;
  toolName?: string;
  userIntent: string;
  position: {
    x: number;
    y: number;
  };
};
```

点击“协议梳理”后，系统将其编译成更严格的节点：

```ts
type CompiledWorkProtocolNode = {
  id: string;
  nodeKind:
    | "input"
    | "department"
    | "longxia"
    | "skill"
    | "tool"
    | "condition"
    | "human_gate"
    | "writeback"
    | "output";
  executorId?: string;
  actionName?: string;
  requiredParams: string[];
  resolvedParams: Record<string, unknown>;
  outputFields: string[];
  confirmationPolicy: "none" | "before_write" | "before_external_action" | "always";
  riskLevel: "low" | "medium" | "high";
};
```

梳理后，节点下方可以出现参数下拉框和字段选择器。用户不是一开始就填这些参数，而是在系统梳理完成后微调。

## 5. 连线设计

连线也不应该只是箭头。连线代表信息流。

每条线可以有一个可展开输入栏：

```text
想把什么传给下一个节点？
```

示例：

```text
把工单摘要、风险点和下一步建议传过去。
只把缺失材料清单传给人工确认。
把上一个节点整理出的写回草案传给结果回执。
```

草稿结构：

```ts
type WorkProtocolCanvasEdgeDraft = {
  id: string;
  fromNodeId: string;
  toNodeId: string;
  transferIntent: string;
};
```

梳理后的结构：

```ts
type CompiledWorkProtocolEdge = {
  id: string;
  fromNodeId: string;
  toNodeId: string;
  mapping: Array<{
    fromField: string;
    toField: string;
    transform?: string;
  }>;
  missingFields: string[];
};
```

如果连线里写的内容无法从上游节点产出，或者下游节点不接受该字段，这条线应该标红。

## 6. 协议梳理按钮

工作协议网关的关键按钮叫：

```text
协议梳理
```

它不是简单保存，而是一次“自然语言画布 -> 标准协议”的编译过程。

推荐链路：

```text
收集画布草稿
-> 读取部门、龙虾、Skill、Tool Registry
-> 大模型理解节点意图和连线意图
-> 生成标准协议草案
-> 后端 schema 校验
-> 权限和对象存在性校验
-> 信息流校验
-> 尝试自动修复低风险问题
-> 返回编译结果、问题列表、节点/连线标注
```

重要原则：

```text
模型负责理解和改写。
后端负责校验和兜底。
UI 负责把问题定位回具体方块和连线。
```

模型输出不能直接作为可执行协议使用，必须经过确定性校验。

## 7. 不能梳理时的兜底

不是每个用户写出来的内容都能被系统梳理成协议。工作协议网关必须把“不能做”做成一等状态，而不是假装成功。

典型失败场景：

| 类型 | 例子 | UI 表现 |
| --- | --- | --- |
| 无可解析意图 | 方块里写的是完全无关或无法理解的句子 | 方块标红 |
| 对象不存在 | 用户提到某个文件夹、工单、部门，但系统找不到 | 方块标红 |
| 龙虾不可见 | 用户把某个龙虾放进它不可见的部门 | 方块标红 |
| Skill 不存在 | 用户提到的 Skill 不在 AI生产资料仓 | 方块标红 |
| Tool 不允许 | 节点需要调用某工具，但部门未授权 | 方块标红或警告 |
| 上游无字段 | 连线要求传“结算金额”，但上游节点不会产出 | 连线标红 |
| 下游不接收 | 连线传了字段，但下游节点 schema 不接受 | 连线标红 |
| 信息不足 | 能理解意图，但缺关键参数 | 方块黄标，提示补参 |
| 写回高风险 | 节点涉及写工单、改文档、外部执行 | 自动建议插入人工确认 |
| 模型不确定 | 模型给出多个解释且置信度低 | 方块黄标，要求用户选择 |

右下角应该有一个“协议问题”浮层，汇总所有问题。

示例：

```text
协议梳理未通过：3 个问题

1. 工单龙虾不可用于“文档归档部门”
   建议：切换为文档龙虾，或把该节点移动到工单部门。

2. 连线 E2 要传递“验收金额”，但上游“文档检查节点”不会产出该字段。
   建议：改为传递“缺失材料清单”，或在上游增加金额读取节点。

3. 节点 N4 提到“合同复核 Skill”，但 AI生产资料仓没有这个 Skill。
   建议：从 AI生产资料仓选择现有 Skill，或先创建该 Skill。
```

## 8. 编译结果结构

协议梳理 API 应返回完整编译状态，而不是只返回成功 / 失败。

```ts
type WorkProtocolCompileResult = {
  status: "valid" | "valid_with_warnings" | "invalid";
  protocolDraft?: CompiledWorkProtocolDefinition;
  issues: WorkProtocolIssue[];
  annotations: WorkProtocolCanvasAnnotation[];
  autoFixes: WorkProtocolAutoFix[];
};
```

问题结构：

```ts
type WorkProtocolIssue = {
  id: string;
  severity: "error" | "warning" | "info";
  targetKind: "node" | "edge" | "canvas" | "department";
  targetId?: string;
  code:
    | "UNREADABLE_INTENT"
    | "OBJECT_NOT_FOUND"
    | "AGENT_NOT_VISIBLE_IN_DEPARTMENT"
    | "SKILL_NOT_FOUND"
    | "TOOL_NOT_ALLOWED"
    | "UPSTREAM_FIELD_NOT_AVAILABLE"
    | "DOWNSTREAM_FIELD_NOT_ACCEPTED"
    | "MISSING_REQUIRED_PARAM"
    | "REQUIRES_HUMAN_GATE"
    | "MODEL_LOW_CONFIDENCE"
    | "SCHEMA_INVALID";
  message: string;
  suggestion: string;
  canAutoFix: boolean;
};
```

画布标注结构：

```ts
type WorkProtocolCanvasAnnotation = {
  targetKind: "node" | "edge" | "canvas" | "department";
  targetId?: string;
  visualState: "normal" | "valid" | "warning" | "error";
  issueIds: string[];
};
```

## 9. 右下角问题浮层

右下角浮层是协议梳理的关键反馈区。

它应该显示：

- 总状态：通过 / 有警告 / 未通过。
- 错误数量、警告数量。
- 每个问题关联到哪个方块或哪条线。
- 可点击定位到画布对象。
- 给出明确解决建议。
- 对可自动修复项提供“应用修复”按钮。

交互建议：

```text
点击问题 -> 画布定位到对应方块 / 连线
悬停红色方块 -> 显示该方块问题摘要
点击“应用修复” -> 自动插入人工确认 / 修改字段映射 / 补默认参数
```

第一版可以先只做定位和建议，不必做自动修复。

## 10. 前端优先的落地顺序

这件事建议从前端推后端，但前端不能只做静态好看。第一版前端要把未来后端契约预留出来。

### Phase A：静态交互骨架

目标：

- 工作协议网关页面改造成新心智模型。
- 有部门大方块。
- 有小方块自然语言输入栏。
- 有连线自然语言输入栏。
- 有“协议梳理”按钮。
- 有右下角问题浮层。
- 有节点 / 连线的红黄状态。

这一阶段可以用前端 mock compile result。

### Phase B：协议梳理 API dry-run

目标：

- 新增 `/api/work-protocols/compile`。
- 输入 canvas draft。
- 读取 Tool Registry、Skill 蓝图、Agent 蓝图、部门 mock。
- 返回 `WorkProtocolCompileResult`。
- 先允许 deterministic mock，不急着接真实模型。

### Phase C：接入大模型梳理

目标：

- 大模型只负责从自然语言画布生成协议草案。
- 后端 schema 校验负责判断是否可用。
- 对模型输出做 repair loop，但最多有限次数。
- repair 失败则返回 `invalid`，不进入执行。

### Phase D：协议持久化和试运行

目标：

- 保存协议 definition。
- 支持试运行。
- 试运行先 dry-run，不默认真实写回。
- 输出执行轨迹、节点产物和问题。

### Phase E：接入真实 BP问问和 Longxia 闭环

目标：

- BP问问可以命中某个工作协议。
- 工作协议网关创建 protocol run。
- Longxia 节点执行 dry-run / 后续真实执行。
- 结果回流 BP问问继续解释。

## 11. 第一版 MVP 范围

建议第一版只支持这些对象：

部门：

- 工单部门。
- 文档空间部门。
- 文档文件夹部门。

节点：

- BP问问入口。
- 部门。
- 龙虾 / AI员工。
- Skill。
- 人工确认。
- 结果回执。

连线：

- 自然语言 `transferIntent`。
- 梳理后生成字段映射。
- 无法传递时标红。

协议梳理：

- 可以先做 mock 模型结果。
- 必须有确定性校验。
- 必须返回问题列表和画布标注。

暂不做：

- 任意外部工具真实执行。
- 完整拖拽低代码编辑器。
- 自动创建不存在的 Skill。
- 完全自动修复所有错误。
- 保证所有用户乱写内容都能跑通。

## 12. 和 BP问问 / 龙虾的关系

BP问问仍然是唯一前台入口。工作协议网关不是新的聊天入口，而是定义 BP问问如何把复杂任务交给后场。

推荐关系：

```text
用户自然语言
-> BP问问理解目标和缺参
-> 命中某个工作协议
-> 工作协议网关按协议编排部门、龙虾、Skill、人工确认
-> 龙虾产出结构化结果
-> 工作协议网关校验和收束结果
-> BP问问把结果解释给用户
```

龙虾不是无边界执行体。龙虾必须被部门沙箱约束：

```text
可见部门决定它能看什么。
部门工具白名单决定它能调用什么。
确认策略决定它什么时候必须停下来等人。
```

## 14. 画布状态机

前端需要把协议梳理后的状态清楚表达出来，避免用户以为“画了就能跑”。

建议状态：

```ts
type WorkProtocolCanvasCompileState =
  | "draft"
  | "compiling"
  | "valid"
  | "valid_with_warnings"
  | "invalid"
  | "dirty_after_compile";
```

含义：

| 状态 | 含义 | UI 表现 |
| --- | --- | --- |
| `draft` | 用户正在搭建，还没梳理 | “协议梳理”主按钮可用 |
| `compiling` | 正在调用梳理逻辑 | 按钮 loading，画布暂不提交新梳理 |
| `valid` | 协议可试运行 | 显示通过，可开启“试运行” |
| `valid_with_warnings` | 协议可试运行，但有风险或建议 | 显示黄标，试运行可用但需用户看提示 |
| `invalid` | 协议不可试运行 | 红色问题浮层，试运行禁用 |
| `dirty_after_compile` | 用户在梳理后又改了画布 | 提示“画布已变更，需要重新梳理” |

只要用户修改节点文字、部门、龙虾、Skill、连线文字或连接关系，就应该从 `valid / invalid / valid_with_warnings` 进入 `dirty_after_compile`。

## 15. 协议梳理 API 请求形状

第一版即使先 mock，也应该按真实 API 形状设计前端状态。

建议请求：

```ts
type WorkProtocolCompileRequest = {
  protocolId?: string;
  canvasDraft: {
    title: string;
    description?: string;
    nodes: WorkProtocolCanvasNodeDraft[];
    edges: WorkProtocolCanvasEdgeDraft[];
  };
  context: {
    userId: string;
    workspaceId?: string;
    source: "ai_dorm_work_protocol_gateway";
  };
};
```

后端不要要求前端传完整 registry。前端只传用户画布，后端自己读取：

- 部门列表。
- Agent / 龙虾列表。
- AI生产资料仓。
- Tool Registry。
- 当前用户权限。

这样可以避免前端拿旧 registry 编译出错误协议。

## 16. 确定性校验顺序

大模型生成协议草案后，后端校验顺序建议固定，便于 debug：

```text
1. JSON schema 校验
2. 节点 / 连线引用完整性校验
3. 部门存在性校验
4. Agent / 龙虾存在性校验
5. Agent 可见部门校验
6. Skill 存在性校验
7. Tool 存在性与部门授权校验
8. 节点输入必填参数校验
9. 连线上游输出字段校验
10. 连线下游输入字段校验
11. 写回 / 外部执行风险校验
12. 可自动修复项生成
```

校验失败不应该直接丢弃模型草案，而应该尽量返回可定位的 `issues` 和 `annotations`。只有 schema 完全不可读时，才返回画布级 `SCHEMA_INVALID`。

## 17. 第一版验收用例

前端 mock 阶段至少要覆盖这些用例。

### 17.1 可梳理成功

```text
部门：工单部门
龙虾：工单龙虾
节点意图：读取这个工单，把状态、风险和下一步整理出来
连线意图：把摘要、风险点、下一步传给结果回执
```

期望：

- 状态为 `valid`。
- 节点显示绿色或正常。
- 右下角问题浮层显示“无阻塞问题”。
- 试运行按钮可用。

### 17.2 Skill 不存在

```text
节点意图：调用合同复核 Skill 检查这个文件夹
```

但 AI生产资料仓没有“合同复核 Skill”。

期望：

- 相关节点标红。
- issue code 为 `SKILL_NOT_FOUND`。
- 右下角建议用户从 AI生产资料仓选择现有 Skill，或先创建该 Skill。

### 17.3 龙虾不在可见部门

```text
部门：文档文件夹部门
龙虾：工单龙虾
节点意图：检查这个文件夹里的归档材料
```

期望：

- 龙虾节点或部门内该龙虾标红。
- issue code 为 `AGENT_NOT_VISIBLE_IN_DEPARTMENT`。
- 建议切换为文档龙虾，或调整龙虾的可见工作部门。

### 17.4 连线传不了

```text
上游节点：检查文件夹缺失材料
连线意图：把验收金额传给下游
```

但上游不会产出“验收金额”。

期望：

- 连线标红。
- issue code 为 `UPSTREAM_FIELD_NOT_AVAILABLE`。
- 建议改传“缺失材料清单”，或增加金额读取节点。

### 17.5 高风险写回

```text
节点意图：把工单状态改成已完成，并通知项目负责人
```

期望：

- 状态为 `valid_with_warnings` 或自动建议插入人工确认。
- issue code 为 `REQUIRES_HUMAN_GATE`。
- 右下角提示“写回动作需要人工确认”。

### 17.6 完全不可理解

```text
节点意图：蓝色的星期三把月亮塞进预算里
```

期望：

- 节点标红。
- issue code 为 `UNREADABLE_INTENT` 或 `MODEL_LOW_CONFIDENCE`。
- 不生成可试运行协议。
