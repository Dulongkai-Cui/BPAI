## 3. 环境变量

来自 `frontend/.env.local.example`：

```text
NEXT_PUBLIC_APP_NAME=BPAI
NEXT_PUBLIC_API_BASE_URL=http://localhost:8000
DATABASE_URL=postgresql://bpai:bpai@localhost:5433/bpai_dev
BPASK_MODEL_PROVIDER=deepseek
DEEPSEEK_API_KEY=your-deepseek-api-key
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-v4-pro
KIMI_API_KEY=your-kimi-api-key
KIMI_BASE_URL=https://api.moonshot.cn/v1
KIMI_MODEL=kimi-k2.5
```

### 3.1 关键说明
- `NEXT_PUBLIC_*` 会暴露到浏览器
- `DATABASE_URL` 是 server-only
- `DEEPSEEK_API_KEY` 与 `KIMI_API_KEY` 是 server-only
- `BPASK_MODEL_PROVIDER` 控制当前 BP Ask 使用 `deepseek` 还是 `kimi`
- `DEEPSEEK_MODEL` / `KIMI_MODEL` 控制 BP Ask 聊天与分类共用的模型名；当前 DeepSeek 默认模型为 `deepseek-v4-pro`
- BP Ask 当前通过兼容 OpenAI 的 `/chat/completions` 接口调用模型 provider
- AI宿舍 / 龙虾 / OpenClaw 的模型配置不受 `BPASK_MODEL_PROVIDER` 影响，仍由 `docker/openclaw/shared/agents/main/agent/models.json` 与 `MOONSHOT_API_KEY` 管理
- 如果将来接入 Claude/OpenAI 等，必须避免放入 `NEXT_PUBLIC_*`

### 3.2 代码中可见的其他默认 env 依赖

在 `frontend/src/lib/auth/server.ts`：
- `BPAI_SESSION_SECRET`

## 4. 数据库基础设施

### 4.1 连接方式

- 文件：`frontend/src/lib/db/client.ts`
- 方式：`pg.Pool` + `drizzle()`
- 当前实现：全局单例 pool `globalThis.__bpaiPgPool`

```text
getDb()
-> drizzle(getPool())
-> connectionString = process.env.DATABASE_URL ?? defaultDatabaseUrl
```

### 4.2 风险点
- 本地默认库地址直接写在代码里，生产环境必须显式覆盖 `DATABASE_URL`
- 数据层与部分 raw shadow / app-store 仍并存，不能假设所有业务都只写 Postgres

## 5. 认证与会话基础设施

### 5.1 Cookie

- Cookie 名：`bpai_session`
- 定义位置：`frontend/src/lib/auth/server.ts`

### 5.2 密码机制

- `pbkdf2Sync`
- 迭代次数：`120000`
- digest：`sha256`

### 5.3 会话机制

```text
登录
-> authenticateUser
-> 生成 session token
-> mirrorSessionToPostgres
-> raw shadow 同步
-> 下发 bpai_session cookie
```

## 6. 内容存储基础设施

### 6.1 本地文件存储

在 `frontend/src/lib/content/server.ts`：

- 存储根目录：`process.cwd()/.bpai/storage`
- OnlyOffice 样例目录：`process.cwd()/public/onlyoffice`

### 6.2 上传链路

```text
createUploadedAsset
-> buildStoredAsset
-> mkdir(path.dirname(absolutePath))
-> writeFile(absolutePath, buffer)
-> mirrorAssetToPostgres
-> raw shadow 同步
```

### 6.3 资产访问路径
- 编辑打开页：`/docs/documents/{assetId}`
- 内容流：`/api/assets/{kind}/{assetId}/content`

### 6.4 风险点
- 当前真实文件存储不是对象存储，而是本地磁盘目录 `.bpai/storage`
- 若部署为多实例或容器重建，必须考虑持久卷/共享存储

## 7. OnlyOffice 集成

### 7.1 文档页集成点
- `frontend/src/app/docs/documents/[docId]/page.tsx`
- `frontend/src/components/onlyoffice/*editor*`
- `frontend/src/lib/content/server.ts`

### 7.2 回调入口
- `frontend/src/app/api/onlyoffice/callback/route.ts`

### 7.3 回调流程

```text
OnlyOffice 回调 payload { key, status, url }
-> rewriteDownloadUrl(必要时把 localhost 改成 ONLYOFFICE_INTERNAL_BASE_URL)
-> fetch(downloadUrl)
-> parseOnlyOfficeAssetKey
-> overwriteAssetBinary
```

### 7.4 legacy 兼容
若 `key` 不是新资产 key，则会走 legacy 路径，把文件写回：
- `public/onlyoffice/*.docx/xlsx/...`

### 7.5 风险点
- OnlyOffice callback 既承担新架构资产回写，也承担 legacy 文件兼容
- 改这块时要区分“正式资产流”与“样例/旧文件流”

## 10. raw shadow / app-store 过渡层

当前项目并非所有业务都直接只写 Postgres。

相关文件：
- `frontend/src/lib/store/raw-shadow.ts`
- `frontend/src/lib/db/app-store-read.ts`
- `frontend/src/lib/db/app-store-write.ts`
- `frontend/src/lib/auth/server.ts`
- `frontend/src/lib/workspace/server.ts`
- `frontend/src/lib/content/server.ts`

### 10.1 它的作用
- 让旧的 app-store / raw store 结构继续可用
- 同时把关键对象镜像到 Postgres
- 作为迁移过渡层

### 10.2 影响范围
- 会话
- 资产
- 合作空间
- 工作区相关状态

### 10.3 风险点
- 改写业务逻辑时，如果只改了 Postgres 或只改了 raw shadow，可能导致读写链不一致
- workspace 相关能力目前尤其需要重点检查这一层

## 12. 基础设施视角下的高风险改动区

| 区域 | 风险来源 | 改动前必查 |
| --- | --- | --- |
| `auth/server.ts` | 登录、session、种子账号、cookie、镜像写入都在这里 | 全链路验证登录与 session |
| `content/server.ts` | 文件上传、落盘、OnlyOffice key、asset mirror 都耦合 | 上传/下载/编辑回写全测 |
| `onlyoffice/callback/route.ts` | 新旧回写路径并存 | 验证 asset key 与 legacy key |
| `db/client.ts` | 所有 DB 连接入口 | 确认 env 与连接地址 |
| `raw-shadow.ts` / `app-store-*` | 迁移过渡层，容易漏同步 | 查读写双方 |
| env 变量 | 公开/私密变量混淆会泄漏密钥 | 审核变量命名 |

## 12. BP Ask / 模型运行事实

当前 BP Ask 的模型接入分为两层：

- `classifyWithModel`：结构化 dispatch 分类增强
- `generateChatReplyWithModel`：普通聊天自然回复

两者都位于：
- `frontend/src/lib/bp-ask/model-provider.ts`

当前普通聊天 prompt 已固定 BPAI / BP问问 身份，不应再被描述为通用 AI 助手。

当前模型分工：
- BP问问“大总管”：`BPASK_MODEL_PROVIDER=deepseek` + `DEEPSEEK_MODEL=deepseek-v4-pro`
- AI宿舍 / 龙虾员工：OpenClaw 侧继续使用 `moonshot` provider 的 `kimi-k2.5`

Docker 运行事实：
- 开发前端服务：`frontend-dev`
- 容器名：`bpai-front-dev`
- 暴露端口：`3001 -> 3000`

在当前项目里，前端改动后若浏览器仍看到旧状态，优先：
1. 强制刷新浏览器
2. 如仍异常，重启 `frontend-dev` 容器
3. 再跑 BP Ask smoke

## 14. 本地启动与最小排障顺序

### 14.1 最小启动顺序
1. 准备 `frontend/.env.local`，至少包含：
   - `DATABASE_URL`
   - `BPAI_SESSION_SECRET`
   - 可选 `DEEPSEEK_API_KEY` 或 `KIMI_API_KEY`
2. 确认 Postgres 可访问
3. 在 `frontend/` 下执行依赖安装
4. 如 schema 有变更，先跑数据库迁移
5. 启动 Next.js 开发服务
6. 如需文档在线编辑，再确认 OnlyOffice 服务与回调地址可通

### 14.2 各类问题的第一定位点
- 启动报错：先看 `package.json` scripts、env、DB 连接
- 登录失败：先看 `/api/auth/login` 与 `auth/server.ts`
- 上传失败：先看 `/api/assets/upload` 与 `.bpai/storage`
- 文档回写失败：先看 `/api/onlyoffice/callback`
- BP Ask 无响应：先看 `/api/bp-ask/threads/[threadId]/messages`、`bp-ask/server.ts`、`dispatch.ts`
- 工单保存失败：先看 `/api/work-orders`、`work-order/server.ts`

## 16. 运维/排障提醒

- `NEXT_PUBLIC_API_BASE_URL` 是浏览器可见变量，不可放密钥
- `DATABASE_URL`、`DEEPSEEK_API_KEY` 与 `KIMI_API_KEY` 必须保持 server-only
- 若上传成功但页面不显示，除查 Postgres 外，还要查 raw shadow / app-store mirror
- 若 OnlyOffice 能打开但不能回写，优先检查：
  - `NEXT_PUBLIC_ONLYOFFICE_FILE_BASE_URL`
  - `ONLYOFFICE_INTERNAL_BASE_URL`
  - asset key 是否符合 `bpai-asset-{kind}-{assetId}`
- 若 BP Ask 页面能发请求但没有持久化，优先检查：
  - `conversation_*`
  - `memory_facts`
  - `execution_*`
  - 以及对应 migration 是否已执行
