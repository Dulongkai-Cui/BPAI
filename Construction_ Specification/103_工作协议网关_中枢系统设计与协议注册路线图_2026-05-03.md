## 0. 核心结论

工作协议网关不应该只被理解成一个画布，也不应该被理解成一条固定管道。

它最合理的工程定位是：

```text
工作协议网关 = 可注册、可启停、可匹配、可编译、可执行、可审计的任务编排层
```

对 BP问问 来说，它应该表现为一组“高阶工具”：

```text
用户自然语言任务
-> BP问问判断是否是任务
-> 查询已启用工作协议
-> 匹配协议触发条件
-> 执行协议
-> 通过 BP问问汇报出口回到 BP问问
-> BP问问用自然语言回复用户
```

部门不是普通节点。部门是资源沙箱和权限边界。

方块不是最终协议。方块是用户可编辑的自然语言草稿。

协议梳理不是保存按钮。协议梳理是“自然语言画布 -> 可执行协议”的编译器。

AI生产资料仓不是单纯 Skill 列表。它应成为模型 Key、Skill 包、RAG、记忆目录、内置蓝图和后续运行时资产的统一生产资料中心。

## 1. 当前现状

### 1.1 BP问问当前状态

当前 BP问问已经具备基础 Tool Calling 主链，不能再按“纯聊天 Demo”看待。

已具备能力：

- 普通自然语言对话入口仍可用。
- 当用户表达明确任务意图时，系统可以进入 task mode。
- 工单和文档基础能力已经能通过 Tool Gateway 调用。
- 缺参时可以追问。
- 搜索出现多个候选时可以要求用户选择。
- 用户补充候选、工单号、文档 ID、写入内容后，可以继续执行后续 step。
- 工单和文档基础工具已通过 Docker smoke 验证。

当前 Tool Gateway 已有 capability descriptor：

- `domain`
- `action`
- `riskLevel`
- `executionMode`
- `inputSchema`
- `outputSchema`
- `requiredContext`
- `plannerHints`
- `failureModes`
- `requiresConfirmationDefault`

这说明系统已经有“工具注册表”的雏形。工作协议网关后续应复用这个思路，把“协议”也注册成 BP问问可选择的高阶能力。

仍然不足：

- 表格 `.xlsx` 精细编辑尚未完成，当前不能可靠改单元格、追加行、按行查询后写入。
- Longxia fallback 有 handoff 方向，但还没有生产级闭环。
- BP问问对复杂任务的规划仍依赖模型可用性。
- 模型规划失败时的 deterministic fallback 还不够丰富。
- Tool 调用结果、协议执行状态、Longxia 结果回流还没有统一 runtime packet。

### 1.2 龙虾当前状态

当前龙虾已经具备产品心智和部分技术入口，但还不能算完整执行层。

已有基础：

- AI宿舍页面里已经有 AI员工 / 龙虾 的概念。
- 已有 Longxia adapter、handoff payload、`ready_to_delegate` 等方向。
- OpenClaw state 目录已经存在，具备后续把龙虾状态和记忆落盘的路径。
- 工作协议网关的部门沙箱里已经可以选择可见 AI员工。
- AI记忆主脑里已经做出龙虾记忆入口列表和单只龙虾记忆页原型。

当前缺口：

- 龙虾还不是协议 runtime 中的稳定 executor。
- 龙虾接到任务后的多轮追问、状态推进、结果回传没有统一协议。
- 龙虾可见部门、可见 Skill 文件夹、可见记忆目录还没有后端强制权限。
- 龙虾产物如何进入 `execution_results`、如何回到 BP问问回复用户，还需要统一链路。

### 1.3 工作协议网关当前前端状态

当前前端“皮相”已经基本够用，主要包括：

- 页面已改名为“工作协议网关”。
- 画布支持固定页面、中间画布拖动、缩放、方块拖动。
- 部门是独立大方块，不再只是普通节点。
- 部门可选择大部门和具体范围。
- 文档档案室支持“全部 / 我的文档空间 / 合作空间”的分层范围选择方向。
- 部门内可见 AI员工可被点击加入部门。
- 部门可以收缩 / 展开，并展示大部门和范围摘要。
- 部门和方块均支持删除。
- 普通方块有连接点、填写框和删除按钮。
- 连线有默认传输提示词，未来可展开编辑。
- “协议梳理”目前仍是 mock compile，但已经有右下角问题面板、节点 / 连线标红方向。

当前可添加的普通方块已经收敛为协议语义块：

- `BP问问入口`
- `Tool调用`
- `Skill调用`
- `RAG检索`
- `任务分派`
- `结果汇总`
- `条件判断`
- `人工确认`
- `BP问问追问`
- `写入对象`
- `BP问问汇报出口`

重要约束：

- `AI员工` 不应从“添加方块”直接添加。
- `AI员工` 应从部门沙箱中选择并放入部门。
- 部门负责“谁能看什么、谁能用什么、谁能写哪里”。
- 普通方块负责“任务如何流转”。

### 1.4 AI生产资料仓当前状态

AI生产资料仓已经从原 Skill 仓库扩展为更大的生产资料中心原型。

当前前端方向包括：

- API Key 中心：DeepSeek、Kimi 等模型访问配置。
- Skill 工厂：命令安装、Zip 导入、本地包快照。
- 本地 Skill 包管理：类似文档档案室的文件夹区域，支持未来把 Skill 包拖入文件夹。
- 内置 Skill 蓝图：系统预设能力的展示。
- RAG 工厂：知识库、索引、检索测试台原型。
- AI记忆主脑：BP问问脑区入口、龙虾记忆入口、做梦模块。

当前关键设计判断：

- Skill 权限不应直接在本地包管理页绑定某只龙虾。
- 本地包管理只负责下载、上传、建文件夹、归档 Skill 包。
- 龙虾配置页未来再按文件夹开放 Skill 可见范围。
- 同一 Skill 文件夹可以授权给多只龙虾复用。
- 这能减少每只龙虾扫描全部 Skill 的上下文成本。

### 1.5 当前系统还不是中枢的原因

当前“看起来像中枢”，但底层还没有中枢。

缺少的核心部件：

- 工作协议 JSON Schema。
- 协议草稿保存和版本管理。
- 协议编译结果结构。
- 协议注册表。
- 协议启用 / 停用开关。
- BP问问协议路由器。
- 运行时 DAG executor。
- 统一 context packet。
- 部门权限 runtime enforcement。
- 协议执行日志和审计。
- 协议测试和 dry-run。

因此下一步重点不是继续堆 UI，而是定义并实现底层协议系统。

## 2. 理想状态定义

### 2.1 BP问问的理想状态

BP问问应该保持自然对话体验：

```text
平常聊天没有负担。
用户说任务时，BP问问能主动打起精神。
BP问问能判断缺什么信息。
BP问问能追问。
信息齐全后，BP问问能选择工具、协议或龙虾执行。
执行结果回到 BP问问，由 BP问问整理成人话回复用户。
```

BP问问不应该直接硬编码所有复杂流程。它应该有三类能力选择：

1. 直接 Tool Calling。
2. 已注册工作协议。
3. Longxia fallback / AI员工任务下发。

推荐优先级：

```text
普通聊天
-> 任务识别
-> 是否有已启用协议匹配
-> 若匹配，走工作协议网关
-> 若不匹配但工具足够，走 Tool Calling
-> 若工具不足或任务需要外部 AI员工，走 Longxia / AI员工
-> 结果统一回 BP问问
```

### 2.2 龙虾的理想状态

龙虾应该是部门沙箱内的专业执行者。

每只龙虾需要具备：

- 可见部门范围。
- 可见资源范围。
- 可见 Skill 文件夹。
- 可见记忆目录。
- 输入 schema。
- 输出 schema。
- 可执行任务类型。
- 是否允许写入。
- 失败回报协议。

龙虾不应自己决定越权看资源。运行时应该只把授权范围内的上下文注入给它。

### 2.3 工作协议网关的理想状态

工作协议网关应该是“自然语言协议 IDE”。

它包含两层：

```text
用户表达层：方块、部门、连线、自然语言填写框
执行协议层：参数代码、schema、权限、输入输出、触发规则、运行状态
```

用户看到的是：

- 选部门。
- 选可见 AI员工。
- 添加方块。
- 拉线。
- 写“您想让它干什么”。
- 写“想传什么给下一个节点”。
- 点“协议梳理”。

系统生成的是：

- `compiledNodeSpec`
- `compiledEdgeSpec`
- `triggerRules`
- `requiredInputs`
- `outputs`
- `permissions`
- `approvalPolicy`
- `runtimePlan`
- `issues`

协议梳理后，每个节点和连线都应该有“参数代码下拉框”：

```text
原始文本保留，方便用户继续修改。
参数代码折叠展示，方便用户和开发者看到系统理解结果。
原始文本被修改后，参数代码标记为 stale。
重新协议梳理后，参数代码更新。
```

### 2.4 AI生产资料仓的理想状态

AI生产资料仓应该提供所有协议生成和执行所需的生产资料。

它至少包括：

- API Key / 模型配置。
- Skill 包市场和本地 Skill 文件夹。
- 内置 Skill 蓝图。
- RAG 知识库和检索测试。
- BP问问记忆和身份 Prompt。
- 龙虾记忆文件夹入口。
- 后续可扩展的工具目录、模板目录、协议模板目录。

它和工作协议网关的关系：

```text
AI生产资料仓提供能力资产。
工作协议网关引用能力资产。
协议梳理读取能力资产目录，生成受约束的可执行协议。
运行时按协议引用能力资产。
```

## 3. 中枢系统总体架构

### 3.1 五层架构

推荐拆成五层：

```text
1. Capability Catalog 能力目录层
2. Protocol Draft 协议草稿层
3. Protocol Compiler 协议梳理层
4. Protocol Registry 协议注册层
5. Protocol Runtime 协议执行层
```

每层职责如下：

| 层级 | 主要职责 | 是否需要模型 |
| --- | --- | --- |
| Capability Catalog | 注册部门、方块、Tool、Skill、RAG、龙虾、写入对象能力 | 否 |
| Protocol Draft | 保存画布草稿、用户原文、节点位置、连线原文 | 否 |
| Protocol Compiler | 把自然语言草稿梳理成参数代码和执行协议 | 是 |
| Protocol Registry | 保存已编译版本、触发规则、启停状态、版本 | 否 |
| Protocol Runtime | 执行 DAG、调用工具、分派龙虾、等待确认、返回结果 | 部分需要 |

### 3.2 核心数据流

```text
前端画布草稿
-> 保存 Protocol Draft
-> 点击协议梳理
-> 加载 Capability Catalog
-> LLM 生成 compiledSpec 草案
-> 确定性校验器校验
-> 返回参数代码、问题、自动修复建议
-> 用户确认并注册协议版本
-> BP问问查询已启用协议
-> 匹配触发规则
-> Protocol Runtime 执行
-> BP问问汇报出口返回结果
```

### 3.3 为什么不能只靠 LLM

协议梳理必须分成两段：

```text
LLM 负责理解和改写。
确定性校验器负责合法性、权限、字段、对象存在性和风险策略。
```

只靠 LLM 的问题：

- 它可能编造不存在的 Tool。
- 它可能假设 Skill 存在。
- 它可能忽略部门权限。
- 它可能让写入动作绕过人工确认。
- 它可能把上游没有的字段传给下游。

只靠规则的問題：

- 读不懂用户自然语言。
- 很难处理“帮我让预警龙虾看看这件事有没有风险”这种模糊表达。

因此必须是：

```text
受约束的 LLM 生成 + 后端确定性校验
```

第一步不是直接做协议生成，而是先整理“每类对象到底有哪些可动参数”。

## 5. 协议草稿与参数代码

### 5.1 草稿结构

画布保存的是草稿，不是最终执行协议。

```ts
type WorkProtocolDraft = {
  id: string;
  name: string;
  description?: string;
  departments: CanvasDepartmentDraft[];
  nodes: CanvasNodeDraft[];
  edges: CanvasEdgeDraft[];
  compileStatus: "draft" | "compiled" | "stale" | "invalid";
  latestCompiledVersionId?: string;
  updatedAt: string;
};
```

### 5.2 节点草稿

```ts
type CanvasNodeDraft = {
  id: string;
  kind: string;
  title: string;
  userIntent: string;
  position: { x: number; y: number };
  compiledSpec?: CompiledNodeSpec;
  compiledSpecStatus: "empty" | "fresh" | "stale" | "invalid";
};
```

### 5.3 参数代码

协议梳理后，节点下面应出现“参数代码下拉框”。

```ts
type CompiledNodeSpec = {
  nodeId: string;
  nodeKind: string;
  actionType: string;
  resolvedAction?: string;
  inputs: Array<{
    name: string;
    source: "entry" | "edge" | "constant" | "department" | "runtime";
    required: boolean;
  }>;
  outputs: Array<{
    name: string;
    type: string;
    description: string;
  }>;
  params: Record<string, unknown>;
  permissions: string[];
  requiresApproval: boolean;
  confidence: number;
};
```

连线也应有参数代码：

```ts
type CompiledEdgeSpec = {
  edgeId: string;
  transferMode: "context_packet" | "field_mapping" | "handoff_prompt";
  fields: string[];
  mapping: Array<{
    fromField: string;
    toField: string;
  }>;
  handoffPrompt: string;
};
```

### 5.4 stale 机制

用户修改原文后：

```text
compiledSpec 不立刻删除。
节点显示“参数代码已过期”。
运行按钮禁用或提示重新协议梳理。
用户重新点击协议梳理后更新 compiledSpec。
```

这能避免用户误以为原文和参数代码仍然一致。

## 6. 协议梳理设计

### 6.1 API 形态

建议接口：

```http
POST /api/ai-dorm/work-protocol-gateway/compile
```

输入：

```ts
type CompileRequest = {
  draftId?: string;
  gatewayDraft: WorkProtocolDraft;
  capabilityCatalogSnapshot: CapabilityCatalog;
  mode: "check" | "compile" | "repair";
};
```

输出：

```ts
type CompileResponse = {
  status: "valid" | "valid_with_warnings" | "invalid";
  compiledProtocol?: CompiledProtocolDefinition;
  nodePatches: NodePatch[];
  edgePatches: EdgePatch[];
  issues: ProtocolIssue[];
  suggestedAutoFixes: AutoFix[];
  summary: string;
};
```

### 6.2 协议梳理流程

```text
1. 收集画布草稿。
2. 加载能力目录快照。
3. 生成 LLM 提示词。
4. LLM 输出候选 compiledSpec。
5. JSON schema 校验。
6. 对象存在性校验。
7. 部门权限校验。
8. Tool / Skill / RAG 输入输出校验。
9. 信息流字段校验。
10. 风险和人工确认策略校验。
11. 生成 nodePatches / edgePatches。
12. 返回 issues 和可视化标注。
```

### 6.3 LLM 输出只允许用目录内能力

提示词必须明确：


## 7. 协议注册设计

### 7.1 注册对象

只有通过协议梳理的 compiled protocol version 才能注册。

```ts
type RegisteredProtocol = {
  protocolId: string;
  name: string;
  description: string;
  enabled: boolean;
  activeVersionId: string;
  triggerRules: ProtocolTriggerRule[];
  entryNodeId: string;
  reportNodeId: string;
  createdAt: string;
  updatedAt: string;
};
```

### 7.2 版本对象

```ts
type RegisteredProtocolVersion = {
  versionId: string;
  protocolId: string;
  versionNumber: number;
  draftSnapshot: WorkProtocolDraft;
  compiledSpec: CompiledProtocolDefinition;
  capabilityCatalogSnapshotHash: string;
  compileIssues: ProtocolIssue[];
  createdAt: string;
};
```

### 7.3 触发规则

```ts
type ProtocolTriggerRule = {
  id: string;
  naturalLanguageDescription: string;
  intentTags: string[];
  requiredEntities: string[];
  priority: number;
  confidenceThreshold: number;
};
```

示例：

```json
{
  "naturalLanguageDescription": "用户要求处理工单风险、分派工单、整理工单下一步时触发",
  "intentTags": ["work_order", "risk_review", "dispatch"],
  "requiredEntities": ["work_order_ref"],
  "priority": 80,
  "confidenceThreshold": 0.72
}
```

### 7.4 启停开关

每个协议应独立开关：

```text
启用：BP问问路由器可以匹配和调用该协议。
停用：协议保留，但 BP问问不会自动走它。
草稿：只能编辑和梳理，不能被路由。
```

这比全局开关更稳，因为不同协议成熟度不同。

## 8. BP问问协议路由器

### 8.1 路由器位置

建议在 BP问问 task planning 入口附近增加 protocol router。

逻辑：

```text
用户消息
-> 普通聊天判断
-> 任务意图判断
-> 查询 enabled protocols
-> 协议匹配
-> 若匹配，生成 protocol execution task
-> 若不匹配，回落 Tool Calling 或 Longxia fallback
```

### 8.2 匹配输入

```ts
type ProtocolRouteRequest = {
  threadId: string;
  userMessage: string;
  recentContext: string;
  knownEntities: Record<string, unknown>;
  enabledProtocols: RegisteredProtocol[];
};
```

### 8.3 匹配输出

```ts
type ProtocolRouteResult = {
  matched: boolean;
  protocolId?: string;
  versionId?: string;
  confidence: number;
  missingInputs: string[];
  reason: string;
};
```

### 8.4 重要兜底

协议匹配失败不能阻断 BP问问。

兜底顺序：

```text
协议匹配失败
-> Tool Calling 规划
-> 若工具不足，Longxia fallback
-> 若仍不足，追问用户
```

协议执行失败也应回到 BP问问：

```text
协议执行失败
-> 生成失败摘要和可恢复建议
-> BP问问向用户解释
-> 可建议切换人工确认、重试、改协议或走默认工具
```

## 9. 协议运行时设计

### 9.1 统一 Context Packet

运行时每个节点传递的不是散文本，而是统一上下文包。

```ts
type ProtocolContextPacket = {

  threadId: string;
  protocolId: string;
  versionId: string;
  currentNodeId: string;
  goal: string;
  constraints: string[];
  resourceScope: Array<{
    departmentId: string;
    scopeId: string;
    resourceRefs: string[];
  }>;
  inputs: Record<string, unknown>;
  outputs: Record<string, unknown>;
  risks: string[];
  artifacts: Array<{
    kind: string;
    ref: string;
    summary: string;
  }>;
  memoryRefs: string[];

    required: boolean;
```


### 9.4 dry-run 优先

第一阶段不要急着真实写入。先做 dry-run：

```text

写入对象只生成写入草案，不真实提交。
```

### 阶段 3：协议梳理 V1

目标：点击协议梳理后，生成参数代码和问题列表。

步骤：

### 阶段 5：BP问问协议路由器

- 不相关聊天不会触发协议。
- 停用协议不会被选中。
- 匹配失败仍可走原 Tool Calling。

- 协议能从入口跑到 BP问问汇报出口。
- 每个节点有运行状态。
- 写入对象不会真实写入。
- 人工确认节点会暂停。

### 阶段 7：第一个真实协议闭环

目标：最小真实链路上线。

建议第一条真实链路：

```text
BP问问入口
-> Tool调用：work_order.search / work_order.read
-> BP问问汇报出口
```

步骤：

1. 注册工单查询汇报协议。
2. BP问问能匹配“帮我看某个工单状态”。
3. Runtime 调用真实 Tool。
4. 输出 context packet。
5. BP问问汇报出口生成结果。
6. BP问问把结果回复给用户。
7. 写 trace 和 execution log。

验收：

- 用户在 BP问问问工单状态时，能走注册协议。
- 协议执行结果回到 BP问问。
- 失败时能说明失败节点和建议。

### 阶段 8：龙虾执行闭环

目标：部门里的 AI员工成为真实 executor。

步骤：

1. 定义 Longxia input packet。
2. 定义 Longxia output packet。
3. 把部门 scope 注入 Longxia。
4. 把 Skill 文件夹 scope 注入 Longxia。
5. 把记忆目录 scope 注入 Longxia。
6. Runtime 下发任务给 Longxia。
7. Longxia 返回结构化结果。
8. 结果进入 context packet。
9. 结果可被汇总或回报 BP问问。
10. Longxia 失败时返回可恢复错误。

验收：

- 部门内 AI员工节点可真实执行。
- 龙虾不能访问部门外资源。
- 龙虾结果能回到 BP问问汇报出口。

### 阶段 9：写入对象与人工确认

目标：高风险动作可控上线。

步骤：

1. 写入对象 executor 只先生成草案。
2. 人工确认节点能展示写入对象、字段、diff、回滚信息。
3. 用户确认后才执行真实写入。
4. 写入后记录 changedObjects。
5. 支持 rollback_ref。
6. 拒绝确认时走失败 / 分支路径。

验收：

- 没有确认不能真实写入。
- 确认后写入成功。
- 写入结果可追踪。
- 失败可返回 BP问问解释。

### 阶段 10：高级能力

包括：

- 定时触发。
- 事件触发。
- 记忆读取 / 写入。
- 做梦整理。
- 协议模板市场。
- 自动协议推荐。
- 运行质量评分。

这些不应早于主链路上线。

8. BP问问触发。
9. 龙虾执行。
10. 结果回 BP问问。

第三批 E2E：

1. 写入对象前不加人工确认。
2. 协议梳理应给警告。
3. 加人工确认后警告消失或降级。
4. dry-run 生成写入草案。
5. 确认后真实写入。

## 14. 兜底机制

### 14.1 编译兜底

场景：模型不可用。

处理：

- 返回 `compileStatus = invalid`。
- 不覆盖旧 compiledSpec。
- 前端提示“模型不可用，保留上一次参数代码”。
- 允许用户继续编辑草稿。

场景：模型输出非法 JSON。

处理：

- 自动重试一次 JSON repair。
- 仍失败则返回 issue。
- 不注册版本。

场景：模型编造能力。

处理：

- deterministic validator 拦截。
- 标红节点。
- 给出“请选择现有能力或先注册能力”。

### 14.2 路由兜底

场景：没有协议匹配。

处理：

- 回落 BP问问 Tool Calling。

场景：多个协议同时匹配。

处理：

- 优先级 + 置信度排序。
- 差距不明显时让 BP问问追问用户选择。

场景：协议停用。

处理：

- BP问问完全不调用。
- 可在 debug trace 里显示“协议存在但已停用”。

### 14.3 执行兜底

场景：节点失败。

处理：

- 记录 failed node。
- 如果有失败分支，走失败分支。
- 如果没有失败分支，进入 BP问问汇报出口说明失败。

场景：Tool 调用失败。

处理：

- 返回 tool error packet。
- 可重试一次低风险只读动作。
- 写入动作不自动重试。

场景：龙虾超时。

处理：

- 标记 agent timeout。
- 允许重试、换龙虾、转人工、回报 BP问问。

场景：人工确认拒绝。

处理：

- 不执行写入。
- 结果回到 BP问问。
- BP问问说明已取消或询问下一步。

### 14.4 权限兜底

原则：

```text
前端显示权限只是提示。
后端 runtime 必须重新校验权限。
```

任何节点执行前都必须检查：

- 当前协议版本是否启用。
- 当前部门 scope 是否允许。
- 当前 AI员工是否可见该部门。
- 当前 Tool / Skill 是否被允许。
- 当前写入对象是否被允许。
- 是否需要人工确认。

### 14.5 审计兜底

所有执行应记录：

- 谁触发。
- 哪个协议。
- 哪个版本。
- 哪些节点跑了。
- 每个节点输入输出摘要。
- 是否使用模型。
- 是否调用 Tool / Skill / 龙虾。
- 是否写入对象。
- 是否人工确认。
- 失败原因。

## 16. 2026-05-03 数据模型审计补充

本轮先检查协议数据模型，不继续接画布。

当前工程里已经形成四层边界：

```text
WorkProtocolDraft
-> CompiledProtocolDefinition
-> RegisteredProtocol / RegisteredProtocolVersion
-> ProtocolExecution / WorkProtocolExecutionPlanRecord
```

审计结论：

- `WorkProtocolDraft` 负责画布原文、位置、部门沙箱和 stale/fresh 状态。
- `CompiledProtocolDefinition` 负责执行协议代码，不应该依赖画布坐标。
- `RegisteredProtocol` 负责启停、优先级、触发规则和 active version。
- `ProtocolExecution` 负责运行态状态、上下文包、trace 和输出包。
- `CapabilityCatalog` 已经把部门、AI员工、方块类型、Tool、Skill、RAG、写入对象统一成可校验目录。
- `validator` 已覆盖对象存在性、权限、mock/planned/disabled 能力、写入确认、断线、自环和入口可达性。
- `runtime` 当前只支持 `plan_only` dry-run，不真实调用 Tool / Skill / RAG / 龙虾，不真实写业务数据。

本轮加固点：

- `RegisteredProtocol` 增加 `runtimeMode`，当前只允许注册为 `plan_only`。
- `RegisteredProtocol` 增加 `createdBy`，方便后续审计。
- `RegisteredProtocolVersion` 保存 `draftSnapshot`，避免只留下 compiled 版本、丢失注册时的画布语义。
- `RegisteredProtocolVersion` 保存 `capabilityCatalogHash`，后续可以判断“协议版本是基于哪一版能力目录编译出来的”。
- BP问问协议匹配结果带上 `runtimeMode`，防止未来 live runtime 接入后，把 plan-only 协议误当正式执行协议。
- execution runtime 在创建 plan-only 计划时会拒绝非 `plan_only` 的注册协议。

这个补充的意义是：注册协议不再只是“能匹配的 compiled JSON”，而是具备可审计来源、运行模式和能力目录版本的协议资产。后面接画布、真实执行器和数据库表时，应继续保持这四层边界，不要把画布草稿字段直接塞进运行态。

## 17. 2026-05-03 状态机审计补充

本轮继续加固地基，先不接画布，目标是把执行状态从 runtime 里的零散判断抽成明确状态机。

新增状态机边界：

```text
compile 状态：
draft -> compiled / invalid / stale
compiled -> compiled / stale / invalid
stale -> compiled / invalid
invalid -> draft / compiled / invalid
```

```text
execution 状态：
queued -> running / waiting_confirmation / completed / failed / cancelled
running -> waiting_confirmation / completed / failed / cancelled
waiting_confirmation -> running / completed / failed / cancelled
completed / failed / cancelled 为终态
```

```text
node 状态：
queued -> running / waiting_confirmation / completed / skipped / failed
running -> waiting_confirmation / completed / skipped / failed
waiting_confirmation -> running / completed / skipped / failed
completed / skipped / failed 为终态
```

工程动作：

- 新增 `frontend/src/lib/work-protocol/state-machine.ts`。
- runtime 节点推进和人工确认推进都改为通过状态机断言。
- 终态 execution 不允许继续推进。
- 等待确认节点只能从 `waiting_confirmation` 被确认到 `completed`。
- 如果执行计划没有可推进节点、没有等待确认节点、也没有完成，则标记为 `failed`。
- 新增 `runtime_deadlock` issue code，用来描述运行时 DAG 卡死或数据异常。

这个补充的意义是：后续接真实 Tool、Skill、RAG、Longxia executor 时，每个执行器不能随便改状态，必须走统一状态机。这样才有可能做到可审计、可恢复、可定位失败。

## 18. 2026-05-03 校验器加固补充

本轮继续检查 `validator`，目标是让坏协议在注册前被确定性拦住，而不是等 runtime 才卡死。

已有覆盖：

- 部门、范围、AI员工、Tool、Skill、RAG、写入对象存在性。
- mock / planned / disabled 能力状态。
- 部门范围权限。
- AI员工可见范围。
- 写入对象权限。
- 写入对象前人工确认提醒。
- 连线缺端点、自连线、空传输说明。
- BP问问入口可达性。

本轮加固点：

- 增加多节点环路检测，不只拦自连线。
- 注册模式下，不可达节点从 warning 升级为 error。
- 有节点但缺少 `BP问问汇报出口` 时，注册模式下拦截。
- `BP问问入口` 不能接收上游连线。
- `BP问问汇报出口` 不能继续向下游连线。
- `条件判断` 节点至少需要两条下游分支，注册模式下拦截。

当前策略：

```text
draft 模式：尽量以 warning 提示，允许用户继续搭。
register 模式：会导致 runtime 卡死、无法回到 BP问问、或破坏入口/出口语义的问题升级为 error。
runtime 模式：后续真实 executor 接入前还要再做执行前权限复核。
```

这个补充的意义是：画布可以宽松，但注册协议必须严格。用户可以乱搭草稿，但不能把明显无出口、不可达、环路、入口/出口错接的协议注册成 BP问问会自动匹配的中枢协议。

## 19. 2026-05-03 runtime 兜底审计补充

本轮继续检查 `runtime`，目标是让 plan-only dry-run 即使遇到注册协议变化、能力目录变化或异常状态，也能明确失败并留下 trace，而不是悄悄推进坏计划。

本轮加固点：

- 创建执行计划时，只接受 `plan_only` 注册协议。
- 创建执行计划时，要求匹配结果引用的 `activeVersionId` 必须仍是协议当前 active version。
- 推进执行计划前，如果 execution 已经是 `completed / failed / cancelled`，直接返回，不再重复推进。
- 推进执行计划前，会重新读取注册协议，确认协议仍存在、仍启用、运行模式仍一致。
- 推进执行计划前，会确认执行计划引用的 version 仍是当前 active version，避免老版本计划继续运行。
- 推进执行计划前，会确认执行计划记录的 `capabilityCatalogHash` 和注册版本一致，避免能力目录变化后继续用旧参数。
- 状态机抛出非法状态流转时，不让异常裸奔到页面，而是把 execution 标记为 `failed`，写入 `invalid_state_transition` issue 和 trace。
- runtime deadlock 已经有独立 `runtime_deadlock` issue；本轮补齐协议启停、版本、运行模式和能力目录的失败原因。

当前失败策略：

```text
协议不存在 / 版本不可用 -> failed + protocol_version_unavailable
协议被停用 -> failed + protocol_not_enabled
运行模式变化 -> failed + runtime_mode_mismatch
能力目录过期 -> failed + capability_catalog_stale
非法状态流转 -> failed + invalid_state_transition
DAG 卡死 -> failed + runtime_deadlock
```

这个补充的意义是：执行计划不再只依赖创建时的快照。每次推进前都要做一次轻量执行前复核，确保“注册协议阀门仍然打开、版本仍然有效、能力目录没有漂移”。后续接真实 Tool / Skill / RAG / 龙虾 executor 时，这一层会继续扩展成完整 preflight guard。

```text
advance execution
-> 复核注册协议仍有效
```

## 23. 2026-05-03 context packet / field flow 补充

本轮继续补工作协议网关的 runtime 地基，目标不是接画布，而是先把“上游节点如何把结果交给下游节点”这件事固定成可测试的数据结构。

新增/强化文件：

```text
frontend/src/lib/work-protocol/field-flow.ts
frontend/src/lib/work-protocol/runtime.ts
frontend/src/lib/work-protocol/executor-adapters.ts
frontend/scripts/work-protocol-gateway-smoke.mjs
```

当前约定：

- 每个节点执行前都会生成一个 `nodeInput`。
- `nodeInput` 会写入 `inputPacket.values.nodeInputs[nodeId]`。
- `nodeInput` 保留用户原始 prompt、当前节点信息、部门范围、callable / agent / writable object 引用。
- `nodeInput.inboundEdges` 记录进入该节点的连线、传输模式、连线提示词、requiredFields 和 fieldMappings。
- `nodeInput.upstreamOutputs` 记录每条入边来源节点已经产出的结构化输出。
- `nodeInput.prompts` 汇总连线上的通讯提示词。
- `nodeInput.fields` 是 fieldMappings 解析后的结构化字段区。
- 每条入边在执行前写入 `edge_transferred` trace。
- adapter 不再只拿 execution record 和 node，而是明确拿到 `nodeInput`。
- plan-only adapter 的输出里会带 `nodeInput`，方便烟测和执行详情页追踪。

字段流当前策略：

- 没有 fieldMappings 时，默认仍然把上游完整输出放进 `upstreamOutputs`，不阻塞执行。
- 有 fieldMappings 时，按 `fromPath -> toPath` 写入 `fields`。
- required mapping 缺失时，生成 `field_flow_mismatch` issue。
- `requiredFields` 缺失时，生成 `field_flow_mismatch` issue。
- 字段流失败时，当前节点进入 `failed`，execution 进入 `failed`，trace 写入 `node_failed` 和 `protocol_failed`。

runtime 当前执行顺序变为：

```text
advance execution
-> 检查注册协议仍有效
-> 检查 catalog hash
-> 找到可执行节点
-> preflight
-> build nodeInput / field flow
-> confirmation gate（如需要）
-> adapter
-> nodeOutputs / nodeInputs / trace
-> 状态机推进
```

烟测新增断言：

- Tool 节点必须收到 entry -> tool 的 `nodeInput`。
- BP问问汇报出口必须在 `nodeInput.upstreamOutputs` 里收到 Tool 节点输出。
- 原有注册、匹配、执行完成、停用协议兜底仍然保留。

当前验证结果：

```text

-> pass

docker restart bpai-front-dev
docker exec bpai-front-dev npm run smoke:work-protocol
-> work protocol gateway smoke passed
```

## 30. 2026-05-03 画布协议梳理接入 groom / draft-store

本轮把前端“协议梳理”按钮从旧的 `/compile` 直连，改成了真实的 `/groom` 主链。画布现在点击“协议梳理”时会做四件事：

1. 从当前画布生成 source draft。
2. 调用 `POST /api/ai-dorm/work-protocol-gateway/groom`，使用 `mode = "register"` 和 `allowMockCapabilities = true`。
3. 将原始 source draft 保存到 `/drafts`，再将 `groomedDraft` 保存成 groomed draft record，并记录 `sourceRecordId`、`catalogHash` 和 grooming metadata。
4. 用 `protocolSummary`、`nodeAnnotations`、`edgeAnnotations` 和 `departmentAnnotations` 回填前端状态：右下角显示总结，节点、连线、部门按 issue 标红 / 标黄，参数代码块继续展示在对应方块和连线里。

注册边界也同步收紧：前端不再把当前画布 draft 直接发给 `/registry`。点击“注册协议”时，必须已经存在可注册的 groomed draft record；如果画布被修改、协议梳理失败、草稿记录保存失败，注册会被前端拦住并提示重新梳理。真正注册时只提交：

```json
{
  "draftRecordId": "draft-record:groomed:...",
  "enabled": true,
  "priority": 1,
  "allowMockCapabilities": true,
  "runtimeMode": "plan_only"
}
```

这一步没有让协议自动启用，也没有把画布和 runtime 做成隐式联动。当前边界是：
- 画布负责编辑自然语言意图。
- groom 负责把意图梳理成参数代码和可注册草稿。
- draft-store 负责保存 source / groomed 两层记录。
- registry 只接受 groomed draft record。
- runtime 只吃 registered protocol version。

## 35. 2026-05-04 runtime preflight 接入能力契约一致性闸门

本轮继续打地基，没有接真实执行器，也没有改画布。重点是让 runtime preflight 不只相信 compiledSpec，而是把 compiledSpec 和 `CapabilityContract v1` 再对一遍，避免旧参数代码或手工改动把高风险能力降级执行。

新增检查：

1. 节点类型必须存在对应契约：

```text
node_kind.{node.kind}
```

如果缺失，返回 `capability_catalog_stale`。

2. 执行对象必须存在对应契约：

```text
tool / skill / rag: 使用 callableId
agent: agent.{agentId}
write_object: write_object.{writableObjectKind}
```

如果 compiledSpec 指向的执行对象在 catalog 里仍能找到，但派生不出 contract，也视为能力目录不一致，返回 `capability_catalog_stale`。

3. 部门范围必须存在对应契约：

```text
department_scope.{departmentScopeId}
```

如果 catalog 里存在 scope，但契约层缺失，说明 contract projection 出问题或目录已过期。

4. 执行能力契约的 `scopes` 不能被绕过。

如果 contract 声明只允许在某些 department scope 执行，而 compiledSpec 使用了其它 scope，runtime preflight 返回 `permission_denied`。

5. compiledSpec 不能降低能力风险。

例如能力契约要求 `riskLevel = high`，但参数代码里写成 `low`，runtime preflight 返回 `field_flow_mismatch`。

6. compiledSpec 不能绕过默认确认。

如果节点类型契约或执行能力契约要求确认，而参数代码里没有 `approvalPolicy = required`，runtime preflight 返回 `approval_required`。

这一步的价值：

- 协议梳理可以越来越智能，但 runtime 不把模型输出当成绝对可信。
- 用户以后在“参数代码下拉框”里手动改参数，也不能把高风险能力偷偷改成低风险。
- 后续接 live runtime 时，这层可以直接作为写入、外部动作、龙虾下发前的统一闸门。

新增 smoke 场景：

- 构造一个 `write_object.work_order` 协议。
- 手工塞入旧 `compiledSpec`，把写入对象错误标成 `riskLevel = low`、`approvalPolicy = none`。
- 注册可以通过，因为这模拟“旧参数代码/手工参数代码进入 registry”。
- 执行推进时必须在 runtime preflight 阶段失败。
- 失败 issue 必须包含 `field_flow_mismatch` 或 `approval_required`。
- 写入节点状态必须变成 `failed`。

- 入口：`WorkProtocolGroomingInputPack`
- 出口：`work-protocol-model-grooming-output.v1`
- 闸门：`validateWorkProtocolModelGroomingOutput`

也就是说，未来点击“协议梳理”时，大模型不应该直接看到整份系统内部对象，也不应该随便返回一坨自由文本。它应该只拿到一个经过裁剪的输入包，并且只能返回受控 JSON。

### 36.1 输入包

新增文件：

输入包结构核心字段：

```ts
{

    id: string,
    name: string,
    description?: string,

  },
```

这里的关键点是：

- `capabilityContracts` 只放当前草稿相关的契约，不把全系统所有能力无脑塞给模型。
- `knownContractIds` 保留 catalog 全量 ID，用于判断模型是否引用了不存在的契约。
- 每个节点都有 `candidateContractIds`，表示这个节点在当前部门范围内允许绑定哪些能力。
- 每个部门也有自己的 `candidateContractIds`，用于后续判断部门沙箱范围是否可用。

### 36.2 模型输出契约

模型出口固定为：

```ts

  status: "groomed" | "needs_user_input" | "invalid",
  protocolSummary?: {...},
  nodeUpdates?: [...],
  edgeUpdates?: [...],
  issues?: [...]
}
```

目前先做结构和 ID 级别校验：

- `schemaVersion` 必须正确。
- `status` 必须是已知状态。
- `nodeUpdates[].nodeId` 必须存在于输入包。
- `edgeUpdates[].edgeId` 必须存在于输入包。
- `contractId / callableId / agentId / writableObjectKind / departmentScopeId` 必须能映射到已知契约。
- 节点引用的契约必须在该节点的 `candidateContractIds` 内。
- `compiledSpec.nodeId/kind` 不允许和原节点不一致。
- `compiledSpec.edgeId/sourceNodeId/targetNodeId` 不允许和原连线不一致。
- `issues[].target` 必须指向存在的 protocol / department / node / edge。

这一步的意义是：后续接真实模型时，即使模型误判、幻觉、引用不存在的 Tool/Skill/RAG/龙虾，也只能被标成校验失败，不能直接进入注册或 runtime。

## 37. 2026-05-04 模型输出应用器：白名单 patch 层

本轮继续补“协议梳理”的地基。上一节已经固定了模型输入包和模型输出契约，本轮新增的是模型输出应用器：

```text
frontend/src/lib/work-protocol/model-output-applier.ts
```

核心原则：

> 即使模型输出通过了 `work-protocol-model-grooming-output.v1` 校验，也不能直接改整份 `WorkProtocolDraft`。模型只能提出更新建议，由后端白名单 patch 层决定哪些字段可以落到 draft。

### 37.1 为什么需要应用器

如果后续直接把大模型输出 merge 到画布草稿，会出现几个风险：

- 模型可能改掉原始自然语言输入，导致用户之后无法追溯“我当时到底写了什么”。
- 模型可能塞入不完整或过度自由的 `compiledSpec`。
- 模型可能绕过 deterministic compiler，把高风险节点写成低风险参数。
- 模型可能改动画布结构、节点 ID、连线端点，导致注册链路不稳定。

所以本轮把“模型输出”和“真实草稿修改”隔开，中间放一个受控应用器。

### 37.2 当前允许应用的字段

节点层目前只允许应用执行对象选择：

```ts
tool_call / skill_call / rag_search:
  callableId

agent_task:
  agentId

write_object:
  writableObjectKind
```

应用后：

- 节点 `compiledSpec` 会被清空。
- 节点 `compiledSpecStatus` 标成 `stale`。
- 后续必须再走 deterministic groom / compile 重新生成参数代码。

模型输出里的这些字段目前不会直接写入 draft：

```ts
intentSummary
compiledSpec
```

原因是原始 prompt 要保留，节点完整 `compiledSpec` 必须由 compiler 生成。后续如果要展示模型润色后的“协议解释”，应该另建参数代码/梳理结果层，而不是覆盖 `userIntent`。

### 37.3 当前允许应用的连线字段

连线层允许应用结构化传输参数，但只写入 sanitized `edge.compiledSpec`：

```ts
transferMode
prompt
compiledSpec.fieldMappings
compiledSpec.requiredFields
compiledSpec.outputPacketSchema
```

应用后：

- 原始 `edge.transferIntent` 不变。
- `edge.compiledSpecStatus` 标成 `stale`。
- 再走 deterministic groom / compile 后，编译器会把这个 sanitized 连线参数保留下来，并标成 fresh。

这符合我们对 UI 的目标：

- 线上的原始文字仍然保留，方便用户修改。
- “参数代码下拉框”里可以看到模型梳理后的结构化传输参数。

### 37.4 新增 API 行为

接口仍然是：

```text
POST /api/ai-dorm/work-protocol-gateway/grooming-contract
```

新增请求字段：

```ts
{
  draft: WorkProtocolDraft,
  modelOutput: unknown,
  applyModelOutput: true
}
```

返回会多出：

```ts
{
  application: {
    schemaVersion: "work-protocol-model-output-application.v1",
    status: "applied" | "applied_with_warnings" | "rejected",
    validation: WorkProtocolModelOutputValidationResult,
    inputPack: WorkProtocolGroomingInputPack,
    appliedDraft: WorkProtocolDraft,
    appliedChanges: [...],
    ignoredChanges: [...]
  }
}
```

如果模型输出校验失败：

- `application.status = rejected`
- `appliedDraft` 保持原草稿
- 不进入 patch

如果模型输出校验成功：

- 只应用白名单字段
- 记录 `appliedChanges`
- 对暂不支持的字段记录 `ignoredChanges`

### 37.5 smoke 新增覆盖

本轮 smoke 增加了模型输出应用链路：

- 合法模型输出必须返回 `application.status = applied`。
- 合法模型输出的连线 `transferMode` 会被应用成 `structured_packet`。
- 原始 `edge.transferIntent` 必须保持不变。
- 应用后的 draft 再调用 `/groom`，必须保留 sanitized 连线参数。
- 非法模型输出必须返回 `application.status = rejected`。

这说明现在的链路已经变成：

```text
canvas draft
  -> grooming input pack
  -> model output contract validation
  -> whitelist patch application
  -> deterministic groom / compile
  -> draft store / register / runtime
```

### 37.6 当前边界

还没有做：

- 调真实大模型。
- 前端展示 `appliedChanges / ignoredChanges`。
- 对节点级参数代码做完整 UI 下拉框。
- 对 `fieldMappings` 做更细的 schema 级别可视化编辑。

但工程地基已经比上一阶段更稳：模型不再有“直接改协议草稿”的能力，只能通过白名单 patch 影响后续 deterministic 编译。

## 38. 2026-05-04 协议梳理结果审计层

本轮继续补“协议梳理”面向前端和后续调试的审计结构。前几轮已经有：

```text
canvas draft
  -> grooming input pack
  -> model output contract validation
  -> whitelist patch application
  -> deterministic groom / compile
```

但如果只返回 `validation / application / compileResult`，前端需要自己拼很多逻辑，后续也很难稳定地把问题标到某个方块或某条连线上。所以本轮新增统一审计层：

```text
frontend/src/lib/work-protocol/grooming-audit.ts
```

### 38.1 审计层目标

审计层不是新的执行逻辑，它只是把已有结果整理成统一事件流：

```ts
WorkProtocolGroomingAudit
```

核心目标：

- 前端右侧“协议问题/链路检查”面板可以直接读。
- 方块和连线可以根据 target 快速拿到自己的审计事件。
- 模型输出验证、模型输出应用、deterministic groom 可以放在同一套事件结构里。
- 后续接真实 LLM 后，模型幻觉、被拒绝的建议、成功应用的 patch 都能清楚展示。

### 38.2 返回结构

新增结构：

```ts
{
  schemaVersion: "work-protocol-grooming-audit.v1",
  status: "pass" | "warning" | "blocked",
  summary: {
    success: number,
    info: number,
    warnings: number,
    errors: number,
    sections: number,
    modelOutputValid?: boolean,
    applicationStatus?: "applied" | "applied_with_warnings" | "rejected",
    appliedChanges: number,
    ignoredChanges: number,
    canRegister?: boolean
  },
  sections: [...],
  eventsByTarget: {
    "protocol:root": [...],
    "node:{nodeId}": [...],
    "edge:{edgeId}": [...],
    "department:{departmentId}": [...]
  }
}
```

### 38.3 事件来源

当前审计事件来源分四类：

```ts
"input_pack"
"deterministic_groom"
"model_output_validation"
"model_output_application"
```

对应含义：

- `input_pack`：模型可见上下文已经生成，包含多少节点、连线、部门和相关能力契约。
- `deterministic_groom`：现有编译/校验/注解结果。
- `model_output_validation`：模型输出契约校验结果，例如未知节点、未知连线、未知 contract。
- `model_output_application`：白名单 patch 应用结果，例如某条连线的 `transferMode` 被应用，或者某个模型建议被忽略。

### 38.4 接入位置

`groomWorkProtocolDraftV0` 现在返回：

```ts
audit: WorkProtocolGroomingAudit
```

也就是普通点击“协议梳理”时，即使没有真实模型输出，也会有审计结果：

- input pack section
- deterministic groom section
- eventsByTarget

`POST /api/ai-dorm/work-protocol-gateway/grooming-contract` 现在也返回：

```ts
audit: WorkProtocolGroomingAudit
```

如果请求里带了 `modelOutput` 和 `applyModelOutput: true`，audit 会同时包含：

- input pack section
- model output validation section
- model output application section

### 38.5 面向前端的用法

后续 UI 可以按这个方式接：

1. 右下角“协议问题”面板读取：
```ts

audit.summary
```

2. 节点方块读取：
```ts
audit.eventsByTarget[`node:${node.id}`]
```

3. 连线读取：
```ts
audit.eventsByTarget[`edge:${edge.id}`]
```

4. 顶层协议读取：
```ts
audit.eventsByTarget["protocol:root"]
```

这样前端不需要知道某个问题到底来自 validation、application 还是 compile。它只需要按 target 和 severity 渲染：

- `error`：标红，阻塞注册。
- `warning`：黄色，建议确认。
- `info`：灰蓝提示。
- `success`：绿色，表示某个梳理动作成功应用。

### 38.6 smoke 新增覆盖

本轮 smoke 增加：

- 普通 groom 必须返回 `work-protocol-grooming-audit.v1`。
- 干净协议的审计状态必须是 `pass`。

- 模型应用事件必须被索引到 `edge:edge-entry-to-tool`。

- 未知 contract 的模型输出错误必须能映射回 `node:node-read-work-order`。

### 38.7 当前边界

当前只是后端审计结构，前端还没有完整使用它。前端目前仍主要使用旧的：

```ts

nodeAnnotations
edgeAnnotations

```
