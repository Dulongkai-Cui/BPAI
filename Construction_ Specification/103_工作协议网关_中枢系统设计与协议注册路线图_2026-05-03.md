## 0. 核心结论

工作协议网关不应该只被理解成一个画布，也不应该被理解成一条固定管道。

它最合理的工程定位是：

```text
工作协议网关 = 可注册、可启停、可匹配、可编译、可执行、可审计的任务编排层
```

对 BP问问 来说，它应该表现为一组“高阶工具”：

```text
用户自然语言任务
-> BP问问判断是否是任务
-> 查询已启用工作协议
-> 匹配协议触发条件
-> 执行协议
-> 通过 BP问问汇报出口回到 BP问问
-> BP问问用自然语言回复用户
```

部门不是普通节点。部门是资源沙箱和权限边界。

方块不是最终协议。方块是用户可编辑的自然语言草稿。

协议梳理不是保存按钮。协议梳理是“自然语言画布 -> 可执行协议”的编译器。

AI生产资料仓不是单纯 Skill 列表。它应成为模型 Key、Skill 包、RAG、记忆目录、内置蓝图和后续运行时资产的统一生产资料中心。

## 1. 当前现状

### 1.1 BP问问当前状态

当前 BP问问已经具备基础 Tool Calling 主链，不能再按“纯聊天 Demo”看待。

已具备能力：

- 普通自然语言对话入口仍可用。
- 当用户表达明确任务意图时，系统可以进入 task mode。
- 工单和文档基础能力已经能通过 Tool Gateway 调用。
- 缺参时可以追问。
- 搜索出现多个候选时可以要求用户选择。
- 用户补充候选、工单号、文档 ID、写入内容后，可以继续执行后续 step。
- 工单和文档基础工具已通过 Docker smoke 验证。

当前 Tool Gateway 已有 capability descriptor：

- `domain`
- `action`
- `riskLevel`
- `executionMode`
- `inputSchema`
- `outputSchema`
- `requiredContext`
- `plannerHints`
- `failureModes`
- `requiresConfirmationDefault`

这说明系统已经有“工具注册表”的雏形。工作协议网关后续应复用这个思路，把“协议”也注册成 BP问问可选择的高阶能力。

仍然不足：

- 表格 `.xlsx` 精细编辑尚未完成，当前不能可靠改单元格、追加行、按行查询后写入。
- Longxia fallback 有 handoff 方向，但还没有生产级闭环。
- BP问问对复杂任务的规划仍依赖模型可用性。
- 模型规划失败时的 deterministic fallback 还不够丰富。
- Tool 调用结果、协议执行状态、Longxia 结果回流还没有统一 runtime packet。

### 1.2 龙虾当前状态

当前龙虾已经具备产品心智和部分技术入口，但还不能算完整执行层。

已有基础：

- AI宿舍页面里已经有 AI员工 / 龙虾 的概念。
- 已有 Longxia adapter、handoff payload、`ready_to_delegate` 等方向。
- OpenClaw state 目录已经存在，具备后续把龙虾状态和记忆落盘的路径。
- 工作协议网关的部门沙箱里已经可以选择可见 AI员工。
- AI记忆主脑里已经做出龙虾记忆入口列表和单只龙虾记忆页原型。

当前缺口：

- 龙虾还不是协议 runtime 中的稳定 executor。
- 龙虾接到任务后的多轮追问、状态推进、结果回传没有统一协议。
- 龙虾可见部门、可见 Skill 文件夹、可见记忆目录还没有后端强制权限。
- 龙虾产物如何进入 `execution_results`、如何回到 BP问问回复用户，还需要统一链路。

### 1.3 工作协议网关当前前端状态

当前前端“皮相”已经基本够用，主要包括：

- 页面已改名为“工作协议网关”。
- 画布支持固定页面、中间画布拖动、缩放、方块拖动。
- 部门是独立大方块，不再只是普通节点。
- 部门可选择大部门和具体范围。
- 文档档案室支持“全部 / 我的文档空间 / 合作空间”的分层范围选择方向。
- 部门内可见 AI员工可被点击加入部门。
- 部门可以收缩 / 展开，并展示大部门和范围摘要。
- 部门和方块均支持删除。
- 普通方块有连接点、填写框和删除按钮。
- 连线有默认传输提示词，未来可展开编辑。
- “协议梳理”目前仍是 mock compile，但已经有右下角问题面板、节点 / 连线标红方向。

当前可添加的普通方块已经收敛为协议语义块：

- `BP问问入口`
- `Tool调用`
- `Skill调用`
- `RAG检索`
- `任务分派`
- `结果汇总`
- `条件判断`
- `人工确认`
- `BP问问追问`
- `写入对象`
- `BP问问汇报出口`

重要约束：

- `AI员工` 不应从“添加方块”直接添加。
- `AI员工` 应从部门沙箱中选择并放入部门。
- 部门负责“谁能看什么、谁能用什么、谁能写哪里”。
- 普通方块负责“任务如何流转”。

### 1.4 AI生产资料仓当前状态

AI生产资料仓已经从原 Skill 仓库扩展为更大的生产资料中心原型。

当前前端方向包括：

- API Key 中心：DeepSeek、Kimi 等模型访问配置。
- Skill 工厂：命令安装、Zip 导入、本地包快照。
- 本地 Skill 包管理：类似文档档案室的文件夹区域，支持未来把 Skill 包拖入文件夹。
- 内置 Skill 蓝图：系统预设能力的展示。
- RAG 工厂：知识库、索引、检索测试台原型。
- AI记忆主脑：BP问问脑区入口、龙虾记忆入口、做梦模块。

当前关键设计判断：

- Skill 权限不应直接在本地包管理页绑定某只龙虾。
- 本地包管理只负责下载、上传、建文件夹、归档 Skill 包。
- 龙虾配置页未来再按文件夹开放 Skill 可见范围。
- 同一 Skill 文件夹可以授权给多只龙虾复用。
- 这能减少每只龙虾扫描全部 Skill 的上下文成本。

### 1.5 当前系统还不是中枢的原因

当前“看起来像中枢”，但底层还没有中枢。

缺少的核心部件：

- 工作协议 JSON Schema。
- 协议草稿保存和版本管理。
- 协议编译结果结构。
- 协议注册表。
- 协议启用 / 停用开关。
- BP问问协议路由器。
- 运行时 DAG executor。
- 统一 context packet。
- 部门权限 runtime enforcement。
- 协议执行日志和审计。
- 协议测试和 dry-run。

因此下一步重点不是继续堆 UI，而是定义并实现底层协议系统。

## 2. 理想状态定义

### 2.1 BP问问的理想状态

BP问问应该保持自然对话体验：

```text
平常聊天没有负担。
用户说任务时，BP问问能主动打起精神。
BP问问能判断缺什么信息。
BP问问能追问。
信息齐全后，BP问问能选择工具、协议或龙虾执行。
执行结果回到 BP问问，由 BP问问整理成人话回复用户。
```

BP问问不应该直接硬编码所有复杂流程。它应该有三类能力选择：

1. 直接 Tool Calling。
2. 已注册工作协议。
3. Longxia fallback / AI员工任务下发。

推荐优先级：

```text
普通聊天
-> 任务识别
-> 是否有已启用协议匹配
-> 若匹配，走工作协议网关
-> 若不匹配但工具足够，走 Tool Calling
-> 若工具不足或任务需要外部 AI员工，走 Longxia / AI员工
-> 结果统一回 BP问问
```

### 2.2 龙虾的理想状态

龙虾应该是部门沙箱内的专业执行者。

每只龙虾需要具备：

- 可见部门范围。
- 可见资源范围。
- 可见 Skill 文件夹。
- 可见记忆目录。
- 输入 schema。
- 输出 schema。
- 可执行任务类型。
- 是否允许写入。
- 失败回报协议。

龙虾不应自己决定越权看资源。运行时应该只把授权范围内的上下文注入给它。

### 2.3 工作协议网关的理想状态

工作协议网关应该是“自然语言协议 IDE”。

它包含两层：

```text
用户表达层：方块、部门、连线、自然语言填写框
执行协议层：参数代码、schema、权限、输入输出、触发规则、运行状态
```

用户看到的是：

- 选部门。
- 选可见 AI员工。
- 添加方块。
- 拉线。
- 写“您想让它干什么”。
- 写“想传什么给下一个节点”。
- 点“协议梳理”。

系统生成的是：

- `compiledNodeSpec`
- `compiledEdgeSpec`
- `triggerRules`
- `requiredInputs`
- `outputs`
- `permissions`
- `approvalPolicy`
- `runtimePlan`
- `issues`

协议梳理后，每个节点和连线都应该有“参数代码下拉框”：

```text
原始文本保留，方便用户继续修改。
参数代码折叠展示，方便用户和开发者看到系统理解结果。
原始文本被修改后，参数代码标记为 stale。
重新协议梳理后，参数代码更新。
```

### 2.4 AI生产资料仓的理想状态

AI生产资料仓应该提供所有协议生成和执行所需的生产资料。

它至少包括：

- API Key / 模型配置。
- Skill 包市场和本地 Skill 文件夹。
- 内置 Skill 蓝图。
- RAG 知识库和检索测试。
- BP问问记忆和身份 Prompt。
- 龙虾记忆文件夹入口。
- 后续可扩展的工具目录、模板目录、协议模板目录。

它和工作协议网关的关系：

```text
AI生产资料仓提供能力资产。
工作协议网关引用能力资产。
协议梳理读取能力资产目录，生成受约束的可执行协议。
运行时按协议引用能力资产。
```

## 3. 中枢系统总体架构

### 3.1 五层架构

推荐拆成五层：

```text
1. Capability Catalog 能力目录层
2. Protocol Draft 协议草稿层
3. Protocol Compiler 协议梳理层
4. Protocol Registry 协议注册层
5. Protocol Runtime 协议执行层
```

每层职责如下：

| 层级 | 主要职责 | 是否需要模型 |
| --- | --- | --- |
| Capability Catalog | 注册部门、方块、Tool、Skill、RAG、龙虾、写入对象能力 | 否 |
| Protocol Draft | 保存画布草稿、用户原文、节点位置、连线原文 | 否 |
| Protocol Compiler | 把自然语言草稿梳理成参数代码和执行协议 | 是 |
| Protocol Registry | 保存已编译版本、触发规则、启停状态、版本 | 否 |
| Protocol Runtime | 执行 DAG、调用工具、分派龙虾、等待确认、返回结果 | 部分需要 |

### 3.2 核心数据流

```text
前端画布草稿
-> 保存 Protocol Draft
-> 点击协议梳理
-> 加载 Capability Catalog
-> LLM 生成 compiledSpec 草案
-> 确定性校验器校验
-> 返回参数代码、问题、自动修复建议
-> 用户确认并注册协议版本
-> BP问问查询已启用协议
-> 匹配触发规则
-> Protocol Runtime 执行
-> BP问问汇报出口返回结果
```

### 3.3 为什么不能只靠 LLM

协议梳理必须分成两段：

```text
LLM 负责理解和改写。
确定性校验器负责合法性、权限、字段、对象存在性和风险策略。
```

只靠 LLM 的问题：

- 它可能编造不存在的 Tool。
- 它可能假设 Skill 存在。
- 它可能忽略部门权限。
- 它可能让写入动作绕过人工确认。
- 它可能把上游没有的字段传给下游。

只靠规则的問題：

- 读不懂用户自然语言。
- 很难处理“帮我让预警龙虾看看这件事有没有风险”这种模糊表达。

因此必须是：

```text
受约束的 LLM 生成 + 后端确定性校验
```

## 4. Capability Catalog 设计

第一步不是直接做协议生成，而是先整理“每类对象到底有哪些可动参数”。

```ts
type DepartmentCapability = {
```

```ts
type AgentCapability = {
```

## 5. 协议草稿与参数代码

### 5.1 草稿结构

画布保存的是草稿，不是最终执行协议。

```ts
type WorkProtocolDraft = {
  id: string;
  name: string;
  description?: string;
  departments: CanvasDepartmentDraft[];
  nodes: CanvasNodeDraft[];
  edges: CanvasEdgeDraft[];
  compileStatus: "draft" | "compiled" | "stale" | "invalid";
  latestCompiledVersionId?: string;
  updatedAt: string;
};
```

### 5.2 节点草稿

```ts
type CanvasNodeDraft = {
  id: string;
  kind: string;
  title: string;
  userIntent: string;
  position: { x: number; y: number };
  compiledSpec?: CompiledNodeSpec;
  compiledSpecStatus: "empty" | "fresh" | "stale" | "invalid";
};
```

### 5.3 参数代码

协议梳理后，节点下面应出现“参数代码下拉框”。

```ts
type CompiledNodeSpec = {
  nodeId: string;
  nodeKind: string;
  actionType: string;
  resolvedAction?: string;
  inputs: Array<{
    name: string;
    source: "entry" | "edge" | "constant" | "department" | "runtime";
    required: boolean;
  }>;
  outputs: Array<{
    name: string;
    type: string;
    description: string;
  }>;
  params: Record<string, unknown>;
  permissions: string[];
  requiresApproval: boolean;
  confidence: number;
};
```

连线也应有参数代码：

```ts
type CompiledEdgeSpec = {
  edgeId: string;
  transferMode: "context_packet" | "field_mapping" | "handoff_prompt";
  fields: string[];
  mapping: Array<{
    fromField: string;
    toField: string;
  }>;
  handoffPrompt: string;
};
```

### 5.4 stale 机制

用户修改原文后：

```text
compiledSpec 不立刻删除。
节点显示“参数代码已过期”。
运行按钮禁用或提示重新协议梳理。
用户重新点击协议梳理后更新 compiledSpec。
```

这能避免用户误以为原文和参数代码仍然一致。

## 6. 协议梳理设计

### 6.1 API 形态

建议接口：

```http
POST /api/ai-dorm/work-protocol-gateway/compile
```

输入：

```ts
type CompileRequest = {
  draftId?: string;
  gatewayDraft: WorkProtocolDraft;
  capabilityCatalogSnapshot: CapabilityCatalog;
  mode: "check" | "compile" | "repair";
};
```

输出：

```ts
type CompileResponse = {
  status: "valid" | "valid_with_warnings" | "invalid";
  compiledProtocol?: CompiledProtocolDefinition;
  nodePatches: NodePatch[];
  edgePatches: EdgePatch[];
  issues: ProtocolIssue[];
  suggestedAutoFixes: AutoFix[];
  summary: string;
};
```

### 6.2 协议梳理流程

```text
1. 收集画布草稿。
2. 加载能力目录快照。
3. 生成 LLM 提示词。
4. LLM 输出候选 compiledSpec。
5. JSON schema 校验。
6. 对象存在性校验。
7. 部门权限校验。
8. Tool / Skill / RAG 输入输出校验。
9. 信息流字段校验。
10. 风险和人工确认策略校验。
11. 生成 nodePatches / edgePatches。
12. 返回 issues 和可视化标注。
```

### 6.3 LLM 输出只允许用目录内能力

提示词必须明确：


## 7. 协议注册设计

### 7.1 注册对象

只有通过协议梳理的 compiled protocol version 才能注册。

```ts
type RegisteredProtocol = {
  protocolId: string;
  name: string;
  description: string;
  enabled: boolean;
  activeVersionId: string;
  triggerRules: ProtocolTriggerRule[];
  entryNodeId: string;
  reportNodeId: string;
  createdAt: string;
  updatedAt: string;
};
```

### 7.2 版本对象

```ts
type RegisteredProtocolVersion = {
  versionId: string;
  protocolId: string;
  versionNumber: number;
  draftSnapshot: WorkProtocolDraft;
  compiledSpec: CompiledProtocolDefinition;
  capabilityCatalogSnapshotHash: string;
  compileIssues: ProtocolIssue[];
  createdAt: string;
};
```

### 7.3 触发规则

```ts
type ProtocolTriggerRule = {
  id: string;
  naturalLanguageDescription: string;
  intentTags: string[];
  requiredEntities: string[];
  priority: number;
  confidenceThreshold: number;
};
```

示例：

```json
{
  "naturalLanguageDescription": "用户要求处理工单风险、分派工单、整理工单下一步时触发",
  "intentTags": ["work_order", "risk_review", "dispatch"],
  "requiredEntities": ["work_order_ref"],
  "priority": 80,
  "confidenceThreshold": 0.72
}
```

### 7.4 启停开关

每个协议应独立开关：

```text
启用：BP问问路由器可以匹配和调用该协议。
停用：协议保留，但 BP问问不会自动走它。
草稿：只能编辑和梳理，不能被路由。
```

这比全局开关更稳，因为不同协议成熟度不同。

## 8. BP问问协议路由器

### 8.1 路由器位置

建议在 BP问问 task planning 入口附近增加 protocol router。

逻辑：

```text
用户消息
-> 普通聊天判断
-> 任务意图判断
-> 查询 enabled protocols
-> 协议匹配
-> 若匹配，生成 protocol execution task
-> 若不匹配，回落 Tool Calling 或 Longxia fallback
```

### 8.2 匹配输入

```ts
type ProtocolRouteRequest = {
  threadId: string;
  userMessage: string;
  recentContext: string;
  knownEntities: Record<string, unknown>;
  enabledProtocols: RegisteredProtocol[];
};
```

### 8.3 匹配输出

```ts
type ProtocolRouteResult = {
  matched: boolean;
  protocolId?: string;
  versionId?: string;
  confidence: number;
  missingInputs: string[];
  reason: string;
};
```

### 8.4 重要兜底

协议匹配失败不能阻断 BP问问。

兜底顺序：

```text
协议匹配失败
-> Tool Calling 规划
-> 若工具不足，Longxia fallback
-> 若仍不足，追问用户
```

协议执行失败也应回到 BP问问：

```text
协议执行失败
-> 生成失败摘要和可恢复建议
-> BP问问向用户解释
-> 可建议切换人工确认、重试、改协议或走默认工具
```

## 9. 协议运行时设计

### 9.1 统一 Context Packet

运行时每个节点传递的不是散文本，而是统一上下文包。

```ts
type ProtocolContextPacket = {
  executionId: string;
  threadId: string;
  protocolId: string;
  versionId: string;
  currentNodeId: string;
  goal: string;
  constraints: string[];
  resourceScope: Array<{
    departmentId: string;
    scopeId: string;
    resourceRefs: string[];
  }>;
  inputs: Record<string, unknown>;
  outputs: Record<string, unknown>;
  risks: string[];
  artifacts: Array<{
    kind: string;
    ref: string;
    summary: string;
  }>;
  memoryRefs: string[];
  approvalState?: {
    required: boolean;
    status: "pending" | "approved" | "rejected";
  };
};
```

### 9.2 Executor 类型


节点运行状态：

```ts
type ProtocolNodeRun = {
```

### 9.4 dry-run 优先

第一阶段不要急着真实写入。先做 dry-run：

```text

写入对象只生成写入草案，不真实提交。
```

- catalog 中不存在的能力不能被协议编译通过。

### 阶段 3：协议梳理 V1

目标：点击协议梳理后，生成参数代码和问题列表。

步骤：

1. 建 `/compile` API。
2. 实现 LLM prompt builder。

### 阶段 4：协议注册表

### 阶段 5：BP问问协议路由器

目标：BP问问能把已启用协议当成高阶工具选择。

步骤：

1. 建 protocol route service。
2. 查询 enabled protocols。
3. 构造任务意图匹配 prompt。
4. 输出 matched / protocolId / confidence / missingInputs。
5. 低置信度时不自动执行。
6. 缺关键参数时让 BP问问追问。
7. 匹配失败时回落 Tool Calling。
8. 增加 BP问问响应里的 route trace。

验收：

- 明确匹配的任务能选中协议。
- 不相关聊天不会触发协议。
- 停用协议不会被选中。
- 匹配失败仍可走原 Tool Calling。

12. 实现 `bp_ask.report` 输出摘要。

验收：

- 协议能从入口跑到 BP问问汇报出口。
- 每个节点有运行状态。
- 写入对象不会真实写入。
- 人工确认节点会暂停。

### 阶段 7：第一个真实协议闭环

目标：最小真实链路上线。

建议第一条真实链路：

```text
BP问问入口
-> Tool调用：work_order.search / work_order.read
-> BP问问汇报出口
```

步骤：

1. 注册工单查询汇报协议。
2. BP问问能匹配“帮我看某个工单状态”。
3. Runtime 调用真实 Tool。
4. 输出 context packet。
5. BP问问汇报出口生成结果。
6. BP问问把结果回复给用户。
7. 写 trace 和 execution log。

验收：

- 用户在 BP问问问工单状态时，能走注册协议。
- 协议执行结果回到 BP问问。
- 失败时能说明失败节点和建议。

### 阶段 8：龙虾执行闭环

目标：部门里的 AI员工成为真实 executor。

步骤：

1. 定义 Longxia input packet。
2. 定义 Longxia output packet。
3. 把部门 scope 注入 Longxia。
4. 把 Skill 文件夹 scope 注入 Longxia。
5. 把记忆目录 scope 注入 Longxia。
6. Runtime 下发任务给 Longxia。
7. Longxia 返回结构化结果。
8. 结果进入 context packet。
9. 结果可被汇总或回报 BP问问。
10. Longxia 失败时返回可恢复错误。

验收：

- 部门内 AI员工节点可真实执行。
- 龙虾不能访问部门外资源。
- 龙虾结果能回到 BP问问汇报出口。

### 阶段 9：写入对象与人工确认

目标：高风险动作可控上线。

步骤：

1. 写入对象 executor 只先生成草案。
2. 人工确认节点能展示写入对象、字段、diff、回滚信息。
3. 用户确认后才执行真实写入。
4. 写入后记录 changedObjects。
5. 支持 rollback_ref。
6. 拒绝确认时走失败 / 分支路径。

验收：

- 没有确认不能真实写入。
- 确认后写入成功。
- 写入结果可追踪。
- 失败可返回 BP问问解释。

### 阶段 10：高级能力

包括：

- 定时触发。
- 事件触发。
- 记忆读取 / 写入。
- 做梦整理。
- 协议模板市场。
- 自动协议推荐。
- 运行质量评分。

这些不应早于主链路上线。

8. BP问问触发。
9. 龙虾执行。
10. 结果回 BP问问。

第三批 E2E：

1. 写入对象前不加人工确认。
2. 协议梳理应给警告。
3. 加人工确认后警告消失或降级。
4. dry-run 生成写入草案。
5. 确认后真实写入。

## 14. 兜底机制

### 14.1 编译兜底

场景：模型不可用。

处理：

- 返回 `compileStatus = invalid`。
- 不覆盖旧 compiledSpec。
- 前端提示“模型不可用，保留上一次参数代码”。
- 允许用户继续编辑草稿。

场景：模型输出非法 JSON。

处理：

- 自动重试一次 JSON repair。
- 仍失败则返回 issue。
- 不注册版本。

场景：模型编造能力。

处理：

- deterministic validator 拦截。
- 标红节点。
- 给出“请选择现有能力或先注册能力”。

### 14.2 路由兜底

场景：没有协议匹配。

处理：

- 回落 BP问问 Tool Calling。

场景：多个协议同时匹配。

处理：

- 优先级 + 置信度排序。
- 差距不明显时让 BP问问追问用户选择。

场景：协议停用。

处理：

- BP问问完全不调用。
- 可在 debug trace 里显示“协议存在但已停用”。

### 14.3 执行兜底

场景：节点失败。

处理：

- 记录 failed node。
- 如果有失败分支，走失败分支。
- 如果没有失败分支，进入 BP问问汇报出口说明失败。

场景：Tool 调用失败。

处理：

- 返回 tool error packet。
- 可重试一次低风险只读动作。
- 写入动作不自动重试。

场景：龙虾超时。

处理：

- 标记 agent timeout。
- 允许重试、换龙虾、转人工、回报 BP问问。

场景：人工确认拒绝。

处理：

- 不执行写入。
- 结果回到 BP问问。
- BP问问说明已取消或询问下一步。

### 14.4 权限兜底

原则：

```text
前端显示权限只是提示。
后端 runtime 必须重新校验权限。
```

任何节点执行前都必须检查：

- 当前协议版本是否启用。
- 当前部门 scope 是否允许。
- 当前 AI员工是否可见该部门。
- 当前 Tool / Skill 是否被允许。
- 当前写入对象是否被允许。
- 是否需要人工确认。

### 14.5 审计兜底

所有执行应记录：

- 谁触发。
- 哪个协议。
- 哪个版本。
- 哪些节点跑了。
- 每个节点输入输出摘要。
- 是否使用模型。
- 是否调用 Tool / Skill / 龙虾。
- 是否写入对象。
- 是否人工确认。
- 失败原因。

## 15. 当前最推荐的下一步

不要马上接复杂龙虾执行。

最推荐下一步：

```text
先做协议 schema 和 catalog。
再做真实协议梳理接口。
再做参数代码下拉框。
再做协议注册表。
再让 BP问问读取已启用协议。
```

最小闭环应为：

```text
BP问问入口
-> Tool调用
-> BP问问汇报出口
```

这个闭环跑通后，再接：

```text
BP问问入口
-> 部门内 AI员工
-> BP问问汇报出口
```

最后再接：

```text
人工确认
-> 写入对象
```

## 16. 一句话交接

当前前端已经足够表达“工作协议网关”的产品形态。后续真正的工程重点是把它从画布升级成中枢：先整理能力目录和可动参数，再用协议梳理生成参数代码，再注册成 BP问问可调用的高阶协议，最后用 runtime 执行、审计、兜底。不要让 BP问问直接硬接所有复杂逻辑，也不要让龙虾越权自由发挥；工作协议网关应该成为两者之间可控、可启停、可追踪的编排层。
