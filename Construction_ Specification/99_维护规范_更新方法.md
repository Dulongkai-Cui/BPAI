# 维护规范与更新方法

> 目标：保证 `Construction_ Specification` 目录长期可用，避免再次变成“巨长但过时”的说明书。

## 1. 总原则

### 1.1 事实优先
- `00-05` 只记录**当前代码事实**。
- 所有结论都应能追溯到具体代码路径、schema、migration、env 或脚本。
- 如果某个能力只在 PRD、原型或会议共识里存在，放到 `06_产品意图到代码映射_仅参考.md`。

### 1.2 少复制、多深链
不要在文档里粘贴大段实现。
优先写：
- 页面/接口/服务/表在哪
- 它依赖什么
- 它影响什么
- 典型调用链是什么

### 1.3 以“索引 + 事实表 + 调用链”为核心结构
推荐每篇文档都优先使用：
- 模块说明
- 路径表格
- 调用链
- 风险点
- 待验证项

## 3. 什么时候必须更新文档

以下情况发生后，至少应更新对应专题文档：

### 3.1 页面/路由变化
- 新增 `frontend/src/app/**/page.tsx`
- 页面职责明显变化
- 组件树重组导致主入口变了

### 3.2 API 变化
- 新增或删除 `frontend/src/app/api/**/route.ts`
- 请求/响应结构明显变化
- route 改为调用不同服务层

### 3.3 数据层变化
- `frontend/src/lib/db/schema.ts` 改动
- 新增 migration
- 业务真源从 raw shadow/app-store 切到 Postgres 或反之

### 3.4 AI 能力变化
- BP Ask 新增 intent / target domain / executor
- 记忆策略变化
- 接入新的模型 SDK 或执行器
- Agent / Skill / MCP / LongxiaAdapter / AI宿舍 runner 的架构边界变化

### 3.5 运行依赖变化
- `package.json` 依赖变化
- `.env.local.example` 新增关键变量
- OnlyOffice/CAD/存储/认证机制发生变化

## 4. 推荐更新流程

### 第一步：先确认事实来源
优先读：
1. 代码入口
2. route
3. server service
4. schema / migration
5. env / scripts

### 第二步：只更新受影响的文档
不要无差别全改。
例如：
- 改工单派单逻辑 -> 至少更新 `02`、`03`、必要时 `01`
- 改 BP Ask 调度 -> 至少更新 `04`，必要时 `02`、`03`
- 改登录/会话 -> 至少更新 `02`、`05`

### 第三步：回链检查
更新完要检查：
- `00` 中导航是否还有效
- 相关专题之间引用是否仍成立
- `06` 中的状态是否需要从“部分实现”改为“已实现”

## 5. 推荐写法模板

### 5.1 页面/接口/模块表格模板

| 对象 | 入口文件 | 上游调用方 | 下游依赖 | 备注 |
| --- | --- | --- | --- | --- |
| 例：工单详情页 | `frontend/src/app/work-orders/[workOrderId]/page.tsx` | `/work-orders` 跳转 | 工单 API / work-order service | 服务端页面 |

### 5.2 调用链模板

```text
页面/组件
-> API route
-> server service
-> DB / 文件存储 / 外部服务
```

### 5.3 待验证项模板

```markdown
## 待验证项
- 当前代码中 `dispatch.ts` 通过 `frontend/src/lib/bp-ask/model-provider.ts` 调用可切换模型 provider；历史 Kimi 封装仍保留在 `frontend/src/lib/bp-ask/kimi.ts`。
```

## 6. 如何避免再次过时

### 6.1 不写“看起来会这样”
凡是没有代码锚点的推断，都不要写进事实文档。

### 6.2 不写“完整故事”，优先写“可定位事实”
开发时真正有价值的是：
- 页面在哪
- API 在哪
- 服务在哪
- 表在哪
- 谁调谁

### 6.3 明确区分“实现中”与“已落地”
如果一项能力只有：
- PRD
- 原型
- 枚举/表结构铺垫
- 但没有可操作页面/API/服务闭环

则只能写成 `部分实现` 或 `待实现`。

### 6.4 对高风险区定期复核
建议优先复核以下区域：
- `workspace/server.ts`
- `store/raw-shadow.ts`
- `db/app-store-read.ts`
- `db/app-store-write.ts`
- `bp-ask/dispatch.ts`
- `content/server.ts`
- `work-order/server.ts`

这些区域最容易因为迁移或功能扩展而让旧文档失真。

## 7. 推荐的最低维护节奏

如果项目继续快速开发，建议：
- 每完成一个里程碑或一个大 PR，至少更新一次相关专题文档
- 每次新增 migration，都回头看一次 `03_数据库模型_迁移_业务映射.md`
- 每次扩 BP Ask，都回头看一次 `04_AI链路_BPAsk_记忆_调度.md`

当本目录第一轮稳定后，可以继续补：
